## Incidents during the audit (for the owner)

1. Two slices (node, gates) each ran a `find /` that did not prune `/tank`. Each walk read part of
   `/tank/media` for up to two minutes before it was stopped. Both walks were read-only, and nothing
   hung because the node was reading the share at the time. The "never touch the media mount" memory
   should also say that `-not -path` does not prune: use `-path /tank -prune`, or never walk `/`.
2. The last check-pr (another agent's) took **327 s against its 300 s budget** (G8).

## Executive summary

Overall the system is in good health. The **store** is the most disciplined part of the system: query plans are tested, upserts
write only when something changed, the writer gate puts people first, and an AST sweep found no
network or node call inside any write transaction. **Remote access** is sound: limits are explicit
and tested, slow Watch Together devices are dropped rather than blocking the hub, the core's retries
are jittered, and connect's pin matches HEAD. The problems below are mostly ones that grow over
time, plus a few hot-path costs. Six themes:

1. **Hot-path values are recomputed rather than cached against a known event (principle §11).**
   This is the biggest group, and almost all of it can be fixed without you.
   - Every settings read is a SQLite query plus a JSON decode, about 20 µs each, across about 90
     call sites (S2/C2). It is already queued and not yet built. Its absence has bred three ad-hoc
     settings caches, which breaks rule 11.
   - Each chunk request rebuilds the film's grid 2–4 times: about 15–20 statements and two decodes
     of roughly 80 KB of timeline JSON (C1).
   - The node parses `/proc/self/mountinfo` on every gated disk operation, including every 1 MiB
     fdproxy read. That is about 15–18 % of a core during a 100 MB/s remux (N2).
   - The node walks and stats the whole prepared directory at every run start, which is a seek
     cost: about 4 s at the default 200 GiB cache (N1).
   - The node re-hashes the film on every run (N4).
   - Each viewer's `/waits` poll reads every open read-through (S5).
2. **Polling where the system already knows the event.**
   - On the server: 11 idle job runners take the cache.db writer about 22 times a second (C6/G4).
     The interest raiser scans every open job every 5 s and re-raises every file ever watched each
     minute (C4/S6). Waits on the request path re-poll every 100–250 ms (C11).
   - In Watch Together, clients' 1 Hz reports drive the hub's wait deadline, and each report sends
     the full roster to everyone, about D² messages a second (R2).
   - On the web: polls keep running in hidden tabs (W2), every polled resource is fetched twice
     at cold start (W3), unchanged answers have no ETag (W5), and four poll loops sit beside "the
     one way to poll" (W4).
3. **Two or more ways to do one job, at the architecture level.**
   - Two transcoding pipelines. The whole-film prepare (about 2.3k lines with its own budget,
     eviction, routes and job kind) now runs only as a fallback for the chunk ladder (C9/N6).
   - Three disk-concurrency mechanisms, while the D329 scheduler is not yet wired (N8, known).
   - Two ways to ask for an identification pass: a scan batch re-passes **every** library (C8).
   - Four hand-written backoffs beside `platform/backoff` (G9), and the replay nonce written twice,
     once in each repo (R4).
4. **Things that grow with uptime or with the library, and are never bounded.**
   - The chunk run tracker never forgets a store (C5).
   - The raiser's watched-file list (C4).
   - Cancelling a run lists every open job of every kind, on the seek path (C3).
   - *Needs a match* is unpaged and polled (S9/W6).
   - Watch Together sessions and links never expire (R6).
   - A refused node result is retried forever (N7).
5. **The gate has slowed by about 4× in 17 days, and nothing noticed.**
   - A test helper opens a new SQLite pool per query and re-parses the 161-row schema each time.
     That is 40 % of identify's CPU; identify went from 6.4 s to 94–99 s in the full suite, and the
     uncached Go step is now 109–115 s (G1).
   - The store's test package reads the whole repo, so it never caches and `make spot` misses it
     (G2).
   - make check's 90 s budget is never measured (G6).
6. **Operability gaps.**
   - Nothing is compressed: the client is 980 KB, 292 KB gzipped (R1, decided in D129, not built).
     There is no code splitting either, so hls.js and the device lab load on the home page (W1).
   - connect.db has no continuous or off-site backup, while outside testers depend on it (R5).
   - There are no runtime log levels, only 12 Debug calls in the whole codebase, and no request ID (G11).
   - The node has no pprof (N13), the core cannot see whether a node reads through fdproxy (N9),
     and retry loops flood the log during an outage (C12).

**What to do first** (each takes an hour to a day, needs no owner decision, and gives a measurable
win):

1. Reuse the pool in `storetest.QueryRaw`/`ExecRaw` (G1).
2. Keep the settings in memory (S2).
3. Share one hash cache between the node's agent and byte socket (N4).
4. Cache the mount table (N2).
5. Cancel by kind and target in SQL (C3).
6. A scan owes a pass only to its own library (C8).
7. Keep an in-memory size index of the prepared directory (N1).
8. Memoise the cut film (C1).
9. Gzip the assets and JSON (R1).
10. Split the code by route (W1).

The decisions that need you: retire whole-film prepare (C9/N6); make sweeps into jobs (C7); back up
connect.db (R5); expiry for Watch Together sessions and links (R6); the gate-side test fixes (G3,
G6, G2's reader list).

## Appendix: Store / SQL layer — audit findings (2026-10-25)

Scope: internal/store (open.go, statistics.go, cache.go, jobs.go, interest_jobs.go, waiting_jobs.go,
search.go, queries, cache/schema.sql), and how internal/core and cmd/orpheum call it. Read-only.

Overall: the store is the most disciplined part of the system. Query plans are tested
(TestQueryPlans_EveryQueryReadsByAnIndexOrSaysWhy, ..._EverySearchNarrowsToAFewRows), every
upsert writes only on change, the writer gate puts people's writes first, slow writes name what
they waited behind, FK child indexes are enforced, backups run off the writer. An AST sweep of
every `Write(...)` closure in internal/ and cmd/ found **no network, node or provider call held
inside a write transaction** (all closures call only queries, clock and pure helpers). The
findings below are therefore mostly at the edges: pool configuration, hot-path reads that should
be memory, background loops that re-do work, and the cache.db side, which has less of the
persistent side's tooling.

Method notes (numbers in S1 and S2 measured after check-pr ended): AST scan for store queries inside for/range bodies (42 sites, most are writes
inside one transaction, which is fine in SQLite); AST scan of write closures; reading of each
read-side site. A micro-benchmark (overlay test, no repo edit) was prepared at
scratchpad/zz_audit_test.go + overlay.json, but the pre-bash hook refused test runs while
`make check-pr` ran (started 20:45 UTC, still running at 20:56, over its 300 s budget). Numbers
below marked "measured earlier" come from data-layer-practice-2026-10-15.md §1.8.

## S1. Reader-pool idle size depends on whether statistics were just reloaded (low-medium)

- **Evidence:** `open.go:155` sets `readers.SetMaxOpenConns(max(MinimumReaders, NumCPU))` but no
  `SetMaxIdleConns`, so database/sql's default of **2 idle** applies. The only `SetMaxIdleConns`
  in the store is `statistics.go:69-71`, which runs only when the committed statistics differ from
  the stored ones (`statistics.go:61` returns early when equal). So a freshly migrated or
  re-statisticed database keeps NumCPU idle readers; an ordinary restart keeps 2. Same for
  cache.db (`cache.go:61` via `open`; it never loads statistics, so always 2).
- **Why it matters:** with more than 2 concurrent reads (the poster grid's art + list + polls,
  Watch Together, the interest raiser, sweeps), each extra connection is closed on release and a
  new one opened next time: re-parse of the schema (58 tables, triggers, views), re-applying 7
  pragmas, reloading sqlite_stat1, and an empty 16 MiB page cache (`cacheSizeKiB`, chosen in DL16
  precisely so passes stop re-reading pages). The DL16 page-cache win is silently lost for every
  connection beyond the second, and the behaviour differs between first boot and later boots.
- **Measured (2026-10-25, 8 CPUs, overlay test scratchpad/zz_audit_test.go):** 16 goroutines x 2000
  ReadTx: idle=2 closed 10 connections, idle=8 closed none; wall time 404 ms vs 434 ms, so no
  throughput loss in a tight loop. The cost is the lost warm page cache and schema under bursty
  real load, not raw throughput: lower priority than first thought.
- **Fix:** in `open()`, `readers.SetMaxIdleConns(readers' max open)` (and 1 for writer and
  maintenance, which they already effectively have); make `loadStatistics` restore that same value
  instead of computing its own. Add a store test that the reader pool keeps as many idle as open
  after Open, with or without a statistics reload.
- **Cost:** 30 min. **Fixable without the owner** (internal store code; open.go is a twin of
  orpheum-connect's, so copy it there in the same batch per doc.go).
- **Known?** New: not in database-access-audit, data-layer-* or data-delivery-* reports.

## S2. Settings are read from SQLite on every use, including per chunk and per request (medium)

- **Evidence:** `settings/settings.go:207-231` — every `Int/Duration/Bool/String` runs
  `GetSetting` on the reader pool, plus `json.Unmarshal`. Hot callers:
  - every authenticated request: `auth.Authenticate` → `sessionIdleExpiry` (`auth/auth.go:578`,
    `auth/policy.go:104`) — one statement outside the request's ReadTx;
  - every chunk ask: `chunks.ensure` → `refreshChunkTiming` (`chunks/chunk_timing.go:38-61`, 3
    settings), plus `ChunkKeptAheadSeconds` (`chunks/interest.go:65,222`),
    `HLSSegmentLengthSeconds` (`chunks/grid.go:147`), `PlayPriorityKeptSeconds`
    (`jobs/queue.go:249`, on every KeepWanted, which the comment says runs "several times a
    second");
  - every artwork serve (`artwork/serve.go:121,129`), every waits/interest tick, every loop's
    `Every` (`cmd/orpheum/metadata.go:521`).
  ~90 call sites over 30 files read settings this way.
- **Measured:** one `GetSetting` through `Read()` takes 19.6 µs (serial, 8-CPU sandbox, fresh DB);
  a one-statement ReadTx 32.8 µs. A chunk ask's ~6 settings reads come to about 120 µs of SQLite work
  and 6 pool checkouts. A map lookup would cost well under 1 µs.
- **Why it matters:** principle §11 ("a value on a hot path is cached against a known event")
  — the core is the only writer (`Set`/`Reset` already run `OnChange` reactions). Its absence has
  already produced **three ad-hoc "as last read" caches** — `chunks/runs.go:25` +
  `chunk_timing.go` (comment: "so its paths, which hold its lock, never wait on the database"),
  `playback/playback_timing.go:31`, `providers/service.go:171` — a rule-11 smell (two ways to hold
  a setting) that will keep multiplying.
- **Fix:** keep a decoded snapshot of all settings in `settings.Service` (atomic pointer to a
  map), loaded at start, replaced inside `Set`/`Reset` after commit (they already know the keys);
  `read` becomes a map lookup. Then delete the three local caches. A test: N reads run zero
  statements (querytally), and a Set is visible to the next read.
- **Cost:** half a day including removing the local caches. **Fixable without the owner** — the
  owner already queued it (memory "queued-db-performance-work", item 1; data-delivery-and-caching
  DD13 / finding 9). **Known, not landed.** One owner question only if settings may ever be written
  by another process (doctor/CLI on a live server) — then an invalidation via `Commits()` or
  data_version is needed; check cmd/orpheum's offline commands.

## S3. Read endpoints are not snapshots, and title detail is N+1 on files (low-medium)

- **Evidence:** only 3 `ReadTx` callers in core (`library/progress.go:30`, `identify/pass.go:247`,
  `auth/auth.go:583`) against 113 `Read().` call sites. `Browser.Title` (`library/detail.go:49-79`)
  runs GetTitleDetail, ListTitleFiles, **one ListStreamsOfVideoFile per file**
  (`detail.go:92`), ListTitleExtras, 3× ListShownArtwork (`art.go:50-63`), episodePlace,
  unreadableItems — each on its own commit and its own pool checkout. Same shape in `Series`,
  `List`, `chooser.Items`, `admin.go:186-225` (CountLibraryFilings per library, ListRootMounts per
  root), `renditions/finished.go:44` (GetFilePath per finished prepare), `nodes/enrol.go:161`
  (GetLibraryForRoot per root).
- **Why it matters:** D303 M2 says a page built from several queries reads through ReadTx; today a
  pass committing mid-request can give a page versions from one commit and art from another. N+1
  here is CPU, bounded by a title's files, so the cost is small; the snapshot is the real point.
- **Fix:** wrap `Browser.Title/Series/List` and the System summaries in `ReadTx`; replace the
  per-file streams with one `ListStreamsOfTitleFiles(title_id)` grouped in Go; one
  `ListShownArtworkOfItem` for all kinds. Add the request-level statement-count test DL6/MD6 asked
  for (TestBrowse_*_RunsTheSameStatementsAtTwiceTheFiles), which does not exist today: only the
  identify pass and the scan comparison have one (`identify/pass_cost_test.go:18`,
  `library/compare_test.go:351`).
- **Cost:** half a day. **Fixable without the owner.** **Known, not landed:**
  data-delivery-independent-review-2026-10-16 MD6, F11, F12; plan step 7 there.

## S4. The read-through sweep enqueues one cache.db write transaction per file, every sweep (medium)

- **Evidence:** `readthrough/readthrough.go:260-275` loops `queue.Enqueue` per file;
  `store/jobs.go:44-66` makes each Enqueue its own `cache.Write` (IMMEDIATE, through the writer
  gate). The sweep re-runs every `read_through_sweep_every_hours` (`cmd/orpheum/metadata.go:507`)
  over every file still lacking loudness or a timeline; files already queued come back as
  `ActionMerge` (`platform/jobqueue/queue.go:206-222`), and `MergeQueuedJob`
  (`cache/queries/job.sql:35-39`) rewrites the row even when nothing changes (it is an UPDATE, so
  the upsert-only-if-changed vet rule does not see it). Same per-item pattern in
  `identify/refresh.go:413,512` and `artwork/make.go:93`.
- **Why it matters:** after a first import of 20k files, each sweep is 20k writer acquisitions and
  commits on cache.db, interleaved with the job runners' claims (also cache.db writes) and the
  interest raiser. The gate keeps people first, but each claim still waits behind whichever
  enqueue holds the writer, and WAL grows with rewritten identical rows.
- **Fix:** an `EnqueueMany` on JobStorage/jobqueue that plans and applies a batch (say 500) in one
  transaction, and a merge that returns `ActionNone` when args, priority, runnable_at and
  destination are unchanged (or `WHERE ... AND (args_json IS NOT ? OR priority IS NOT ? ...)`).
  Test: a second sweep over an unchanged library takes the writer ⌈N/batch⌉ times and changes 0
  rows (RowsChanged), mirroring TestPass_OverAnUnchangedLibrary...TakesNoWriter.
- **Cost:** a day. **Fixable without the owner** (internal API, no behaviour change).
- **Known?** New as stated; D303 DL9 covers upserts only.

## S5. The waits estimate reads every open read-through on every poll (medium, grows with the queue)

- **Evidence:** `waits/waits.go:176-211` — `readThroughOf` calls `OpenReadThroughs`
  (`store/waiting_jobs.go:31`, `ListOpenReadThroughs`: every open read_through job, decoding each
  one's args_json via `readthrough.IsIndexRead`), then `ListFileSizesAndNodes` with a json_each of
  all their file ids — **before** it knows whether this file has an open read-through at all
  (`fullReadsAndOwn` decides `isOpen` after reading everything). The client polls
  `GET /files/{id}/waits` every `interest_said_every_seconds` (15 s) per viewer of a film page
  (`web/apps/web/src/file-waits.ts:31-41`).
- **Why it matters:** after an import the open read-throughs are the whole unread library (S4's
  sweep), so each poll by each viewer reads O(library) rows from both databases to answer a
  question about one file — DL6's "nothing a request does grows with the library", violated, and
  untested (S3).
- **Fix:** first `ListOpenJobsOfTarget(read_through, file)`; return nil when none (the common
  case). When one is open, compute "bytes ahead on its node" in SQL on cache.db alone, or keep a
  per-node running total in memory (the estimator already keeps per-node speeds in memory).
  Test: the waits request's statement count and rows are the same at 1× and 2× open read-throughs.
- **Cost:** half a day for the early exit (most of the win), a day for the in-SQL sum.
  **Fixable without the owner.** **Known?** New (data-timeliness audits designed the estimate,
  not its cost).

## S6. Interest raising re-writes "for good" raises every minute and takes the cache writer each tick (low-medium)

- **Evidence:** `interest/raise.go:199-215` `RaiseWatched` runs every 12th 5 s tick
  (`raise.go:279`, `cmd/orpheum/metadata.go:103`): every live file anyone has ever watched and
  its title (`ListWatchedLiveFiles`, listed as a whole read in `plans_test.go`) as two JSON arrays
  into `RaiseJobsOfInterest` (`store/interest_jobs.go:27-58`), which **always** takes the cache
  writer, lists matching open jobs by `json_each` IN-lists, then runs one `RaiseJob` UPDATE per
  open job. A raise "for good" is persistent (priority only rises), so repeating it each minute
  only matters for jobs enqueued since. `demoteUnwanted` also takes the cache writer every 5 s
  (`metadata.go:653`) whether or not anything is wanted.
- **Why it matters:** the arrays grow with watch history (thousands of ids for a household after
  a year), and the minute-ly write contends with job claims; it is a poll maintaining an invariant
  that has a known event (a job's enqueue, or a first play).
- **Fix:** give the priority at enqueue time: Queue.Enqueue asks "is this target watched?" (an
  in-memory set the raiser refreshes, or a cache.db `watched_file` table written on first play),
  and drop RaiseWatched's loop; meanwhile, cheaply, run the list in a read transaction and take the
  writer only when some job's priority is below the target (the WriteUnlessUnchanged pattern
  persistent.db already has — cache.db has no equivalent).
- **Cost:** 2 h for read-first; a day for at-enqueue. Read-first **fixable without the owner**;
  moving the raise to enqueue time changes when work is prioritised — **needs the owner** (D324).
- **Known?** New.

## S7. cache.db has none of persistent.db's plan tooling (low-medium)

- **Evidence:** only `statistics/persistent.tsv` exists; cache.db never loads statistics
  (`cache.go:56-81`), so its planner uses defaults. `TestQueryPlans_EverySearchNarrowsToAFewRows`
  iterates `queriesIn(t, "queries")` + search only (`plans_test.go:375`), so no cache query is
  checked for weak searches. Several cache queries filter on json_each IN-lists over job without an
  index on `item_id`/`file_id` alone (`job.sql:166-172`, `185-192`); only `job_open_target`
  (leading on kind) and `job_state` exist (`cache/schema.sql:59-68`). There is no
  `WriteUnlessUnchanged` for cache.db (S6).
- **Why it matters:** the job table is the busiest table in the system (claims, enqueues, raises,
  demotions), it holds the whole library's work after an import, and its plans are the least
  checked.
- **Fix:** commit `statistics/cache.tsv` from a reference-scale queue (TestReferenceScale already
  builds persistent's), load it in OpenCache, extend the weak-search test to cache queries; add
  partial indexes `job(item_id) WHERE state IN open` and `job(file_id) WHERE state IN open` if the
  plans show scans. cache.db is versioned by discard, so a schema change is cheap.
- **Cost:** half a day. **Fixable without the owner**, except that adding a statistics file and
  changing plan-test lists touches test baselines — `plans_test.go` allowlists may count as a gate
  (scripts/gate_paths.py lists `testdata/golden|baselines`); confirm, and **ask the owner if the
  allowlists are gates**.

## S8. Every statement is re-prepared; hot reads pay the compile each time (low)

- **Fix:** `emit_prepared_queries: true` (database/sql then prepares per connection lazily) once
  S1 keeps connections alive; measure before and after with the prepared overlay benchmark.
- **Cost:** 1 h + regenerate. **Needs the owner:** `sqlc.yaml` is a gate file
  (`scripts/gate_paths.py:29`). **Known, not landed** (data-layer-practice §1.8 noted it).

## C1. A chunk request rebuilds the film's grid two to four times — HIGH (medium at today's load)

**Evidence.**
- `api/chunks.go:118` getChunkFile → `chunks/files.go:53` offeredStream → `chunks/offer.go:421`
  cutForPlay → `chunks/grid.go:133` cut. Each cut runs `library.PlayableFile` (a join), reads
  `hls_segment_length_seconds`, reads `GetVideoTimeline`, json-decodes the probe, the keyframes
  and the per-second byte counts (`grid.go:138,172,175`), then rebuilds the grid (`GridOf`).
- `offerOf` (`offer.go:112`) then reads `chunk_qualities` (or `_hardware`), `chunk_sound_kbps`
  and the loudness levels, and parses the quality ladder string. When the stream is not in the
  offer, offerOf runs a second time (`offer.go:437`).
- After a chunk is served, `Served` (`files.go:184`) calls askedFor → `ensure.go:62` cut, which
  is a whole second cut, plus `refreshChunkTiming` (`chunk_timing.go:38`), which reads three
  settings, plus a cache.db write (`KeepWanted`, `files.go:191` / `ensure.go:82`).
- The master playlist handler runs cutForPlay and offerOf twice: `MasterPlaylist` then `Ladder`
  (`api/chunks.go:96-101`, `offer.go:301,345`).
- Around all of this sit Authenticate (a settings read plus a read tx of 3+ statements,
  `auth/auth.go:572`), ChunksOf (one settings read, `playback/chunks.go:17`) and `chunk_hold_ms`
  (`api/chunks.go:162`).
- Traced total for a chunk the node already has: **about 15–20 SQL statements, 2 full timeline
  decodes (~80 KB of JSON each, 2–5 ms of CPU), and one cache.db write transaction.** That is per
  request, for the picture and for the sound, every few seconds, for every viewer.
- Nothing shows it. `api/slow_requests.go:57` `isTimedRequest` leaves `/bytes/` paths out of the
  query tally, so the slow-request log never covers the busiest path.

**Why it matters.** Principle §11 (a hot-path value is cached against a known event). The grid
changes only when a read-through upserts the timeline or a setting changes, and the core causes
both. On the production NAS (i3-N305) x264 shares the CPU, so per-chunk allocation churn and decode time add
directly to time-to-first-byte and to the GC pressure that stalled playback before (memory:
the settings-registry stall, 2026-10-05).

**Fix.**
1. Memoise `cutFilm` per (file id, payload hash, grid kind, segment length) in the chunks
   service. Invalidate it on the timeline upsert (readthrough keep), on the segment-length setting
   (`settings.OnChange`), and when a file is retired.
2. Have `ensure` and `Served` take the cut film they already have instead of cutting again.
3. Have the master handler compute the offer once and derive the ladder from it.
4. Tally `/bytes/` statements at debug level so the change can be measured.

**Cost.** M (1–2 days with tests). **Fixable without the owner.** It is DD13's rule applied:
the invalidating event is the core's own.

## C3. Cancelling a chunk run lists every open job of every kind — MEDIUM (new)

**Evidence.**
- `chunks/interest.go:82` cancelRun → `jobs/sweep.go:51` CancelMatching →
  `platform/jobqueue/sweep.go:150` CancelWhere → `store/jobs.go:367` ListOpen →
  `ListEveryOpenJob`, which returns full rows of every queued, running and assigned job.
- The match is done in Go (`json.Unmarshal` of each candidate's args), and then each match gets
  its own `Cancel` write transaction.
- This runs on the playback path: `Want` → `StopUnwanted` on every request for a chunk not yet
  made, whenever a run is no longer wanted (a seek past it).
- During a library's first scan there are thousands of open fetch, artwork and read-through jobs.

**Why.** A seek during a scan pays O(open jobs) in row decoding on the request's path, in line
with the "a person's work never waits for background work" scenarios (D324).

**Fix.** Add a store query `ListOpenJobsOfKindAndTarget` (the `job_open_target` index already
covers kind plus target), and cancel the matches in one transaction. Keep CancelWhere for
retires, which are rare.

**Cost.** S. **Fixable without the owner.**

## C4. Interest raising scans all open jobs every 5 s, and raises every watched file each minute — MEDIUM (new)

**Evidence.**
- `interest/raise.go:116` Raise runs every `raiseInterestEvery` = 5 s (`cmd/orpheum/metadata.go:103`)
  → `store/interest_jobs.go` RaiseJobsOfInterest.
- Inside one cache.db write transaction it runs `ListOpenJobsOfItemsAndFiles`. The plan, checked
  with Python's sqlite3 3.46 against `cache/schema.sql`, is `SEARCH job USING INDEX job_state
  (state=?)` followed by `USE TEMP B-TREE FOR ORDER BY`. That is every open job, filtered by
  `item_id IN json_each OR file_id IN json_each` (job.sql:166).
- It then runs one `RaiseJob` UPDATE per row. Each one writes, because `wanted_until` advances
  every tick.
- `RaiseWatched` (`raise.go:199`) runs every 12th tick (60 s). It lists every live file anyone has
  ever watched (`ListWatchedLiveFiles`) and raises all of their open jobs. The list grows with the
  household's history.

**Why.** It costs a writer transaction every 5 s, O(open jobs) per tick, and N row-writes. It
competes with the playback writes that S8 (data-timeliness) says go first.

**Fix.**
1. Bump the cache schema version and add partial indexes `job(item_id)` and `job(file_id)`
   WHERE state IN the open states. cache.db is discardable by design, so this needs no migration.
2. Use one `UPDATE … WHERE … RETURNING`, and skip rows whose priority and wanted_until would not
   change.
3. Give the watched rung at enqueue time (a job for a watched file starts at shown-interest)
   instead of re-raising the whole history every minute.

**Cost.** S for 1–2. M for 3. **Fixable without the owner.** Point 3 keeps D324 §2's
behaviour; it only changes when the rung is applied.

## C5. The chunk run tracker never forgets a store, and walks every store ever played — MEDIUM (new)

**Evidence.**
- `chunks/runs.go:17` `storeByDir` and `:20` `evictedOnAt` have no delete. Each store keeps
  `isMade map[int]bool`, one entry per chunk ever served (`runs.go:200,234`).
- `runByFirst` is pruned (`runs.go:211,220`), but the store entry itself never is.
- `cutUnwanted` (`interest.go:131`, called on every not-made chunk request via StopUnwanted) and
  `runningOn` (`capacity.go:74`, the upload and capacity paths, every 5 s through
  KeepUnderShare) range over every store under the tracker's one mutex, parsing each dir string
  (`streamOfStore`).
- `playback/unplayable.go` `films` and `readthrough` `noIndex.byKey` likewise only grow (small).

**Why.** Memory and per-request CPU grow with uptime: each film watched × streams × chunks. That
is roughly 0.5 M map entries a month for a household, and more with Watch Together quality
switching. Contention on the tracker mutex grows with it.

**Fix.**
1. Key the stores by file id (`map[fileID]map[dir]*storeRuns`), so the per-file paths touch only
   that film.
2. Forget a file's stores when its last playback's token goes and no run is on its way. The
   release path in `chunks/release.go` is the natural hook.
3. The node's own store index stays the truth for "made". The core may only forget, never
   wrongly remember (§14).

**Cost.** S–M. **Fixable without the owner.**

## C6. Idle job runners make ~22 cache.db write transactions a second — MEDIUM (new)

**Evidence.**
- `cmd/orpheum/metadata.go:558-576` starts 11 runners (one per kind, concurrency 1), each with
  a 1 s ticker.
- Every tick, `jobqueue/runner.go:78` RunDue calls `failOverdueAssigned` → `TakeOverdueAssigned`,
  an UPDATE in `cache.Write` (`store/jobs.go:280,291`), then `claim` → `Claim`, also a
  `cache.Write`, holding `queue.claimMutex`, which every kind shares (`runner.go:174-187`).
- So, with nothing to do: 11 × 2 writer-gate acquisitions per second, all serialised.
- On top of that: the 1 s silence watch, the 5 s demote (a query), the 5 s raise (C4), and the
  1-minute sweep check.
- The wake channels (`registerWake`) already make the tick redundant except for retries coming
  due and assignments running out.

**Why.** It is background noise on the single writer, which is the scheduled resource (S8). It
wakes the CPU on an idle NAS, and every claim attempt shows in the writer gate's statistics.

**Fix.** Each runner sleeps until the earliest of: a wake, `min(runnable_at)` of its kind's queued
jobs, and `min(assigned_until)` of its assigned ones. That is one cheap read through
`job_claim`/`job_state`, re-armed after each claim or enqueue. Run the overdue check once per
queue, not once per runner.

**Cost.** M (timing semantics need care and fake-clock tests). **Fixable without the owner.**

## C7. Sweeps do heavy work inline and in turn, outside the queue's priorities — MEDIUM (needs the owner)

**Evidence.**
- `platform/jobqueue/sweep.go:94` Sweeping runs every due or requested sweep on one goroutine,
  one after another.
- Several sweeps are not derivations that queue jobs. They are the work itself:
  - `pass.IdentifyAll` / `IdentifyOwed`: every library's pass plus `RefreshSortAndSearchKeys`
    (`identify/pass.go:117,138-157`);
  - the invariants check;
  - the two retention purges (`cmd/orpheum/metadata.go:446-512`).
- While a pass over a large library runs, the backup, certificate and scheduled-scan sweeps wait.
  So do requested sweeps (a destination coming back).
- The pass also gets no priority, parking or progress in the job view.

**Why.** D231 §3's model is that "sweeps derive, jobs do". Here the heaviest database work in the
core sits outside the scheduler that D324 and data-timeliness spend so much design on, and it
cannot be pre-empted or seen.

**Fix.** Make the pass, invariants and purges job kinds (`identify_library` per library, and so
on), and have their sweeps only queue them. Alternatively run each sweep on its own goroutine.

**Cost.** M–L. **Needs the owner:** it adds job kinds and changes what the job view shows.

## C8. Two ways to ask for an identification pass; new files re-pass every library — MEDIUM (new)

**Evidence.**
- `cmd/orpheum/nodes.go:101-102`: when a scan batch stores a new file, it calls
  `sweeps.RequestSweeps(sweepPasses)`, which runs `IdentifyAll`, the pass of every live library.
- Matches and refreshes use `pass.OwePass(libraryID)` (`identify/owed.go:29`), one pass per
  library however many ask (D303 DL14).
- So a scan of library A that adds files in several batches re-runs the passes of libraries B, C
  and the rest, each followed by a full `RefreshSortAndSearchKeys`.

**Why.** Rule 11 (two ways to do one job), and wasted whole-library reads during the scans that
already load the writer.

**Fix.** Have the ingester's hook call `OwePass` for the libraries covering the scanned root.
Keep `sweepPasses` for the hourly and start-up runs only.

**Cost.** S. **Fixable without the owner** (mechanical, and behaviour-preserving for the library
scanned).

## C10. One mutex serialises every scan's batch ingest — LOW (new)

**Evidence.**
- `library/scans.go:67` `Scans.mutex` is held across `openBatch`, `IngestScan`, which is a

- `library/ingest.go:154` also holds `Ingester.mutex` while the `onNewFiles`, `onPathsFound` and

**Fix.**

**Cost.** S–M. **Fixable without the owner.**

## N1. Starting a run of chunks walks the whole prepared directory, on the seek and play path. HIGH

- **Evidence:** `chunks.Maker.Make` calls `keeper.MakeRoom` (internal/node/chunks/maker.go:143)
  before FFmpeg starts. `prepared.Shelf.MakeRoom` calls `Evict` (shelf.go:131-132), which calls
  `listRuns` (shelf.go:298-322). That globs every `<file_id>/<profile>/<run>` and runs
  `diskspace.TreeBytes` (a `WalkDir` plus a `Stat` per file) over each one, including every chunk
  store. `Preparer` does the same (prepare.go:106), and so does the agent after every prepare
  (agent/prepare.go:63).
- **Measured:** on staging's prepared directory (.staging/node/cache/prepared): 35 stores, 3,650
  files, 1.1 GiB, **22.6 ms** walking warm. That is about 3,300 files per GiB. At the default
  `prepared_budget_gib = 200` (internal/deployment/templates/node.toml:17), a full directory is
  about 660k files, so **about 4 s per run start warm**. Cold dentries on a spinning cache disk
  make it far longer.
- **Why it matters:** a make_chunks run starts when a player first asks for a chunk, and again at
  every seek outside a run (D247 §10, D260). So this cost lands directly on play-start and seek
  latency, and grows with how full the cache is. Concurrent starts also walk the tree concurrently.
- **Fix:** keep an in-memory index of run sizes. Walk once at start (or read sizes from the
  manifests). Add each chunk's bytes as `PutChunk` stores it, and each rendition's at its end
  (prepare already measures it, prepare.go:141). Subtract on eviction. `Evict` then sorts the index
  and walks nothing. Optionally re-walk once an hour as a self-check (principles §14).
- **Cost:** about 1 day including tests. **Fixable without the owner** (internal; behaviour stays
  the same).

## N2. Every gated disk operation reads and parses /proc/self/mountinfo, including every 1 MiB fdproxy read. MEDIUM-HIGH

- **Evidence:** the node's gate is built with `KeyingByMounts(hardware.MountPointOf)`
  (cmd/orpheum/node.go:428). `diskwatch.Run` calls `gate.placeOf` (gate.go:104, 73-82), which
  calls `MountPointOf`, which calls `readMounts("/proc/self/mountinfo")`
  (hardware/storage.go:164-168) on every call. `fdproxy.FileSource.ReadAt` runs each READ through
  `diskwatch.Run` (filesource.go:46-63), at the 1 MiB block the spec prefers
  (fdproxy-specification.md:388). The byte socket does the same on every range or segment open
  (byteserver.go:174). `readMounts` is also quadratic: `slices.DeleteFunc` runs per line.
- **Measured:** one `readMounts` on this sandbox's 44-line mountinfo takes **1.5-1.8 ms** (about
  0.5 ms to read, about 1 ms to parse). A remux reading 100 MB/s makes about 100 gated reads per
  second: **about 150-180 ms of CPU per second, 15-18 % of a core, per run, spent finding the same
  mount point.** A NAS with Docker or ZFS has hundreds of mounts, so it costs more there. Each read
  also starts a goroutine and a timer and does an fstat (filesource.go:53), which is small next to
  this.
- **Fix:** cache the mount table in hardware or diskwatch. Re-read it when the kernel signals a
  change: poll() on /proc/self/mountinfo raises POLLPRI on a mount change, or simply re-read it
  each hello or status tick. Or resolve the place once per `FileSource` or `OpenedFilm` and pass it
  in. Replace the per-line `DeleteFunc` with a map.
- **Cost:** half a day. **Fixable without the owner.**

## N3. Every embedded text subtitle track is its own job and its own whole-file read, and only one runs at a time. HIGH (disk I/O)

- **Evidence:** `nodeproto.ExtractSubtitle` carries one `StreamIndex` (nodeproto/subtitle.go:11-16).
  The extractor maps one stream per run (`-map <one>`, subtitle/extract.go:118). The core extracts
  "every text subtitle track of a played video" when it is played (core/subtitles/doc.go
  invariant 1). `SlotExtract` has one slot (nodeproto/commands.go:143, 169-171).
- **Why it matters:** a film with N text tracks costs N full reads of a 20-60 GB file. The reads
  are serial, each about 200 s per 20 GB at 100 MB/s (data-timeliness.md:170), and they compete on
  the same disk with the playback that started them. The 8th track becomes available only after 7
  whole reads. On NFS or spinning disks that is tens of minutes of extra seeking during viewing.
- **Fix:** one extraction per video naming all its text tracks. FFmpeg writes several outputs in
  one pass (`-map 0:s:a … out1 -map 0:s:b … out2`, ASS to temp outputs, or one pipe per track
  through ChildFiles). One answer carries every track's text. The longer-term plan to compute
  subtitles from the playback's own read (data-timeliness.md §4.4) is separate and still open.
- **Cost:** 1-2 days, covering the protocol (bump ProtocolVersion), the core job keyed per video
  not per track, and the tests. **Mostly fixable without the owner:** the protocol may change
  freely (break-early). It changes the job's granularity, though, so the owner should hear of it.
  Folding it into the read-through pass **needs the owner**.

## N4. The agent re-hashes the film on every run; only the byte socket remembers hashes. MEDIUM

- **Evidence:** the agent opens command files with the uncached `namedfile.OpenNamed`
  (agent/agent.go:206). Each prepare, read-through, index-keyframe read, chunk run and subtitle
  extraction recomputes `hash.PayloadIdentity`. That reads the payload's first and last MiB and
  walks the container (namedfile.go:138-160). The byte socket keeps a `namedfile.Hashes`
  (byteserver.go:65). A play-start index read (agent/readthrough.go:98) and each chunk run that
  follows (film.go:24) hash the same unchanged file again.
- **Why it matters:** each re-hash is 2 MiB of reads plus seeks to both ends, on the seek path (N1
  again) and on cold or network disks.
- **Fix:** build one `namedfile.Hashes` in cmd/orpheum/node.go, share it between byteserver and
  the agent, and set `openFile = hashes.OpenNamed`. The version check (inode, size, mtime, ctime)
  stays the same. That is one mechanism, as rule 11 wants.
- **Cost:** about 1 hour. **Fixable without the owner.**

## N5. An examine opens each video four times and reads its two ends twice. MEDIUM-LOW

- **Evidence:** in scan/examine.go, `statFile` opens and closes (line 98). `payloadIdentity` opens
  (189). `openSubtitlesHash` opens (173). `probe` opens again (150). The identity reads the
  payload's first and last MiB; the moviehash reads the file's first and last 64 KiB, the same
  regions, read twice.
- **Why it matters:** an initial scan of a 10k-file library makes 40k opens instead of 10k. On NFS
  each open is LOOKUP+OPEN+GETATTR round trips, and on HDD the ends are re-sought. The record also
  joins facts from four different opens, so a file replaced between them yields a stat of one file
  and a hash or probe of another. `namedfile` catches that later, so this is minor.
- **Fix:** open once, `Stat` that handle, and pass the one `*os.File` (as an `io.ReaderAt`) to both
  hashes and to the probe's `OpenedFilm`. Optionally read the ends once into a buffer that both
  hashes use.
- **Cost:** half a day. **Fixable without the owner.**

## N6. Two output pipelines for playback (whole-film prepare and on-request chunks) on both sides. MEDIUM (rule 11, needs the owner)

- **Evidence:** the node has `prepare` (HLS EVENT renditions, profiles remux/h264) and `chunks`
  (grid stores). Both live in one prepared directory with two manifest kinds, two eviction rules,
  two byte routes (byteserver.go:183-205) and two reconciliations. The core has `renditions` plus
  `prepare` jobs and `chunks` plus `make_chunks` jobs. Playback uses prepare only when a film is
  not on its ladder (core/playback/playback.go:254-259, "A film on its ladder needs no prepared
  copy (D260 §1)").
- **Why it matters:** two ways to do one job, each with its own eviction, keep and evict at hello,
  progress and failure paths. Every change to the cache (N1), to confinement or to scheduling is
  made twice.
- **Fix:** decide whether the remaining not-on-ladder cases (no index and not read yet? unsupported
  codecs?) can be cut on time (D269) and so retire prepare, or say why it stays.
- **Cost:** a design question, then several days. **Needs the owner** (design: D193 "prepare is
  the one path besides direct play", revised by D247/D260).

## N7. Results the core refuses are posted again every 30 s forever, a poison message. MEDIUM-LOW

- **Evidence:** `postUntilAcknowledged` (agent/answer.go:141-170) retries every non-200 answer
  with backoff capped at 30 s (answer.go:28-30), "never given up while the node runs" (doc.go,
  D234 §5). The core answers a malformed result with 400 (`ErrMalformedResult`,
  core/nodes/channel.go:130-131), and a Recorder that always fails always refuses. Each retry
  logs at Info, and a held result's bytes stay in memory until acknowledged (`HeldResults`).
- **Why it matters:** one bad result is a log line every 30 s and pinned memory (up to 64 MiB for
  an artwork result) until the node restarts, and it is easy to mistake for a live problem.
- **Fix:** treat 400 or 422 as permanent. Log once at Error, forget the result, and report it in
  the status as a crashed attempt.
- **Cost:** 2 hours. **Needs the owner** (it revises D234 §5's "never given up"), though it is
  small.

## N8. Three disk-concurrency mechanisms side by side, and the scheduler is not wired. MEDIUM (known, in progress)

- **Status:** known. This is work-scheduling.md phase 1 ("Next in phase 1: wire diskschedule into
  the node"). Recorded here so the audit says the transitional state carries all three.
- **Fix:** finish phase 1. When it lands, delete the SIGSTOP pausing and the reader-limit
  bookkeeping it replaces, and route byte-socket reads through it too.
- **Needs the owner** (phase decisions already in flight).

## N9. The core cannot see whether a node's FFmpeg reads through fdproxy. LOW-MEDIUM (diagnosability)

## N11. The watchdog scans all of /proc every 5 s per run, for a group of one process. LOW

## N12. Waiting work is reported twice each tick: in the status and as one POST per attempt. LOW

- **Evidence:** every tick, `postStatus` already lists each held attempt with its state

- **Cost:** 2-3 hours. **Fixable without the owner** if the reconcile already marks the attempts
  heard; check D234 §5 wording first.

## R1. Nothing the core serves is compressed (D129 decided gzip; not built) — MEDIUM

- Evidence: no `Content-Encoding` anywhere in `internal/` or `cmd/` (only `platform/bounded/gzip.go`,
  a reader). `internal/core/webclient/webclient.go:110-115` serves `assets/` with `http.ServeFileFS`
  raw. Measured on today's dist: `client-main-*.js` 979,652 B → 291,962 gzip -9 (3.4x);
  `transport-choice-*.js` 407,054 → 130,927; cast receiver `index-*.js` 608,528 → 187,604. API JSON
  is uncompressed too (`/titles` page 12.8 KB → 3.3 KB, per the research below).
  orpheum-connect's `internal/webclient/webclient.go:100-130` is a near copy, also uncompressed,
  though Cloudflare in front of `app.` compresses for it.
- Known: data-delivery-and-caching-2026-10-16.md §"Nothing is compressed" (line 74) and
  client-from-core-2026-10-17.md:84 (bundle 1.2 MB / 380 KB compressed then; it has grown).
  D129 decided "gzip on the client channel". The fix has not landed.
- Why: a direct-path load from a household's published name, an update after each release
  (immutable assets change), the Chromecast/TV receiver, and every API page over a relayed
  WebRTC or TURN path carry about 3x the bytes. Over a data channel, bytes are the cost (credit
  windows, cwnd), so this hits remote first loads hardest.
- Fix: precompress `assets/*` once at start-up (embed FS → gzip-9 in memory, keyed by name) and
  serve `.gz` bytes with `Content-Encoding: gzip` + `Vary: Accept-Encoding` when accepted; gzip-1
  middleware for JSON API responses only (not for byte paths: chunks, images; not for responses
  mixing secrets with attacker-reflected input — the API's JSON carries no CSRF token reflection,
  but check BREACH for any response that echoes request input next to a secret). stdlib
  `compress/gzip`, no dependency. Apply the same to connect's copy (or leave it to Cloudflare).
- Cost: S–M (half a day with tests: an asset is served gzipped when accepted, identity otherwise;
  a range request on a byte path is never encoded).
- **Fixable without the owner** (D129 already decides it). Revert-red test straightforward.

## R2. Watch Together: every state message rebroadcasts the full roster; while a group waits, clients drive the server's timer — MEDIUM

- Evidence: `internal/core/together/hub.go:533-546` `takeState` ends with `current.sendRoster()`
  unconditionally, whether or not anything in the roster changed (rtt, buffering, status).
  `sendRoster` (hub.go:583) broadcasts `roster()` (hub.go:562, rebuilt and sorted each time) to every
  device; each device's writer JSON-marshals its own copy (`api/together_socket.go:308`). The hub
  has no timer ("Starts no goroutine", doc.go invariant), so a sync point's wait ends only when a
  message arrives: `defer handled.endWait(now)` (hub.go:506), and the web follower sends a state on
  every drift tick while the group is `Waiting` (`web/packages/sdk/src/together-follow.ts:381-389`,
  "by which the server ends a wait whose time is up").
- Why: during every wait (each film put on, each host play after pause, each seek), D devices each
  send ~1 state/s, each producing D roster messages: D² rosters per second, mostly identical. 10
  devices ≈ 100 roster messages/s ≈ 150 KB/s of the core's upload, during exactly the moments the
  group's players are loading over that upload (D286 is about upload being scarce). Separately,
  making clients tick to advance server time is fragile: if the only ready player's tab is
  backgrounded (Chrome throttles timers to once a minute), the wait overruns its sync wait by up to
  a minute — the protocol makes clients do the server's job.
- Fix: (a) send the roster only when its view changed — compare the new `[]MemberView` with the
  last sent (or keep a dirty bit set by takeState/standing/attach/detach) — and marshal once per
  broadcast (pre-encode the Outbound into bytes in the hub or a shared cache) rather than once per
  device. (b) Give the hub one clock-driven deadline per waiting session (`clock.AfterFunc` at
  `waitUntil`, cancelled on change) so endWait does not depend on client traffic; then the 1 Hz
  client report while waiting can go.
- Cost: (a) S; (b) M (touches a stated invariant and the D247 §4 client behaviour).
- (a) **fixable without the owner** (internal; a test that an unchanged state sends no roster).
  (b) **needs the owner**: it reverses the "starts no goroutine" invariant and D247 §4's
  client-driven end of a wait.

## R3. Pairs of Go/TypeScript constants that must agree, with no test holding them — MEDIUM

- Evidence: `internal/core/rtcapi/rtcapi.go:25` `MaxMessageBytes = 64<<10` vs
  `web/packages/sdk/src/rtc-request.ts:11` `maxMessageBytes = 64*1024`; `rtcapi.go:35`
  `ClientConnections = 4` vs `rtc-transport.ts:19` `clientConnections = 4`; server `channelLimit = 16`
  (rtcapi.go:75) vs client `requestsPerConnection = 12` (rtc-transport.ts:88); `rtcapitest/client.go:280`
  `grantEvery = 16` vs `rtc-request.ts:139` `grantEvery = 16`; `rtcapi.go:60` gatherAfterReflexive
  300 ms vs `rtc-connect.ts:24` 300 ms. grep finds no Go test reading the TS values. The one pair that
  *is* held is WT's ping (`api/together_socket.go:36-44`, `TestTogether_TheSilenceLimitIsThreeOfTheClientsPings`),
  and WT's tuning is sent in the welcome (`Tuning`), which is the better pattern.
- Why: lowering `channelLimit` below 12, or `MaxMessageBytes` below the client's, silently refuses
  requests ("refused a request past a connection's limit") or breaks large responses on remote
  paths only — where it is hardest to diagnose.
- Fix: either (i) a coupling test per pair in the WT style (Go test greps the TS constant), or
  better (ii) the core states its limits on the negotiation channel's Verdict message
  (`rtcapi/verdict.go`), the client adopting them, as WT's welcome carries Tuning.
- Cost: (i) S; (ii) M.
- (i) **fixable without the owner**; (ii) a wire addition — the owner said protocol formats change
  freely in development, so arguably fixable without, but it is a protocol shape: ask.

## R4. The MAC'd stateless nonce is implemented twice, not recorded as a twin — MEDIUM (security drift)

- Evidence: `discovery/single/single.go:35-45, 240-300` (issue, `nonceMAC`, `nonceExpiry`,
  `isSigned` with a `spent` map swept on each spend) and orpheum-connect
  `internal/cores/nonces.go:30-105` (`issue`, `mac`, `spend`): the same design (8-byte expiry ‖ 16
  random ‖ 16-byte HMAC-SHA256, spent set until expiry), written separately. Neither the look-alike
  watch list nor the twins table (`docs/contributors/look-alike-watch-list.md`) names it, and
  `internal/twins` in connect does not hold it.
- Why: this is the replay protection of every signed core call (security audit S13). A fix in
  one (e.g. the next audit's) will not reach the other. D275 §1 says the paid service assembles the
  public `discovery/` building blocks — this is one that was not made one.
- Fix: move it into `discovery/proof` (e.g. `proof.Nonces{Issue, Spend}`), used by both; or, if the
  owner prefers copies, make connect's a byte-identical twin and add it to the twins test and table.
- Cost: S (either way).
- Promote-to-public: **needs the owner** (a new public API in `discovery/`, which crosses repos;
  the "copy, don't publish" rule). Twin + test + table row: **fixable without the owner**.

## R5. The paid service's database has no continuous or off-site backup in production — MEDIUM (ops; known as planned)

- Evidence: spec.md:676-679 and service.md P11 call for Litestream to another provider, a nightly
  snapshot and a restore drill (milestone M-S6). `orpheum-connect/deploy/production/compose.yaml`
  has no Litestream service; orpheum-ops `production/README.md:205-206` says "back it up with the

  Only `up.sh migrate` keeps a pre-migration copy. No uptime check or status page is deployed either

- Why: accounts, claimed cores, zone records and subscriptions for every beta household live in one

- Fix: build P11's backup slice before more households: Litestream sidecar + bucket at a second
  provider (write-only key), a restore drill script in orpheum-ops; an external uptime check of

- Cost: M (a day including the drill), plus a small monthly cost.
- **Needs the owner**: a new dependency (Litestream image), a provider account and credentials,
  which may not enter the sandbox (connect AGENTS.md rule 1).

## R6. Watch Together sessions and unused links never expire — LOW-MEDIUM (needs a decision)

- Evidence: sessions end only by `End` or process exit (`together/hub.go:367-377`; watch-together.md:85
  "A restart ends every session"). `AddLink` (`links.go:38-62`) has no bound on links per session
  and no lifetime; each unused link's locate hash is re-registered with the discovery on every
  change and under each session, renewed with a rolling 2-day expiry (`together/discovery.go:34-41`,
  `discovery/links.go`). `Open` (hub.go:217-249) gives a host their old session back forever.
- Why: a host who never presses End keeps every link they ever made admitting a stranger and
  findable through the discovery for the life of the process (weeks on the production NAS). The link set sent
  to the discovery grows without bound. No idle-expiry rule exists (the grant table has one; the hub
  does not).
- Fix: an idle rule — a session with no attached device for N hours ends (links withdrawn,
  discovery told); unused links expire after M days; a per-session cap on live links. Values as
  settings.
- Cost: S–M.
- **Needs the owner** (behaviour: how long a forgotten session/link should live).

## R7. orpheum-connect sweeps whole in-memory maps on every request — LOW (beta), MEDIUM at scale

- Evidence: `internal/clients/clients.go:189-199` `newBootstrap` iterates every live bootstrap token
  (up to `bootstrapsMost = 100000`, line 35) under the service mutex on every locate, to delete
  expired ones. `internal/cores/nonces.go:76-84` (`spend`) and `discovery/single/single.go:285-290`
  iterate the whole spent set on every signed call. Under a locate flood the per-request cost becomes
  O(n) under one lock — exactly when the bound is being tested.
- Fix: sweep at most once per interval (remember `lastSweep`), or keep an expiry-ordered queue
  (tokens all share one lifetime, so a FIFO slice of (token, expires) pops expired ones in O(1)
  amortised).
- Cost: S.
- **Fixable without the owner** (connect has no pre-commit hook: commit only inside `make check`).

## R8. A new core address waits up to 10 minutes to be published — LOW-MEDIUM

- Evidence: connect `internal/cores/probe.go:66-75` `probeIfDue`: `isDue := !wasProbed ||
  (now.Sub(last.at) >= probeEvery && !allReached(...))` with `probeEvery = 10*time.Minute` (line 16).
  A candidate that changed (an IPv6 prefix rotation, a new port mapping) is in `public` but not in
  `last.results`, so `resultsFor` gives it nothing and it is not published until the next probe is
  allowed; the doc comment above says candidates are probed "when they changed", which the code
  does not do inside the 10-minute window. The probe also runs synchronously inside the core's
  heartbeat request (`verified` → `probeIfDue` → `group.Wait()`), up to 8 HTTPS probes.
- Why: after a prefix change the direct IPv6 path disappears for up to 10 minutes, so clients fall
  back to WebRTC through the service (slower start, relay load). Probe memory is per-process, so a
  connectd restart re-probes every core on its next heartbeat inside the heartbeat calls.
- Fix: treat a set of candidates different from the last probed set as due (keep a hash of the
  probed set), still capped by a per-core minimum interval much shorter than 10 min (S10's rate
  concern is abuse, which a changed-set rule bounded at e.g. once a minute still answers); fix the
  comment either way.
- Cost: S.
- **Needs the owner** only for the rate (S10 / protocol §2.6 number); the comment fix and the
  changed-set detection behind the existing constant are fixable without.

## R9. `auth.Service` is a 61-method god object wired by setters; nil means off — LOW-MEDIUM

- Evidence: `internal/core/auth` is 7,556 lines over 21 files; `Service` has 61 exported methods
  spanning sessions, accounts, devices, device codes, pairing, hand-offs, invitations, locators,
  realm, roles/reach, reset, retention and setup (`grep '^func (service \*Service) [A-Z]'`). Its
  collaborators arrive after construction by setters — `OnLinksChanged`, `SealLinksWith`,
  `SetRealm`, `ClaimDeviceCodesFrom`, `OnDeviceActivated` (auth.go:154-181, called from
  `cmd/orpheum/discovery.go:176-181`, `serve.go:555`), each "nil does nothing"; the hub does the same
  (`SnapSeeksBy`, `OnLinksChanged`, written without the hub mutex, hub.go:478, discovery.go:94).
  The wiring resolves a cycle (discovery needs rtcapi; rtcapi's ICE servers need discovery,
  discovery.go:182) by late-bound closures over a variable assigned later (`discovered`).
- Why: a forgotten setter silently disables a feature (no link registration, no device-code
  claims) rather than failing; a setter called after serving starts is a data race the type does not
  prevent. Reviewing auth means loading the whole package.
- Fix: (a) cheap: make each setter's absence visible — log at start-up which optional parts are
  off, or a `Ready()` check `serve` calls; guard hub's setters with the mutex or take them in
  `NewHub`. (b) larger: split auth along its seams (sessions+principals; people/roles/reach;
  device enrolment: codes, pairing, hand-off; links/locators) into sibling packages sharing the
  store queries.
- Cost: (a) S; (b) L.
- (a) **fixable without the owner**. (b) **needs the owner** (package layout, cut-a §3).

## R10. `rtcapi.MaxConnections = 64` is a constant while its per-network share is a setting — LOW

- Fix: make it a setting beside the per-network one (or derive it from the upload budget, D293–D295),

- Cost: S.
- **Needs the owner** (hard-coded values watch: setting vs justified constant is the owner's

## R11. The WT client reconnects without jitter — LOW

- Evidence: `web/packages/sdk/src/together-connection.ts:68-71` `reconnectWaitMs(attempt) =
  min(first * 2^attempt, longest)`, no random term; contrast the core's jittered retries
  (`internal/core/discovery/discovery.go:577-590`, C7).
- Why: a core restart (every staging deploy) drops every device at the same instant; all reconnect
  in lockstep at 1 s, 2 s, 4 s... each reconnect rebuilding sockets and (remotely) WebRTC offers
  through the discovery at once. Small for a household; the same pattern in `rtc-transport.ts:434`
  (`replace` backoff) multiplies it across connections.
- Fix: full jitter (`random() * wait`) in both.
- Cost: XS.
- **Fixable without the owner**.

## R12. Same path, different file: connect's `internal/core/auth/{accounts,invitations,realm}.go` collide with the twin convention — LOW

- Evidence: the twins rule ("a twin is at the same path in each", look-alike-watch-list.md §Twins)
  makes `password.go`, `limiter.go` twins (4-line diffs: licence/module), but connect's
  `internal/core/auth/accounts.go`, `invitations.go`, `realm.go`, `doc.go` sit at the same paths as
  Orpheum's and differ by 218-568 diff lines: different code under twin-looking names.
- Why: a reader (or agent) applying "change once, copy everywhere" by path will copy the wrong
  thing; the convention's signal (same path ⇒ same file) is broken.
- Fix: move connect's own auth files to a non-colliding package (`internal/accounts`, say) or rename
  the files; keep `internal/core/auth/` for twins only.
- Cost: S (connect only).
- **Fixable without the owner** (internal rename in connect), though it is the owner's convention:
  mention it.

## R13. A claimed core's heartbeat is two signed calls, plus a third poll every 10 s for signalling — LOW

- Evidence: `internal/core/discovery/discovery.go:500-545`: each due heartbeat first `askStatus`
  (a signed call) then `PUT addresses` (a second); `signal.go:25` `signalCheckEvery = 10 s` loop
  checks claim state in-process (cheap, no network). Cadences are split between settings
  (`DiscoveryAddressCheckEverySeconds` etc.) and constants (`heartbeatEvery = 5 min`,
  `signalCheckEvery`, `pingEvery = 27.5 s`).

- Fix: return the standing in the addresses response (the response already carries Published,
  Probe, ReachableFrom); drop the separate status call for claimed cores.
- Cost: S across both repos and a protocol tweak.
- **Needs the owner** (protocol shape, both repos).

## W1. The whole app ships as one 980 KB chunk: no route-level code splitting, hls.js loaded at startup
- **Severity:** medium (high on TVs)
- **Evidence:** `dist/assets/client-main-DG0pftTc.js` 979,652 B (291,962 B gzip) plus a shared
  `transport-choice-*.js` 407,054 B (130,927 B gzip, react-dom and qrcode). The only dynamic imports
  are `index-*.js` → `client-main`/`loader-main` (`src/main.tsx`). hls.js (its `MANIFEST_PARSED`
  etc., about 400 KB minified) sits inside `client-main`: `client-main.tsx:7` imports
  `canFollowAGroup` from `@orpheum/player`, whose `hls.ts:15` imports the `Hls` value, so the player
  stack loads before the home page draws. The device lab (`lab*.ts*`, 133 KB of source of the app's
  1.15 MB) and admin screens (system, server-settings, people, jobs, files) are all in the same chunk.
- **Why it matters:** the closed beta targets Fire TV / Silk / TCL TV browsers, where parse and
  compile of ~1.4 MB of JS dominates first paint; over the discovery's WebRTC path every byte also
  rides the data channel and the loader hashes it (D308).
- **Fix:** `React.lazy` + `Suspense` per screen group in `app.tsx`'s `Screen` (player screens,
  admin screens, `/lab`, Watch Together); move `canFollowAGroup`'s capability check behind a small
  module that does not import `hls.js` (or lazy-import it where first needed). Dynamic chunks
  already work under the loader (index → client-main is one), but check `client-files.ts`/the signed
  manifest list every emitted chunk. Measure with the build's `modules-client.json`.
- **Cost:** 0.5–1 day. **Fixable without the owner** (no behaviour change; add a test that the home
  route's chunk graph excludes `hls.js` and `lab-*`, e.g. from `chunk-modules`).

## W2. Background polls keep running in hidden tabs
- **Severity:** medium
- **Evidence:** `pollUntilStopped` (`apps/web/src/polling.ts`) never consults
  `document.visibilityState`; grep finds visibility handling only in page-interest, signed-out-watch,
  play-state and lab code. `useFileWaits` (`file-waits.ts:40`) also polls on `setInterval` while
  hidden. A tab left on Home polls `/continue-watching`-style rows, newest films and newest series
  (three resources, `home.tsx:45`, `continue-watching.tsx:192`) every 30 s forever; a System page
  or a films list with two pages in view does the same.
- **Why it matters:** forgotten tabs and TVs left on a page are the commonest client; each poll is a
  full read and serialisation on the core and, through a discovery, a WebRTC data channel per
  request. Scales linearly with idle clients for no one's benefit.
- **Fix:** in `pollUntilStopped` (the one way to poll), pause while `visibilityState === "hidden"`
  and ask at once on becoming visible (as `checkSessionWhileShown` already does). Inject the page
  like `CheckedPage` for tests. Route `useFileWaits` through the same poller.
- **Cost:** 2–4 h. **Fixable without the owner** — but D237 §1 says "asks again ... up to 30 s"
  without mentioning visibility; arguably a behaviour change. It shows nothing different to a
  person, so I rate it fixable; mention it to the owner.

## W3. Every polled resource is fetched twice on a cold start (the poller's identity changes)
- **Severity:** low–medium
- **Evidence:** `app.tsx:162-175` `useServersPoller` returns `backgroundChangesPoller` until
  `/client-settings` answers, then a new `backingOffPoller(...)` object. `use-resource.ts:86`
  (`[key, attempt, poller]`) and `use-pages.ts:246` (`[load, poller, shown, show]`) restart their
  effect on that change, and the restart's `read()` asks again at once. `SignedIn` renders the
  screen before client settings arrive, so Home's three rows, a films list's pages, a title, etc.
  each GET twice within the first second.
- **Why it matters:** doubles the startup request burst exactly when the page is slowest (TV, relay
  path, cold core).
- **Fix:** make the poller a stable object that reads its waits through a ref/getter (the waits
  apply from the next scheduled ask), or hold the screen until client settings are read (they are
  tiny). A test: count requests in `test-dom`'s stand-in server across a client-settings answer.
- **Cost:** 1–2 h. **Fixable without the owner.**

## W4. The "one way to poll" has four siblings
- **Severity:** low–medium (rule 11)
- **Evidence:** the README and `polling.ts` declare `pollUntilStopped` the one way to poll, but
  `file-waits.ts:41` (`setInterval` every interest seconds, failures swallowed, no abort, no
  timeout), `signed-out-watch.ts:63` (`setInterval` 60 s), `moving-down.ts:101` (`setInterval` 3 s),
  `page-interest.ts:45` (a heartbeat, legitimately different) and the SDK's `ready.ts:readyAnswer`
  (425 + Retry-After, up to 600 attempts) and `reopen.ts:askUntilAnswered` (fixed waits) each run
  their own loop. A title page waiting on a prepare runs three loops at once against the core: the
  playlist's 425 loop every ~1 s, `/files/{id}/waits` every 15 s and `/interest/{id}` every 15 s.
- **Why it matters:** each loop has its own (or no) answer-timeout, visibility rule and backoff, so
  fixes like the 2026-10-24 "a request that never answers stops a page's refresh for good" (now in
  `pollUntilStopped`) do not reach them: `useFileWaits` has exactly that defect still (no timeout;
  `setInterval` keeps firing so it does not stop, but overlapping asks can pile up on a stalled
  transport).
- **Fix:** move `useFileWaits` onto `useResource` with a fixed-interval `Poller`; give `Poller` a
  fixed-interval variant for `moving-down`/session check. Leave `ready.ts` (protocol-driven).
  Longer term (owner): one "what is this page waiting on" read, or a push channel (D237 §3).
- **Cost:** 3–5 h for the mechanical part. **Fixable without the owner**; the merge of the three
  wait loops into one endpoint/push **needs the owner** (protocol).

## W5. Change detection by `JSON.stringify` of whole answers, with no conditional requests
- **Severity:** low–medium
- **Evidence:** `use-resource.ts:51` serialises every answer to compare with the last; no `ETag`
  / `If-None-Match` anywhere in sdk or app (grep). Every unchanged poll costs the core a full query
  + JSON encode, the wire a full body, and the client a parse + stringify.
- **Why it matters:** with W6's unpaged lists this is O(list) work on both ends every 2–30 s per
  client, and TV CPUs are slow.
- **Fix:** core answers polled GETs with a weak ETag of the body (or of a per-resource change
  counter, principles §11) and 304s; the SDK passes `If-None-Match`; `useResource` treats 304 as
  "unchanged". Server-side is mechanical with a middleware; the WebRTC transport already carries
  headers and 304 (`rtc-request.ts:44` lists 304 as bodiless).
- **Cost:** 1 day. **Fixable without the owner** if done as an HTTP-level middleware with no API
  shape change; flag it.

## W6. *Needs a match* reads two unpaged lists of every waiting item, and polls them
- **Severity:** medium
- **Evidence:** `identify.tsx:159-172` — two `GET /items?identificationState=…` with no limit,
  polled by `useBackgroundChangesPoller()`. The handler
  (`internal/core/api/identification.go:182-205`) returns every item (`Chooser.Items`) with no page.

- **Why it matters:** the one admin page most used right after a first scan is the one with no

- **Fix:** page `/items` by cursor and read it with `usePages` as browse/files do (D306 §7

- **Cost:** 0.5–1 day (query, handler, generated client, screen, tests). **Fixable without the

## W7. Hand-rolled stale-while-revalidate in three screens instead of in `useResource`; `/me` read by four screens
- **Severity:** low (rule 11)
- **Evidence:** `remembered.ts` (`Remembered` + `useRemembered`) is bolted onto `app.tsx:105`,

## W9. A device's sound offset is written on every click, unordered, and a failure is swallowed
- **Severity:** low–medium (silent data loss of a user choice)
- **Evidence:** `sound-delay.tsx:60` `void setMyDeviceSoundOffset(api, deviceId, next).catch(() =>

- **Cost:** 1–2 h. **Fixable without the owner.** (Similar silent swallows of server writes:
  `page-interest.ts:29,35`, `interest.ts:56,66` — documented as harmless — and
  `app.tsx:119`/`together-viewer.tsx:92` `haveBackMySessions`, which hides why a session did not
  follow a person; at least `reportFailure` those.)

## W10. `play.tsx` drives `useResource` as a command channel through mutable refs

## G1. A test helper opens a new SQLite pool for every query, re-parsing the whole schema each time: 40% of identify's CPU — HIGH

- **Evidence.** `internal/store/storetest/storetest.go:141-200`: `ExecRaw` and `QueryRaw` each
  call `sql.Open` and `Close` on every call. A new modernc connection parses the full schema the
  first time it is used: 161 schema rows (72 tables, 14 triggers, 4 views, 0058's triggers among
  them). Measured (`conncost/`): **3.4 ms of CPU for each new connection and its first query,
  against 40 µs for a query on a warm connection**, about 85 times as much. Profile of
  `go test ./internal/core/identify/` run alone (22 s wall, 50 s CPU): `storetest.QueryRaw`
  takes **39.7%** of the samples, and schema initialisation (`_sqlite3InitCallback`) 36%.
  `sqlite3Prepare` → `_yy_reduce` is 66% overall. 13% of the CPU goes to `Mutex.lockSlow`
  inside modernc's global `libc.Xmalloc`, so parallel tests also contend for its allocator lock.
  `dumpIdentified` (random_test.go:206) runs one `QueryRaw` per identified table, twice per
  step, for two libraries, five steps, twelve subtests.
- **Why it matters.** identify is the critical path of an uncached `go test ./...`. In the full
  suite it took 94–99 s (runs at 19:03 and 19:06), so the whole Go step took 109–115 s. That is
  more than make check's 90 s budget by itself, whenever store, settings, library or identify
  change. The 2026-10-08 test audit measured identify at **6.4 s** and the whole uncached suite at
  24.7 s, so this has grown about 4× in 17 days without anyone deciding it should.
  186 call sites use `ExecRaw` or `QueryRaw`.
- **Fix.** Have `QueryRaw` and `ExecRaw` keep one query-only pool (and one writable pool) per
  path for each test, closed in `tb.Cleanup`, through a `sync.Map` keyed by `tb` and path.
  Alternatively, `dumpIdentified` could read every table in one `QueryRaw` connection.
  Expected result: identify roughly 40% less CPU, and the uncached Go step's critical path cut
  by a similar share. Add a test-weight.md entry ("a helper that reconnects per call").
- **Cost.** About 1 hour, including a test that the helper reuses its pool.
- **Fixable without the owner.** `storetest` is not a gate path.

## G2. The store's test package reads every Go file in the repository, so its 109 tests (10–20 s) never come from the test cache — HIGH

- **Evidence.** `internal/store/sqlcgen_test.go:105` (`callerSources`, for
  `TestGeneratedQueries_EachHasACaller`) and `internal/store/statistics_test.go:80`
  (`TestStatistics_NothingElseAnalyzes`) each `filepath.WalkDir("../..")`. That reads every
  directory in the repository and every `.go` file. Go's test cache records each file opened and
  each directory listed, so any edit to any Go file, and any file added or removed anywhere,
  invalidates the whole `internal/store` package. In all **20 of the last 20** recorded make
  check Go runs, `internal/store` ran for real (5–20 s, median about 12 s), and
  `internal/archtest` in 18 of the 20 (about 10 s). Together they are the 15–18 s floor of
  every "cached" `go-test`. A run of `GODEBUG=gocachetest=1` showed the input ID changing
  between two back-to-back runs while other agents were editing the tree, and caching once the
  tree was still.
- **Second effect: an impact blind spot.** `scripts/revert_red_dependents.py:26` names only
  `./internal/archtest` in `GO_SOURCE_READERS`. Removing a query's last caller in another package
  therefore does not reach `TestGeneratedQueries_EachHasACaller` in `make spot` or in revert-red's
  dependents. Only the full `go test` finds it. test-weight.md "Caches bring their own risk"
  says such a reader must be listed.
- **Fix.** Move the two source-reading tests out of `internal/store`, into `internal/archtest`
  (which reads the sources anyway and is already uncached) or into a new test-only package. Then
  the store's 107 other tests cache. Saves about 12 s of CPU on almost every make check, and
  removes contention for the other steps.
- **Cost.** About 1 hour. check_test_weakening accepts a move with a `Test-Renamed:` trailer.
- **Moving them to archtest needs the owner** (a gate path). **Fixable without the owner** if
  they go to a new non-gate package, plus its architecture-map row. Adding the package to
  `GO_SOURCE_READERS` is a `scripts/` change and needs the owner.

## G3. archtest runs `go list` and re-reads every source file in each of its tests — MEDIUM (needs the owner)

- **Evidence.** `internal/archtest/graph_test.go:42-87`: `loadModulePackages` and
  `loadCoreImportGraph` run `go list -json` (and `-deps`) as a subprocess. They are called 27
  times across the package (`grep -c 'loadModulePackages(t)\|loadCoreImportGraph(t)\|readSourceFiles(t'`),
  with no `sync.Once`. One `go list -json` of the module takes 1.5 s wall and 1.4 s CPU here.

- **Fix.** Load once per test binary with `sync.OnceValues` (packages, graph, parsed files).
  Expect archtest at about 3–5 s.
- **Cost.** 1–2 hours.
- **Needs the owner** (`internal/archtest/` is a gate).

## G4. The job runners poll cache.db every second each, and every poll takes the writer twice, even when the core is idle — MEDIUM

- **Evidence.** `cmd/orpheum/metadata.go:560-566` gives every runner a `time.NewTicker(time.Second)`.
  There are 11 kinds (`runners()`, metadata.go:264), each with concurrency 1. Each tick runs
  `RunDue` (`internal/platform/jobqueue/runner.go:75`). That calls `failOverdueAssigned` →
  `JobStorage.TakeOverdueAssigned` → `take` → `cache.Write` (store/jobs.go:280-306), and then
  `claim` → `JobStorage.Claim` → `cache.Write` (store/jobs.go:200-228). Each of those is an
  IMMEDIATE transaction through the writer gate. At idle that is **about 22 write transactions a
  second on cache.db**, plus `demoteUnwanted` (5 s), `raiseInterestEvery` (5 s),
  `uploadKeptEvery` (5 s) and the 1 s silence watch. A write transaction that changes nothing
  writes no WAL frame, so it costs no fsync. It still costs a BEGIN IMMEDIATE, two prepared
  statements and the gate. When slow-write reporting is on, it also costs a `runtime.Callers`
  stack walk (`callerOutsideTheStore`, open.go:124). Each one also contends with a person's
  writes for the cache writer, such as the chunk records a playing film makes.
- **Why it matters.** Waking the CPU and doing the work all the time on a NAS (an N305, idle most
  of the day). It also makes the queue's own tick the bound on latency rather than the event.
  The queue already knows when the next job is runnable, since it has `runnable_at` and wakes
  on enqueue.
- **Fix.** Option 1: read first. Use a read transaction for "is anything due or overdue" and
  take the writer only when it finds something, the `WriteUnlessUnchanged` pattern the store
  already has (D303 DL9). Option 2: sleep until the earliest `runnable_at` or `deadline` of the
  kind (one indexed MIN query), woken early by `runner.wake`. Option 1 is mechanical. Option 2
  changes how the scheduler behaves: check it against the queue redesign (D329,
  data-timeliness.md) first.
- **Cost.** Option 1: half a day with a test that an idle tick takes no writer (querytally
  already counts writes). Option 2: a day.
- **Option 1 is fixable without the owner. Option 2 needs the owner**, given the queue redesign
  in progress. **New:** not in database-access-audit-2026-10-15.

## G5. The reader pool keeps two idle connections out of up to NumCPU, so bursts close and reopen connections, each re-parsing the schema — MEDIUM (overlaps the store slice)

- **Evidence.** `internal/store/open.go:155` sets `readers.SetMaxOpenConns(max(MinimumReaders, NumCPU))`.
  It never sets `SetMaxIdleConns`, so database/sql's default of 2 applies. The one place that
  raises it is `statistics.go:68-71`, and only when the committed statistics differ from those
  stored (`slices.Equal` → `return nil` at :61 skips it on an ordinary start). Under concurrent
  reads (a browse page, several players, the scan's pass), each connection past the second is
  closed when it is returned. The next burst opens a new one, which pays the DSN's pragmas plus
  the full schema parse: 3.4 ms of CPU against 40 µs (G1's measurement), under modernc's global
  allocator lock. cache.db opens the same way.
- **Fix.** `readers.SetMaxIdleConns(maxOpen)` (and the same for the cache's pools) in `open`,
  with a test that `Stats().MaxIdleClosed` stays 0 after N concurrent reads.
- **Cost.** 30 minutes.
- **Fixable without the owner.** **New.** Raise it with the store/DB slice so it is not reported
  twice.
