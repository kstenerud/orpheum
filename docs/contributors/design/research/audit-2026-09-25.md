# Audit after M2 (2026-09-25)

The third audit between milestones, as the owner asked after M1 (*"between each milestone, we
should do another audit of the architecture, procedures, rules etc"*). It follows
[audit-2026-09-24.md](audit-2026-09-24.md)'s form. Findings that are only document fixes were
made in the same change and are listed as done; everything else is a proposal for the owner.

## 0. The verdict

M2 is built and its acceptance list holds, as tests. It also grew beyond the plan's row, by the
owner's decisions: artwork end to end (D212), text hygiene (D211), provider etiquette and the
rolling refresh (D213), local artwork (D215), and the first web client. Three things are
unfinished: the reference-scale database generator (still open from the M1 audit), a web page to
set the TMDB key, and a way for an admin to see a node's roots. Two decisions are needed before
M3's first line: how the media cookie reaches M3's byte paths (§7.1), and where the embedded web
client is served from (§7.2).

## 2. What went wrong in the work, and what it teaches

### 2.1 Two decided rules were not built, and a comment pointed at code that was never written

D162's suffix evidence and D163's `extra` filing were both decided, both in the plan, and both
missing until a fixture tree exercised them. The unit tests covered the cases someone thought
of; the acceptance tree covered the ones people have. **Lesson:** build the milestone's
acceptance fixture early, not last. **Proposal 1:** a check that a comment naming an identifier
in this package's style — `(extraBySuffix)`, `see fooBar` — names one that exists. It is
imprecise and could be noisy; the owner may prefer to leave it to review.

### 2.2 An external service's failures were decided in code, not with the owner

The first artwork job gave up on a 404 for good. The owner saw that a replaced image or a CDN
fault would leave a blank forever, asked for research, and D213 followed — including TMDB's
six-month limit on keeping its data, which D170 had not known. **Lesson:** every call to another
host has failure classes (404, 429, 5xx, a timeout, a host that keeps failing), and each needs a
stated policy before it is built. **Proposal 2:** standards/go.md gains a short section listing
those classes and pointing at D213 as the pattern.

### 2.3 Options offered for a question a decision had already answered

Asked how an `<img>` authenticates, I offered three options; D154 had settled it — a media
cookie scoped to the byte paths — two milestones earlier. The owner chose the same answer, so
nothing was lost, but a decision re-asked is a decision that can drift. **Lesson:** search the
decisions before offering design options. (Recorded as agent guidance; no gate proposed.)

## 4. Mechanisms still missing

### 4.1 The reference-scale database generator (open since the M1 audit, §3.2)

migrations.md's 10-second step budget is still checked by review. Migrations 0007–0011 each
rebuild or add an index over `file` or `item_text`; none was measured at the reference scale.
**Proposal 3:** build the generator before M3 adds its first migration, now that the tables it
fills — titles, files, streams, artwork, series — exist.

### 4.2 No page to set the TMDB key

The M1 audit named the settings and secrets pages as the first of M2's web work; the web client
built everything else first. An owner must set the TMDB key with `curl` (`PUT /secrets/{name}`).
**Proposal 4:** a small admin page for secrets and settings, using the endpoints M1 built, before
M3.

### 4.3 No way to see a node's roots

Creating a library needs a node's name and one of its configured roots, and nothing lists them;
the form takes them typed, and the server refuses a root the node did not configure.
**Proposal 5:** `GET /nodes` (admin): each node, whether it is connected, and the roots its last
hello named — the facts `nodes.Service.Roots` already holds. Recorded as plan-deviations P24.

### 4.4 Smaller gaps, recorded

- A match's own re-derivation does not see images beside the media, so in a library that reads
  NFO files it can fetch one TMDB image a local one covers; the next pass corrects the choice.
  One download per such title, once.
- The artwork cache's running total is kept from one listing at start and every write since; a
  file someone deletes by hand is counted until the next start. Harmless: the ceiling errs
  towards evicting early.

## 7. What M3 needs decided before its first line

### 7.1 The media cookie and M3's byte paths

D154 scopes the media cookie to the byte paths. M2's is `Path=/api/v1/art/`; M3 adds
`/api/v1/media/...` and `/api/v1/media/sub/...`, and a cookie has one path. The options:

1. **One prefix for every byte path** — `/api/v1/bytes/art/…`, `/api/v1/bytes/media/…` — and one
   cookie scoped to it. The browser then sends the cookie nowhere else. An API change to `/art`
   now, while nothing but our own client uses it.
2. **One cookie per byte path**, set together at sign-in and cleared together.
3. **`Path=/api/v1/`**, with the server accepting the cookie on byte routes only. The browser
   sends it with every API call, which the API ignores; D154's CSRF argument holds, because the
   API never reads it, but the scoping D154 asked for is gone.

**Recommendation:** 1 — the narrowest cookie, one to set and clear, and `/art` moves before
anyone else depends on it.

### 7.2 Serving the web client from the binary

cut-a §2 has the core serve the embedded web client; today only Vite's dev server does. M3's
"usable on a phone" acceptance, and any test from outside the dev loop, need the built client
served by the core. **Proposal 9:** embed `web/apps/web/dist` with `go:embed` behind the release
build, served at `/`, with the SPA's routes falling back to `index.html`. It touches the Makefile
(a gate): the release build must build the web client first.
