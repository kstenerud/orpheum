# Before Phase 4: the readiness audit (2026-09-30)

The owner asked, at the point of starting Phase 4 of the [jobs rebuild](../plans/jobs-rebuild.md):
is the design sound, is the architecture clean for what comes next, and are we following our
principles or set up to follow them? Three read-only reviews ran in parallel over everything since
[M3's closing audit](audit-2026-09-29.md) (earlier commits): the design against what was built
(D231, D233, the plan, the scenarios), the architecture against Phase 4's needs, and the whole
[checklist](../../audit-checklist.md) against the diff. The coordinator took the gates and the
process. Findings were checked at their use sites before they were written here.

## 0. The verdict

**Not ready.** Phases 1–3 are sound: the queue, destinations, provider services, derived work and
retire are built as D231 says, apart from the differences listed in §1, and every test the plans
call built exists. Phase 4 is not ready on two counts, and both come before its code:

1. **Its design has holes exactly where it is hard** (§2). Adopting a job at hello after a restart
   needs a job that is running on a node with no goroutine waiting for it, a state the queue does
   not have; the node's outbox, the attempt token's life, the rendition inventory, the node as its
   own service and "wanted until" are all unspecified. These are design, so they are the owner's.
2. **The code Phase 4 changes exists five times** (§3). The send-and-wait-and-cancel loop to the
   node is hand-written in prepare, loudness, subtitle extraction, fetched-subtitle conversion and
   artwork, each with its own real-clock timer and its own way out that leaves the node working.
   Tokens, the outbox and late results would each be written five times.

The recommended order is §6: decide §2's questions, build one seam (§3), then Phase 4 in four
steps.

## 2. Phase 4's design: what is not decided

Each of these is a question of what the system does, not how, so it goes to the owner (§5).

1. **A job running on a node with nobody waiting for it.** Today a job exists only while a
   goroutine blocks in `Runner.handle` (`jobqueue/runner.go:182-259`); the storage has claim,
   record and requeue-at-start (`storage.go:29-41`). Reconciliation at hello and surviving a core
   restart both need a dispatched state that a result (by attempt) or the hello completes. D233
   implies it; neither it nor the plan says it.
2. **Awaiting hello.** After a restart, how long the core waits for a node to report a job before
   it parks or requeues it, and whether that is a setting.
3. **The outbox.** The node's reports live in memory and are numbered from the core's sequence
   (`node/agent/report.go:15-23`). A durable outbox is a journal on the node's disk: its size
   bound (artwork answers are large), retention, and what happens when that disk is full.
4. **The attempt token.** Where it is minted and stored, what a cache.db discard does to it, and
   whether the node keys its jobs by (job, token) so a retry cannot overwrite a cancel (S27).
5. **The rendition inventory.** Rebuilding the index from the node needs a manifest per rendition
   (profile, run id, source identity, gains) that nothing writes today.
6. **A handler that fails after its command reached the node.** The plan says "tell the node to
   stop, *or* reconciliation finds it". One must be chosen; the architecture review recommends
   both: the seam cancels on every way out, and reconciliation catches what a lost cancel leaves.
7. **The node as its own service** (D233 §2). The core starts and kills the node as its child
   today (`core/nodes/supervisor.go:57-66`), and a dropped session cancels all node work
   (`node/agent/agent.go:139-147`). The service unit, installation, the dev loop, D43 and D207's
   amendments, and who restarts a node that hangs while staying connected are undesigned. Once
   core and node can run different builds, the protocol number is needed, so it ships with this.
8. **"Wanted until"** (D233 §7): demoted or dropped when it passes, after how long, and whether
   the length is a setting.
9. **What a person sees** (D231 §12) for Phase 4's new waits: a node on an incompatible version,
   "awaiting hello" after a restart, waiting for a slot on a node, a node crash loop (S86's node
   side, which no phase owns).

**Phase 4 is too big for one step.** The design review's split, which the rest of this audit
assumes:

- **4a — the node stands alone:** the node as its own service, node work tied to the agent not
  the session, the protocol number, unknown commands refused (S89).
- **4b — results known by what they are:** tokens, the core's run id per attempt, the durable
  outbox, answers accepted only from the node the job was sent to, the "changed" refusal (S74),
  G13 (S81, S83–S85).
- **4c — nothing lost across a restart:** the dispatched state, awaiting hello, reconciliation, the
  rendition index rebuilt from the node, ended commands never sent, G8, S72 (S26, S27, S82, S91).
- **4d — slots and priority:** per-node slots in claiming (replacing `runnerPool`), a play pausing
  background reads, "wanted until" (S87, S88).

S90 moves to a small step of its own with its schema change; S79/S80 move to Phase 5.

## 3. The architecture: one seam before Phase 4

The core↔node boundary is clean: the node's imports stay within node, nodeproto and platform, and
provider health is the queue's own destination state, not a second record. On top of it:

1. **Five copies of the round trip** (blocker). Send, wait on an `AnswerRouter`, a real-clock
   silence timer, then `Unanswered` or a cancel: `playback/prepare.go:184-220`,
   `playback/loudness.go:284-323`, `playback/subtitles.go:293-329`, `playback/fetch.go:234-260`,
   `artwork/service.go:279-301`. The answer side is split the same way: four sinks and setters
   (`nodes/service.go:43-116`), four endpoints (`nodes/channel.go:128-172`), four `/node/v1/*`
   paths, and a `JobID` in eight payloads while the `Command` envelope has none. The architecture
   map's F3 says four copies; there are five. **Fix:** the job id and (later) the attempt in the
   envelope, one result endpoint and router, and one `nodes` seam that sends, waits on a
   clock-driven silence limit and cancels on every way out. Handlers keep "build the command"
   and "take the result".
2. **Ways out that leave the node working** (fixed by the seam, not five patches). A failure after
   the send (`prepare.go:193,197`, the known suspect of the hang, and `:242-243`); every silence
   timeout, which returns `Unanswered` and retries while the node may still work, so it gets a
   duplicate; the context ending for anything but a cancel, in all five; `fetch.go:258-259`, which
   never cancels when the person's request ends.
3. **Real timers in core job paths.** `clock.Clock` has only `Now` and `Sleep`
   (`platform/clock/clock.go:13-18`). Real timers at the five sites above, `nodes/channel.go:45`,
   `opensubtitles/requests.go:219` and the node's `agent/answer.go:63`; `api/prepare_test.go:92`
   really sleeps. Phase 4's watchdogs and reconciliation cannot be tested deterministically this
   way. **Fix:** `NewTimer`/`After` on `Clock` and `clocktest.Fake`, used by the seam.
4. **`nodes/service.go` does four jobs** (542 lines): enrolment, the connection registry, the
   in-memory command queue (whose `Enqueue`, `:467`, silently drops a cancel to a node that is not
   connected) and facts. Split the connection and command queue, the outbox's counterpart, from
   enrolment and facts. The node role lives in `cmd/orpheum/node.go`; a node that is its own
   service suggests its own command, decided with §2.7.
5. **Two routes for converting a fetched subtitle:** a job, and a synchronous path with negative
   ids (`fetch.go:233`). Phase 4 already removes the negative ids; route it through the seam.
6. **Later:** `cmd/orpheum/metadata.go` (420 lines) holds every runner, sweep and pool and some
   identify logic (`queueOwedFetches`, `:390-418`), under a name that says "metadata"; first matches
   are queued twice after a pass (harmless: merged); `playback` holds four node job handlers, its
   split already Phase 6's.

## 5. The gates and the process

1. **A failure's log is overwritten by the next run.** `scripts/quiet_gate.py` keeps one log per
   target. The hang recurred during the last agent's `make check` and printed its new diagnostic
   into a log that the passing re-run then replaced, so the evidence was lost. **Fix**
   (a gate change): keep the last failed run's log beside the latest, and name it in the failure
   summary.
2. **A doc.go may cite any test name and nothing checks it**, which is how §4's folded-away
   `TestMigrate_Step0027…` survived. `check-claims` resolves only `TestArch_` names. **Proposal:**
   resolve every `Test…` name cited in a `doc.go` or README.
3. **A test's wait can be unbounded and nothing says so.** Proposal, after the bounded receive
   exists: a lint that refuses a bare receive from a channel in a test outside that helper.
4. **Gate redesigns this session:** revert-red now passes removed dead code as UNREACHABLE, and a
   `Refactor-Only:` claim rides on any commit of the branch (1498557, the owner's rule of
   2026-09-30: a gate that blocks a valid edit is redesigned, never worked around, A16).
5. **Cost:** a full `make check` in the pre-commit hook takes minutes, and a hang takes ten; with
   the bounded waits a hang now fails in one. The owner asked for fewer tokens: quiet gates and
   targeted re-runs are in, and this audit ran as three reviews rather than five.

## 7. What the owner is asked to decide

**Phase 4's design** (§2), framed as what the system does:

- D1. After a core restart, how long may a node take to say what it is still doing before its jobs
  are given up and queued again, and is that a setting?
- D2. When the node's disk fills, may the node drop reports it has not delivered (the core then
  learns by reconciliation), or must it stop taking work?
- D3. A handler that fails after its command reached the node: the core both tells the node to
  stop and relies on reconciliation for a lost message (recommended), or only one?
- D4. The node as its own service: installed and restarted by the system's service manager on
  both machines, with the core no longer starting it (recommended, as D233 §2 says), and does a
  node that stays connected but stops answering get restarted by the core or only reported?
- D5. "Wanted until": when a person stops waiting for a prepare, is it demoted to background
  priority or cancelled, and after how long?
- D6. The four-step split of Phase 4 (4a–4d), and a preparation step 4.0 first.

**Smaller:**

- D7. Is the offline banner's dismissal a preference? It is stored in the `preference` table as
  `offline_reminder_dismissed_at`; the alternative is a small per-user state table.
- D8. Should something newly offline bring a dismissed banner back at once (recommended), rather
  than waiting out the interval?
- D9. Contract renames: `library_check_every_hours` is only a new library's starting interval
  (→ `new_library_scan_every_hours`); the API's `removedFileCount` counts tombstoned files
  (→ `tombstonedFileCount`).
- D10. Phase 2 read D231 §12 as "a person's own call to a host that sent a 429 waits too, with a
  countdown"; confirm.
- D11. The gate changes of §5: keep the failed log; resolve every cited test name; later, a lint
  for unbounded waits in tests.
