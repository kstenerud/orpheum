# Audit after M3 (2026-09-27)

The fourth audit between milestones, following [audit-2026-09-25.md](audit-2026-09-25.md)'s
form and, for the first time, the whole [audit checklist](../../audit-checklist.md). The naming
pass (item 7) ran over the whole tree, as the 2026-09-26 pass's lists were lost; it and the
checks of duplicates, documents and derived data ran as seven parallel read-only reviews, each
finding checked against its use sites. Findings that are fixes needing no one's decision are
listed with their commits; the rest are proposals, gathered in §10.

## 0. The verdict

M3's features are built and in use on the owner's phone, and four of its five acceptance items
are either proved by a test or waiting on a device (§1). It is not done. **Three things decided
for M3 were not built**: the node's eviction of prepared renditions (D217 §5, whose status line
said built), hardware encoders (cut-a §6), and the Playwright test of playback timing (D217 §4).
Two queries that read whole tables reached `main` because the gate that finds them ran only in
CI (fixed: An earlier commit). The gates themselves had four blind spots, all found this
milestone and fixed (§5). M4 needs about nine things decided before its first line (§8), none of
which the plan settles.

## 3. What is unfinished (items 3, 4)

**Decided for M3 and not built:**

1. **Eviction of prepared renditions (D217 §5).** No budget, no grace, no 95% disk limit, no
   refusal when full, and `/doctor` does not show a node's use. The prepared directory only
   grows. D217's status line said "built in M3". *To build now.*
2. **Hardware encoders (cut-a §6: `h264_qsv`, else `h264_nvenc`, else `libx264`).** Every encode
   is `libx264`, and the hello's capabilities are empty. devnas (J3455) has Quick Sync. *To build
   now, verified on devnas by a VQ.*
3. **The Playwright test of playback timing (D217 §4).** *To build now*; it needs Playwright's
   browsers, about 500 MB of the sandbox's disk.
4. **Prepares run one at a time in the core.** The node has two remux slots and one encode slot
   (cut-a §5.3), but the core's one prepare runner hands it one job at a time: a second person's
   prepare waits for the first to end. *To build now.*
5. **D217 §6 says a subtitle file beside the media is converted at scan;** it is converted when
   its video is first played. *Proposal: amend the decision* — conversion at play costs nothing
   until it is needed.
6. **Scans and backups are not jobs** (cut-a §5.3), so the job view never shows them, and
   `internal/core/backup/doc.go` still promises scheduled backups "with the job queue (M2)".
   *Proposal below.*

**Deferred by the owner:** Next Up (and "recently added" on `/home`), to a later milestone.

**Waiting on a device:** VQ1 (argon2id on devnas, open since M1), VQ7 (accounts on a phone), VQ9
(the escape test on devnas), iPhone Safari (and its boost switch, which does nothing there:
Safari's own HLS player ignores `setAudioRendition`), `mediastreamvalidator`.

## 6. The names (items 7, 8)

The seven reviews found about 180 names a reader has to look up or that could be clearer, and
about 25 doc comments that drifted. They split by who may change them:

- **Internal names** (Go identifiers, TypeScript names, catalogue keys, query names that only
  need regeneration): renamed without asking, package by package, in `refactor` commits. The
  largest: `identify`'s `type run` with receiver `work` and method `work.work`; `library` and
  `identify`'s `Ident` for the identification state; `playback`'s `located.id` (which also
  printed a stream id as a file id), `service.source()` beside the type `Source`, and `Lost`
  (which prepares again); `nodes.Connected()` (which picks a node); `metadata` for what runs all
  jobs; the web client's callback props named as values (`changed`, `answered`, `switched`) and
  `isOpen(job)`.
- **Names in a contract** — the API's JSON, the node protocol, database columns, setting and
  config keys — need the owner (AGENTS.md rule 17). Listed in §10, question 1.

**Duplicates** (rule 11), to fix: the web client's refusal handling written by hand at 21 sites
beside `dataOrThrow`/`throwIfRefused`; a second pattern at seven sites that **never shows a

copies of "create a user and sign in" in API tests; two fake TMDB providers. The setup code's own

**Derived data** that an input's change does not refresh, to fix: search lists titles whose files
are all gone; an override of an ambiguous item's name keeps its old candidates; a subtitle choice

the locale or the folding changes; a rendition is not prepared again when an audio track is

carrying a subtitle choice reads outside its own transaction.

## 8. What M4 needs decided before its first line (item 16)

Walking one M4 request — an invite, a registration, joining Watch Together, voice, now playing —
through the plan finds values no decision produces. Framed as the kinds of gap they are:

1. **Who an anonymous guest is to the byte paths.** D217 §2 and D216 need a session or the media
   cookie for every byte; D191 says a Watch Together seat never needs an account. Nothing says
   what a membership may play.
2. **How a signed-in guest's viewing is recorded** when the playing device is a TV that is not
   signed in (D191) and a browser's WebSocket cannot send an Authorization header.
3. **Where a join link's and an invite's secret travel.** D154 bans credentials in URLs; D218's
   fragment is its one exception; M4's acceptance tests for exactly this in a HAR.
4. **What an invite is, beside D218's registration link** (who picks the name, expiry, what the
   invited person can see — the share predicate D193 §4 deferred), without a second way to do one
   job.
5. **The HTTPS name's configuration:** the domain, ACME account, DNS provider, and the listen
   addresses for HTTPS and TURN. None is a config key or a setting.
6. **TURN's numbers:** ports, relay range, realm, credential lifetime, and the public relay
   address, which behind a VPS tunnel is the VPS's.
7. **Reachability on the owner's line** (DS-Lite, no public IPv4, native IPv6): the plan's first
   route, a port-forward, cannot work there, and the IPv6 route needs the AAAA record kept up to
   date when the prefix changes.
8. **Watch Together's numbers:** the drift, jitter and loss bounds and the netem profiles M4's
   acceptance measures against, D119's cap, and how now playing's stop message reaches a
   player alone (the play report has no channel back).
9. **Dependencies:** pion/turn, a WebSocket library and a DNS-01 client are not allowlisted, and
   no decision names them, as D217 §4 did for M3.

## 9. Platforms and dependencies (items 17, 18)

The module builds and vets for `linux/amd64`, `linux/arm64` and `darwin/arm64`, and builds for
`linux/riscv64`. This milestone had added a riscv64 file to the confinement against the owner's
rule to keep riscv64 out of the code; it is gone, and an architecture without a
written seccomp filter reports seccomp missing, cause `architecture_unwritten`. D205's seccomp row
now says what is built: amd64 and arm64, tested on amd64 only. New dependencies since the last
audit: `qrcode-generator`, `happy-dom` (both architecture-independent JavaScript), and
`golang.org/x/sys` made direct. The pinned FFmpeg is still the riscv64 blocker.
