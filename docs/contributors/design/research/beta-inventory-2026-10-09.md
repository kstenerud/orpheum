# Closed-beta inventory: self-deployment reachability and the hosted discovery tier

Read-only survey, 2026-10-09. `WN` = `docs/contributors/decisions/working-notes.md`. Line numbers are of the file at an earlier commit.

## (a) What is decided

### Product shape and the promise
- **D14** (WN:358): remote access for non-technical family is a headline requirement, not a deployment note.
- **D25** (WN:1242-1330): three tiers. *Local* (free, no account), *self-hosted assist* (our software on the user's machine, "load-bearing, not optional"), *hosted assist* (we run rendezvous, relay, `*.<hash>.<ourdomain>` certificates, identity directory; subscription). The promise is "we charge only for things that genuinely require another machine". Consequence (WN:1322): software must **degrade to tier 1 rather than break** if the hosted service goes, with a documented and *tested* exit path. Status says "provisional"; whether to operate a hosted service "is not a technical decision".
- **D68** (WN:4430): TURN is not a premium-tier justification; the media server is already the relay (embedded `pion/turn`, D193 §4).
- **D71** (WN:4690): a `relay` role of the same binary that the **core dials out to** (no port-forward, DDNS, UPnP; works behind CGNAT); tunnel mode (byte pipe, TLS passes through) is the one to build, cache mode speculative; untrusted by construction, clients authenticate the core; place it near the home server. Cloudflare Tunnel/CDN ruled out by its video terms (WN:4779). **Deferred by D193 §4.**
- **D72** (WN:4798): if hosted: **no free tier** (a free tier whose cost scales with use is forbidden), holds no data, **no accounts on the relay** (payment identity separate from access: buy a token, the token authorises a slot), payment is the abuse control, stated allowance never silent throttle, "same open-source binary, leaving takes an afternoon" (WN:4833-4880).
- **D73** (WN:4889): blind is not opaque; the relay reports what it sees to the household's core; only machine health is the operator's (remote-access plan :83-88).
- **D149** (WN:10599, §"business-model hole"): a relay with no per-role ceiling is an unbounded bill; per-role max bitrate and concurrent streams (F31) must exist before anything meters against it.
- **D152** (WN:10978): "am I reachable" is three observers (core, relay, client); a failure names its hop; the relay hands the core gap counts on reconnect (F53).
- **D154** (WN:11149): one opaque, hashed, revocable grant table; `relay` is one of its grant kinds (auth.md:194).
- **D187** (WN:14548, table WN:~14584): no directory of servers, no open sign-up, no payments between users.
- **D192** (WN:15115): three stages only: internal (private repo) → public betas (repo public, `0.x`, `BREAKING-CHANGES`, D85/D181 binding from the first public beta) → stable. Image/signed repo/release feed are "beta-stage work", built before the first public beta (WN:15133-15135).
- **D193 §4–§5** (WN:15285-15290, ~15300): no own relay role in Cut A; reachability order port-forward → IPv6 → standard tunnel (rathole/frp/WireGuard) to a VPS; one public name, Let's Encrypt by DNS-01, split-horizon or hairpin inside.
- **D195** (WN:15508): name provisional; **trademark clearance due before any store listing or the paid relay**.
- **D214** (WN:16393-16458), the decision closest to the owner's paid tier: *recorded, not scheduled*. A later commercial service **connects clients to a core without carrying content**:
  - §1 (WN:16408): core reports current addresses; a real HTTPS name + cert under the service's domain by DNS-01 (plex.direct shape); QR set-up carrying the core's key fingerprint + one-time pairing secret; UDP introductions for native apps/WebRTC.
  - §2 (WN:16419): the gap it cannot close (TV/Cast on IPv4-only network → core without public IPv4, ~2–10% of sessions); three options left **to be chosen when the service is built**: relay for that case only (brings legal.md §4 duties), provision a VPS in the user's own cloud account, or "unsupported, said plainly".
  - §3 (WN:16434): answers "where is this core" only to a pairing-secret holder; personal non-commercial terms; short log retention; no free tier whose cost scales.
  - §4 (WN:16444): Cut A keeps open a **stable core key identity** a client can pin, pairing completable from a scanned code, and a device code typed at the service must name its core (registered codes or a core prefix; "decided when the service is designed").
  - **Hosted relay stays deferred** until: a release aimed at owners who won't run a VPS, measured drop-off at the VPS step, someone to carry legal.md §4, no acceptable outside service (WN:16453).
- **D218** (WN:16590): admin-created accounts, one-time registration link/QR (secret after `#`), TV added by 8-char safe32 code typed on the TV.
- **D220** (WN:16661): before a **public release**, every dependency (transitive too) pinned to an audited commit; bumps audit the diff. Mechanism "designed with the release work". Not built.
- **D235** (WN:17420): containers; runtime image amd64+arm64; compose deployment; `make release` via GoReleaser with SBOM and signatures (§5). GoReleaser is not built (no `.goreleaser*`, no Makefile target).
- **D242** (WN:17724): an instance is one directory; backups are tarballs of `persistent/`.
- **D243 §6** (WN:17851): name `media.orpheum-app.com`; ACME DNS-01; **Cloudflare** API token scoped to Zone→DNS→Edit, sealed secret; record DNS-only, never proxied; domain, ACME contact, HTTPS and TURN listen addresses are config keys.
- **D243 §7** (WN:17858): reachability is **a VPS** (Hetzner, Nuremberg/Falkenstein); the core dials out over WireGuard; VPS forwards TCP 443, TCP+UDP 3478 and the relay range without rewriting the client's address; A and AAAA point at the VPS.
- **D243 §8** (WN:17863): TURN on 3478, relay ports 49160–49199, per-membership credentials, the VPS's address as the relay's public address.
- **D243 §4/§5** (WN:17817, 17832): library access is a role's; rebroadcast (a second core consuming a role's libraries) designed, built later.
- **D249** (WN:18195): dev / staging / release; deployment = runtime image + compose with `orpheum-tunnel` (WireGuard in a container, CAP_NET_ADMIN), `orpheum-core` sharing its network (tunnel not the default route), `orpheum-node`. Amendment (WN:18241): **one VPS address can front only one machine's TURN**, so a second name waits for a second address or VPS.
- **D261 §5** (WN:~18640): `https.acme_directory` is a config key.
- **D272** (WN:19039-19100): production on nas.example (§1); name swapped between staging and nas.example (§2); install = the image's setup command + `docker compose up -d`, **"the tunnel is optional, for a host reached without the VPS"** (§3); image built on nas.example from a tag, **registry publishing waits for the public beta** (§4); sliding migration window "until the public beta, when every step is kept for good (D181)" (§5); staging and nas.example share one tunnel key pair (§8).

## (d) Open questions and gaps for a closed beta (conceptual)

1. **Stage gap: "closed beta" is not a stage D192 defines.** D192 has internal → public beta (repo public). Which of the public-beta obligations apply to invited outsiders: D181/D85 compatibility promises, D272 §5's "every step kept for good", D220 supply-chain audit, D195 trademark clearance, `BREAKING-CHANGES`, published images? This is a policy question the owner must answer before anything else, since it decides the artefact channel and the migration promise.
2. **Distribution gap: no way for a non-owner to obtain the software.** Private repo + build-on-target (D272 §4) + registry deferred (D235 §5). Whether testers get source access, a prebuilt image, or something else is undecided.
3. **Design gap in D272 §3 vs the build: the tunnel-less deployment is decided but deferred** (`plans/release.md:44`). For testers with public IPv4 or usable inbound IPv6, the decided reachability order of D193 §4 (port-forward → IPv6 → tunnel) has no deployment shape at all; remote-access.md:6 says those routes are "not used", which was a statement about the owner's line becoming a de facto product limit.
4. **Self-hosted-assist gap (D25's "load-bearing, not optional" tier): the user's VPS side is a manual runbook, not software.** D71's `relay` role (the intended "our software, their machine") is deferred by D193; research option B (one-command install) was never decided. Whether the beta's self-hosted path is "WireGuard + our docs" or "our relay role" is undecided, and the two lead to different paid-tier designs.
5. **Name-and-certificate gap for anyone without a Cloudflare-hosted domain.** D243 §6 chose Cloudflare for the owner; the beta user's naming story is undecided: bring-your-own domain on any DNS provider, or a name under the project's domain (D214 §1's plex.direct shape), which in turn needs a decision on who holds DNS-01 authority for a shared zone (a zone-scoped token cannot be given to tenants), and on certificate issuance limits for many names under one registered domain (not researched).
6. **Paid-tier scope gap: D214 vs D72 vs D25 are three different products.** D25's hosted tier = rendezvous + relay + certificates + directory; D72 = a paid blind relay; D214 = connection-only (addresses, names/certs, QR pairing, no content), relay deferred behind four conditions (WN:16453). The owner's "central discovery/relay service" straddles them. Which of D214 §2's three options for the unreachable-TV case is taken is explicitly owed "when the service is built" — i.e. now.
7. **Legal/commercial gap: carrying content brings legal.md §4's duties** (repeat-infringer policy, DMCA agent, DSA contacts, logs) and D195's trademark clearance "before the paid relay". Also an internal tension: legal.md §4 advises "free or at cost, no price tied to bandwidth", while D72 forbids a free tier whose cost scales; D214 §3 says "a lawyer confirms". Unresolved, and a paid beta (even closed) triggers it.
8. **Identity-and-trust gap: the core has no stable key identity.** D214 §4 says Cut A keeps open a pinnable core key, QR-completable pairing, and device codes that name their core; none is built (no code; D214 cited nowhere outside the log). Any discovery service that hands a client "where is this core" needs the client to verify it reached *that* core, so this is the precondition for (6).
9. **Multi-tenancy gap: everything on the reachability path assumes one core per public address** (D249 amendment; `orpheum.nft`; TURN public address per core; client address preserved by policy routing). A shared service needs a per-tenant demux for HTTPS and a per-tenant answer for TURN, and must preserve or replace the client-address property D243 §7 relies on (now-playing location, rate limits). Not researched.
10. **Account/billing gap: D72 says no accounts on the relay, payment identity separate from access ("buy a token")**; how a tester obtains, renews and loses a slot, and what the stated allowance is (D72, F31), is undesigned. F31 per-role ceilings, which D149 says must exist "before anything meters against it", are not built.
11. **Exit-path gap (D25 consequence, remote-access research §8):** a hosted tier must degrade to tier 1 and the exit must be *tested*. Nothing defines what a core does when the hosted service is gone or a subscription lapses, or how a user moves from hosted to their own VPS.
12. **Observability gap: D73/D152's relay-side observer does not exist**, so the hop-naming today has two observers (core's self-check, client). For a support-light beta, whether testers' reachability failures are visible to anyone but the tester (D13/D73 limit what may flow to the operator) is undecided.
13. **Host-platform gap:** the deployment assumes a Linux host with WireGuard, BBR and Landlock available to Docker, IPv6 in Docker, and an Intel GPU, verified on amd64 only. Which host classes the beta supports (Synology/Unraid/TrueNAS/Proxmox, ARM) is undecided; the node's `confinement_policy = "require"` makes Landlock a hard prerequisite.
14. **LAN secure-context gap:** at home the deployment serves plain HTTP; D193 §5's "same name inside the house" depends on router hairpin or split DNS that the user must arrange. Whether beta users are told to use the public name at home is undecided.
15. **Measurement gap that gates the hosted relay:** D214's deferral rests on "measured drop-off at the VPS step"; nothing measures it, and D13 rules out telemetry. A closed beta is the only chance to collect it; how (asking, a reported reachability result) is undecided.
