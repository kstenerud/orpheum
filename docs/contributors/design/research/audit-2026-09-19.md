# Design audit, 2026-09-19

Run against the tree at 79 decisions, as an adversarial pass: *what did we not write down, what
did we write down wrongly, and what has somebody else already been burned by?*

## Method

- **The design tree read end to end** — 62 files, ~16,000 lines — and then swept for absence
  with a keyword battery, because a gap does not appear in a table of contents. Roughly half of
  what follows was found by the sweep rather than by the reading.
- **Source read locally**, from the depth-1 clones in the cache, and listed in §Sources below.
  Where this document describes another project's model it is from that code, not from
  documentation about it — which mattered at least once: §7's account of what Jellyfin 12.0
  removed is **not** what the write-ups say.
- **The complaint record, by reaction count**, from the GitHub search API across the server and
  five clients (`jellyfin`, `jellyfin-web`, `jellyfin-androidtv`, `Swiftfin`, `findroid`,
  `streamyfin`) on 2026-09-19. Reaction counts index breadth of demand, not severity; comment
  counts index pain, and the two disagree often enough to be worth reading separately.
- **The large commercial operators first**, per [README.md](README.md) §Method: Netflix's
  published delivery specifications and its own SIGCOMM paper, Apple's HLS authoring
  specification and App Store history, and the two statutory regimes that bind every commercial
  player (FCC/CVAA in the US, the EU Accessibility Act).
- **Reddit still unreachable** — same blocks as [sentiment.md](sentiment.md) §Method — but
  **`forums.plex.tv` was never tried and works**: Discourse, with `/top.json`, `/search.json`
  and `/t/<id>.json` all answering. That is first-hand Plex-user sentiment, and §31 is what it
  changed. Worth remembering as a general lesson: the blocked source was allowed to stand in
  for *all* first-hand user data, and a different one was sitting there.

## 2. The one-way door: GPLv3 and the App Store

[tech-licensing.md](tech-licensing.md) concluded "**GPLv3 for the project**" (now corrected in
place, and its §5 carries the client half). It reached that
by following FFmpeg's licence ladder, which is correct reasoning about **the server** and was
never tested against **the clients** — a distinction the document does not draw anywhere.

**The history is unambiguous.** VLC was removed from the iOS App Store in **January 2011** after
a GPL-compliance complaint; VideoLAN relicensed libVLC from GPLv2 to **LGPLv2.1** in late 2011,
explicitly to address "the widely publicized incompatibility of copyleft licensing with various
App Store agreements"; and the VLC application itself returned to the App Store in **July 2013
under MPL-2.0**. The relicensing took roughly two years because it required agreement from
every copyright holder.

**And the field has already converged on the answer.** Licence files read from the local clones,
star counts from the API on 2026-09-19:

| Project | Role | Licence | Ships on |
| --- | --- | --- | --- |
| `jellyfin/jellyfin` | server | **GPL-2.0** | — |
| `jellyfin/Swiftfin` | iOS + tvOS client, 4,173★ | **MPL-2.0** | Apple App Store |
| `streamyfin/streamyfin` | iOS + Android client | **MPL-2.0** | Apple App Store |
| `jarnedemeulemeester/findroid` | **Android-only** client, 4,257★ | **GPL-3.0** | Play Store, F-Droid |
| `jellyfin/jellyfin-androidtv` | Android TV client, 4,562★ | **GPL-2.0** | Play Store |

Read the pattern in the last three rows: **the Apple clients are MPL, the Android ones are
GPL.** That is not taste. Google Play tolerates GPL; Apple's terms have not.

**Why it matters more here than for Jellyfin.** Jellyfin's Apple clients are third-party and
were licensed independently from the start. Ours are first-party by design
([D10](../../decisions/working-notes.md)), tvOS is explicitly planned
([D30](../../decisions/working-notes.md)), and
[D67](../../decisions/working-notes.md) commits that tvOS never gates a feature — a commitment
that is void if the app cannot be distributed at all. Under a whole-project GPLv3 there is no
iPhone client, no iPad client and no Apple TV client, for the project whose overview says
**"the project is judged on its TV app."**

**The fix is free if taken now and expensive later**: licence by artefact. GPLv3 for the server
and node — that is where the FFmpeg ladder lands us and where copyleft is worth having — and
**MPL-2.0 for the clients and the shared SDK**. MPL's copyleft is per-file, so our code stays
open while the app is distributable, and it is the licence VLC, Swiftfin and Streamyfin all
independently arrived at. It also serves [D20](../../decisions/working-notes.md): the shared
TypeScript SDK is meant to be the thing third parties build clients on, and a GPL SDK is a
poor foundation for that.

**Worth stating alongside it: why GPLv3 and not AGPL.** Immich chose AGPL-3.0. We do not, and
the reason is [D71](../../decisions/working-notes.md)/[D72](../../decisions/working-notes.md):
the relay is a mode of the same binary and we intend people to run it on their own VPS. AGPL
would attach a source-publication obligation to that act. The cost of declining AGPL is that a
competitor may host a modified relay without publishing; since the relay holds no data and has
no moat, that is a cost worth paying.

## 3. Play state is a row where it should be a log

Read from `Emby.Server.Implementations/Library/UserDataManager.cs` and
`MediaBrowser.Model/Configuration/ServerConfiguration.cs`:

```csharp
public int MinResumePct            { get; set; } = 5;
public int MaxResumePct            { get; set; } = 90;
public int MinResumeDurationSeconds{ get; set; } = 300;
```

and the state it guards is a single row per `(user, item)` carrying
`PlaybackPositionTicks`, `Played`, `PlayCount`, `LastPlayedDate`. **No device, no sequence, no
history.** Two clients reporting progress for one item are two writers to one cell, and the
last one wins.

The tracker is what that produces, sorted by comment count:

| Issue | Comments |
| --- | --- |
| *Most movies now appear to be 75% watched in Continue watching* | 44 |
| *Movie favourites are randomly unfavourited* | 33 |
| *'Continue Watching' not displaying on home screen* | 30 |
| *Media playback randomly starts over again or jumps back — STILL* | 29 |

Note the second row. Favourites live in that same single row, which is why an unrelated-looking
bug sits in the same cluster: one race, three symptoms.

And two defaults in that same function are worth copying down as things **not** to do:

```csharp
else if (!hasRuntime)
{
    // If we don't know the runtime we'll just have to assume it was fully played
    data.Played = playedToCompletion = true;
}
```

— a missing fact silently becomes a destructive assertion about the user's state — and
`MinResumeDurationSeconds = 300`, which marks **anything under five minutes fully played the
moment it is opened**, and never resumes it.

**What the commercial side does.** Plex's client protocol is a heartbeat: the `/:/timeline`
endpoint is hit on every play-state change and otherwise **every 10 seconds on LAN/WAN and
every 20 seconds on cellular** — a cadence, not an event. That is the right transport shape and
it does not by itself solve the race; what solves the race is that the *thing being reported* is
an event with an origin and an order, not an assignment to a cell.

**And there is a whole product in the absence of the log:** Tautulli, 6,590★, exists to give
Plex users watch history and statistics, which the server does not keep. Jellyfin's tracker has
an open request titled *Native Playback Statistics — Per-User Watch Time Tracking*. A play log
is not a luxury feature; it is the thing people bolt on.

**So:** a monotonic `(user, edition)` position with a sequence number that a stale device cannot
rewind, **plus** an append-only play-event log — `started`, `progress`, `paused`, `seeked`,
`completed`, `abandoned` — carrying device, timestamp and the client's own monotonic clock. The
log is what makes offline reconciliation possible at all, and it is what answers "why does this
say 75% watched" without a debug build.

**One hole in [D79](../../decisions/working-notes.md) closes here too.** Watch state attaches at
the Edition, but a Version may be **multi-part**. "Resume at 00:12:30 of part 2" is not an
Edition-level position. So each File carries its offset within the Version's timeline, and the
stored position is **Edition-relative** — which is also what makes resume survive the
1080p→4K switch that D79's fixture requires.

## 4. Media segments are typed, and they belong at the Version

**A precise statement of what is missing, because this one is half-present.**
[plugins-and-workarounds.md](plugins-and-workarounds.md) §3 gives Intro Skipper a whole section,
correctly calls it *"the best available specification for D19's tier 3"*, and concludes that
intro/credit detection *"should be the second tier-3 plugin we write"*. The **detector** is
researched and scheduled.

What is absent is everything it would publish into: no segment model, no table, no statement of
where a segment attaches given [D79](../../decisions/working-notes.md)'s four levels, no
distinction from chapters, no client contract, and no plan file. That research even records the
symptom without drawing the conclusion — Intro Skipper *"contains an EF migrations directory of
its own"*, and then **"the core absorbed the feature (media segments became native)"** in
Jellyfin 10.10. A plugin carrying its own schema is what a missing core model looks like, and
Jellyfin fixed it by adding one. We planned the plugin and not the table.

**Netflix's is the reference implementation**, shipping since 2017: the boundaries come from
audio fingerprinting of recurring theme music, shot-boundary and title-card
detection, subtitle timing cues, and human-in-the-loop validation for the hard cases. We cannot
do the ML half, and we do not need to — most of the value is in the *model*, not the detector.

**Jellyfin already built the model**, in 10.10 — the absorption noted above — and it is worth
copying because it is right in the one place that matters. From
`src/Jellyfin.Database/.../Enums/MediaSegmentType.cs` and `Entities/MediaSegment.cs`:

```csharp
public enum MediaSegmentType { Unknown, Commercial, Preview, Recap, Outro, Intro }

public class MediaSegment {
    public Guid   Id; public Guid ItemId; public MediaSegmentType Type;
    public long   StartTicks; public long EndTicks;
    public required string SegmentProviderId;   // provenance
}
```

Their own documentation states the reason for not reusing chapters: *"Unlike chapters, which
have no type, media segments can contain type information, allowing different actions based on
the type."* That is the whole argument, and it is correct. Chapters are authored container
metadata; segments are typed, derived, and carry provenance.

The demand: `intro-skipper/intro-skipper` at **2,780★**, plus **968★** on the archived original
it forked from, and Swiftfin has an open *Skip button for media segments* request.

**Where we should differ.** `ItemId` in Jellyfin points at a `Video`, which is
[D79](../../decisions/working-notes.md)'s conflated Edit/Manifestation/Item. Segment
**timecodes index an encoding**, not a work: a 4K remux and a web-dl of the same episode can
differ by seconds of lead-in, and PAL-speedup rips differ throughout. So segments attach at the
**Version**, with a documented derivation for a sibling Version by runtime alignment rather
than a second detection pass. Add a `confidence` and a **user override** that survives
re-detection, per [principles §3](../../principles/README.md).

## 5. Audio: nobody is doing the arithmetic, and we already own the pipeline

The tree contains no mention of loudness, downmix, dynamic range, or dialogue level. This is the
gap with the best value-to-cost ratio in the audit, for one reason:
[D22](../../decisions/working-notes.md) already puts **audio encoding in the core**, so we are
the ones doing the downmix.

**Netflix's answer is to fix it at ingest.** Their delivery specification requires **-27 LKFS
±2 LU, dialog-gated**, with true peak not exceeding **-2 dBTP**, measured per ITU-R BS.1770.
The dialog-gated target was chosen empirically: content compliant with the earlier -24 LKFS
full-programme spec clustered at -27 when measured dialogue-only. So the entire Netflix
catalogue is loudness-consistent before a player ever sees it.

**We cannot do that**, because [principles §2](../../principles/README.md) says the files are
not ours to rewrite. But the music world solved exactly this constraint a quarter of a
century ago: **measure once, store the number, apply gain at playback.** That is ReplayGain
(proposed 2001, and in every serious audio player since), and the node
already opens every file at scan time. FFmpeg's `ebur128` filter implements EBU R128; the
measurement is one extra pass over audio we are already decoding.

**Honest limitation, stated now so nobody is surprised:** FFmpeg measures *programme* loudness
(BS.1770 gated), not Netflix's **dialogue-gated** figure — dialogue gating needs Dolby's
Dialogue Intelligence, which is not in FFmpeg. So our number is comparable across our own
library and is **not** the same quantity as Netflix's -27 LKFS. Say so rather than implying
parity.

**The second half is the downmix, and Jellyfin's documentation is an admission of defeat.** It
offers **five** algorithms — `None`, `Dave750`, `NightmodeDialogue`, `RFC7845`, `AC-4` — and
documents a dialogue caveat against nearly every one:

- `None`: *"The auto-generated matrix may produce weaker volume levels"*, *"too low perceived dialog"*
- `Dave750`: *"dialogues might sound too quiet compared to music"*
- `NightmodeDialogue`: *"Too quite sound effects is not ideal for movies"*
- `RFC7845`: *"too-quiet center channel, which can cause sound effects and music to potentially overpower dialogues"*

Five wrong answers in a dropdown is what a problem looks like when it has been pushed to the
user. The underlying physics is simple: dialogue lives on the centre channel at a level that
assumes its own speaker, and every downmix matrix attenuates it to avoid clipping the sum.

**And there is a third mechanism that everybody ignores.** AC-3 and E-AC-3 carry `dialnorm` and
DRC metadata authored with the content. FFmpeg's decoder **applies DRC by default**
(`drc_scale = 1`), which is right for a phone on a train and wrong for a home cinema — Kodi
carried this as a bug for years, and Jellyfin has it open as
*"Can't set Dynamic Range Compression (DRC) decoding preference when ffmpeg transcodes Dolby
Digital audio"* (#10148).

Notice the shape of that: the correct value of `drc_scale` depends on **the room the listener is
in**, which is exactly the class of fact [D2](../../decisions/working-notes.md) says the server
cannot know. So it is a per-device preference, not a server setting — D2 applied to audio.

## 6. Parental controls, and why certifications are not an integer

Absent from the tree. `jellyfin-androidtv`'s **third-most-reacted issue** is *PIN protection for
users* (+56), behind only the playback rewrite and SyncPlay.

**Netflix's model is the one to copy**, and it separates two levels cleanly: **per profile** —
a profile-lock PIN, a maturity-rating ceiling, and explicitly blocked titles — and **per
account** — a PIN required to *create* a profile, which is the bypass that otherwise makes all
of it theatre. The second one is the part homegrown implementations forget.

**The schema trap is that a rating is not a number.** Netflix's own help text: *"Maturity ratings
are either set by Netflix or by a local standards organization... Different countries use
different rating systems."* BBFC 15, FSK 16, MPAA R, ACB MA15+ and PEGI 18 are not points on
one scale, and TMDB returns certifications as a **list keyed by country**. So a certification is
`(system, code)` with an **ordering defined per system**, which is structurally the same
per-locale split [D45](../../decisions/working-notes.md) already built for names — and it fails
the same way if flattened, except that flattening a rating fails *open*.

**The access-control half is nearly free**, and pleasingly so: a kids profile is **a grantee plus
a predicate**, which is [D76](../../decisions/working-notes.md) again. It becomes a fifth
binding of the rules engine rather than a subsystem, and it inherits D76's fail-closed rule,
which is the correct direction for this binding too.

## 7. Client/server skew has no contract, and our clients are in app stores

Jellyfin's 12.0 cycle is the cautionary case, and reading the source on master
(`AssemblyVersion 13.0.0`, read 2026-09-19) makes it sharper than the secondary reports do — because they did **two different
things** to two legacy surfaces and only one of them was a deprecation:

- **The `/emby/` and `/mediabrowser/` route prefixes are simply gone.** No occurrence anywhere
  in `Jellyfin.Api` or `Jellyfin.Server`. A client calling them gets a 404, in the middle of
  whatever it was doing.
- **`X-Emby-Authorization` was not removed — it was put behind a flag**, read only when
  `_configurationManager.Configuration.EnableLegacyAuthorization` is set, along with the
  `Emby` scheme name in the `Authorization` header. The property is declared
  `public bool EnableLegacyAuthorization { get; set; }` with no initialiser, so it **defaults
  to off** and one setting brings it back.

The second is a good deprecation and the first is not, and nothing in their process distinguishes
them — which is exactly the gap. Add to that a runtime move to .NET 10 that broke binary
compatibility with every plugin built for 10.11, and the support-forum thread title is
*"New server version incompatible with clients?"*.

**Three things make this worse for us than for them**, and none is written down:

1. **Our clients are first-party and ship through app stores.** A server-side fix is a
   `docker pull`; a client-side fix is a review queue. The server can always be newer than the
   client and frequently will be.
2. **Televisions do not update.** A TV app sits at whatever version the household installed.
3. **[D2](../../decisions/working-notes.md) puts decision logic in the client.** A thin renderer
   can be fixed from the server. A client that probes its own decoder, intersects a menu and
   picks a rendition cannot be.

And [D18](../../decisions/working-notes.md)'s Jellyfin adapter means we additionally inherit
*somebody else's* compatibility obligations, against clients we do not control.

**The contract has to be written before the first client ships**, and it is cheap: response
shapes grow but never change meaning; a removal needs a deprecation window measured in releases
and an advertised sunset; the server declares a minimum supported client revision and the client
declares the revision it was built against; the mismatch produces **one legible message**
rather than a 404 in the middle of playback; and CI diffs the generated OpenAPI document and
fails a breaking change that has no explicit waiver. The OpenAPI document is already generated
from the code and the build is already gated on it being current
([D20](../../decisions/working-notes.md)) — the gate just needs to compare against the last
release as well as against the source.

**It applies to three protocols, not one.** [D61](../../decisions/working-notes.md) already
requires the node wire format to skip unknown record kinds. The core↔relay and core↔client
directions need the same rule stated, and the version inventory D61 and
[D74](../../decisions/working-notes.md) already share is where it belongs.

## 8. There is no adaptation, and the one link that needs it is the one we charge for

[overview.md](../overview.md) lists under *not building*: **"A Netflix-style encoding ladder —
bandwidth is free on a LAN."** True, and it is the right call for the LAN. But the headline
feature and the entire commercial proposition is **remote access**
([D14](../../decisions/working-notes.md), [D71](../../decisions/working-notes.md)), where
bandwidth is a hotel Wi-Fi, and on that path the design offers a ranged GET of a 20 Mbps remux
and nothing else. When the link degrades, playback stalls. There is no fallback, because the
rendition list was resolved once, at the start.

**Netflix published the definitive study of this, and it is a correction to the obvious
approach.** Huang, Johari, McKeown, Trunnell and Watson, *A Buffer-Based Approach to Rate
Adaptation: Evidence from a Large Video Streaming Service*, SIGCOMM'14 — run on Netflix's own
production traffic, "millions of real users". The finding: bandwidth estimation is the wrong
input. Choosing the rate **from buffer occupancy alone** reduced the rebuffer rate by
**10–20% against their own production algorithm**, and their conclusion is precise —
*"capacity estimation is unnecessary in steady state; however using simple capacity estimation
(based on immediate past throughput) is important during the startup phase."* The same family
of algorithm (BOLA) is the default in dash.js and is in production at Akamai, the BBC and CBS.

**What this means for us is not an encoding ladder.** It is three things:

1. **Say the truth out loud.** Direct play over a WAN has no adaptation. That belongs in
   `remote-access.md`, not discovered by a user in a hotel.
2. **The client already picks; let it re-pick.** [D2](../../decisions/working-notes.md) put
   rendition choice on the client, which means the *correct* adaptation signal — its own buffer
   level — is already in the right place. No server-side bandwidth estimator, no ABR ladder: the
   existing negotiation, re-run, driven by buffer occupancy. That is D2 turning out to be more
   right than it was argued.
3. **Accept the roadmap consequence.** On a constrained remote link the only lower renditions
   that exist are ones a *transcoder* makes. `transcoding.md` (b), "bandwidth transcoding", is
   currently Phase 4 and described as "deliberately late". It is not late — it is **on remote
   access's critical path**, and remote access is the paid tier. The plan already half-says this
   ("treat it as coupled to remote access, not to the library"); the roadmap does not.

**And Apple has already written down what interchangeable variants require.** The *HLS
Authoring Specification for Apple Devices* states that key frames (IDRs) **should be present
every two seconds** and that **video segments must start with an IDR frame** — which is the
same constraint arrived at from the other direction, and which AVPlayer enforces in practice.
Apple also ships `mediastreamvalidator`, which parses a playlist and its variants and reports
non-conformance. Nothing in our tree mentions either. Running the validator against our own
output is a free conformance test for the Apple client and for AirPlay, and it belongs in
[testing-strategy.md](../plans/testing-strategy.md).

**And one invariant collides.** [D23](../../decisions/working-notes.md): *"no operation on one
axis may restart another"* — with video named as the axis whose change is expensive. A
mid-film bandwidth downshift **is** a video-axis change, in precisely the situation where a
restart is least affordable. Either the video axis gets segment-aligned interchangeable
variants (which `transcoding.md` §(b) already specifies: "use the source keyframe grid as the
segment grid for **every** rendition including passthrough, so variants are interchangeable" —
so the mechanism exists and its consumer was never identified), or we state that remote
adaptation costs a reposition. The first is better and is already designed; it just needs to be
named as a requirement of remote access rather than a detail of transcoding.

## 9. Offline download is the field's top client request and has no server side

Our tree treats offline as a **client** state machine ([D29](../../decisions/working-notes.md),
[shared-core.md](shared-core.md)) — "the one genuinely hard part". Nothing describes what the
*server* owes it.

The demand, by reaction count:

| Repo | Issue | Reactions |
| --- | --- | --- |
| Swiftfin | **Local Downloads** | **145** — the single most-reacted issue on that tracker |
| findroid | Allow transcoding of multimedia content | 52 |
| findroid | **Transcode downloads to save storage space** | 32 |
| findroid | Downloader suggestion | 25 |
| findroid | Downloading & Deleting Enhancements | 21 |
| findroid | Download storage location | 21 |
| findroid | Batch download a whole season / unwatched episodes | 18 |
| streamyfin | Choosing download location (internal/SD) | 16 |
| streamyfin | Download queue stops when background downloading | 8 |

Note what the second and third entries actually say: people want a download to be **smaller than
the original**, which is the compatibility transcoder used for a completely different reason
than compatibility. That is a server-side capability with a server-side cost and it is
unplanned.

**And there is a cross-cut nobody has noticed.** [D53](../../decisions/working-notes.md)–
[D58](../../decisions/working-notes.md) build an elegant on-demand font pipeline: Noto served by
language, subset per subtitle track at scan time, embedded fonts fetched only on explicit
opt-in. **Every one of those is an HTTP fetch from the server.** On a plane, a downloaded film
with a Japanese subtitle track renders as tofu. The same is true of the per-track subtitle
resources, the artwork, and (per §4 above) the segment list.

So: **a download is a rendition plus a lease, and it is self-contained.** The manifest for an
offline item enumerates every resource the client must also fetch; the lease is what lets the
server know a stored rendition is still referenced and must not be reaped; and deletions
reconcile through [D8](../../decisions/working-notes-archive.md)'s change journal, which is the reason
D8 exists and still has no consumer.

## 10. Casting is Watch Together with a group of one

The tree mentions Chromecast once, as a "v2 client". Meanwhile: Swiftfin *iOS — Chromecast*
(+43, its second-most-reacted issue), Swiftfin *Support for SharePlay* (+29), Swiftfin *tvOS —
Support Deep Links* (+26), androidtv *Deep Link Support* (+22).

The observation worth having is that **we have already designed this and not noticed.**
[D62](../../decisions/working-notes.md) defines the per-client Watch Together surface as six
methods — join, leave, report position, accept a play/pause/seek, report readiness, report
buffering. Casting is *one device driving another device's playback*. That is the same six
methods with a group of size one plus a remote controller, on the LAN, with the voice channel
switched off.

Getting this said now costs nothing and prevents the usual outcome, which is a second,
parallel, subtly different remote-control protocol. It also makes a **Chromecast receiver**
exactly what [D2](../../decisions/working-notes.md) says a client is, rather than a special
case, and it makes **AirPlay** free where the Apple client uses AVPlayer.

**Deep links are the other half** and are an API commitment: an item needs a stable, shareable
URL form before anything publishes one.

## 11. There is no way to delete anything

Zero occurrences of "trash", "recycle", "delete the file" or "delete media" in the tree. The
positions that exist point in opposite directions: [principles §2](../../principles/README.md)
mounts media read-only, and [D75](../../decisions/working-notes.md) makes retention **mark**
items rather than delete them — deliberately, and correctly, because Maintainerr and Janitorr
delete and people are frightened of them.

But "mark and review" has no "act", and users do delete things. Left unstated, somebody
eventually writes `os.Remove` in a handler, and then the read-only promise is a comment.

The position should be explicit: a **writable path is opt-in per library** and off by default;
deletion is **two-phase** — mark, then a confirmation that names every file and its size;
it goes through the node, never the core (the core does not touch media filesystems —
[D33](../../decisions/working-notes.md)); and it is the one place §2 is deliberately relaxed,
which is worth saying in §2 itself rather than in a corner.

## 12. Caption presentation has a legal floor, and we meet most of it by accident

[D78](../../decisions/working-notes.md) says text subtitles stay the default because "a bitmap
cannot honour a user's subtitle-size setting, and subtitle size is accessibility rather than
preference". Correct — and the list is far longer than size, and it is **statutory**.

**United States — 47 CFR §79.103** (CVAA), which binds apparatus and video programming
distributors. Users must be able to control:

| Control | Requirement |
| --- | --- |
| Font | the **eight fonts required by CEA-708**, assignable per style |
| Size | **50% to 200%** of default |
| Text colour | override authored colour, palette of **at least 8** (white, black, red, green, blue, yellow, magenta, cyan) |
| Background colour | same 8-colour minimum, from the 64 CEA-708 colours |
| Background opacity | opaque / semi-transparent / transparent |
| Caption window colour and opacity | same again, separately from the background |
| Character edge | **five** attributes: none, raised, depressed, uniform, drop-shadow |

And since **17 August 2026** — a month ago — those settings must additionally be *"readily
accessible"* to deaf and hard-of-hearing users, rather than merely present.

**European Union — Directive (EU) 2019/882**, the European Accessibility Act, applicable since
**28 June 2025**, requires the player itself to expose caption size and font controls and to
make audio description reachable. Audiovisual media services are explicitly not exempt.

**Three consequences.**

1. **[D55](../../decisions/working-notes.md) is already on the regulatory path and does not know
   it.** The served font set was chosen as "the CTA-708 style axis, six upright variable faces
   covering the seven real caption styles" for typographic reasons. That *is* the statutory
   list. Make the eight-style mapping explicit and it becomes a conformance artefact instead of
   a coincidence.
2. **The overlay rendition forecloses every control in that table.** A pre-rendered bitmap has a
   fixed size, colour, background, window and edge. D78 noticed one row of seven. So the overlay
   must never be the *only* offer for a caption track, and when it is chosen the client must say
   which controls it has lost — [principles §3](../../principles/README.md), applied to
   accessibility.
3. **Audio description is a track kind, not a disposition flag we happen to parse.** It appears
   in [identification.md](../plans/identification.md)'s track-kind derivation and nowhere in the
   client contract or the preference axes.

**The user-facing convergence is the nice part.** `jellyfin-web`'s open subtitle issues are, in
order: *Subtitles disappear when fullscreen*, *Subtitle offset text field is clamped*,
*Inconsistent size of subtitles*, *Subtitles dark background box*. Users are asking, one at a
time, for the statutory list.

**And a fourth item rides along.** *Manual audio and subtitle sync offset* appears on **four
separate trackers**: androidtv *Adding audio / subtitles sync menu* (+31), findroid *Subtitle
timing change* (+17), jellyfin-web *Subtitle offset clamped* (+8), streamyfin *Subtitle offset*
(+8). It is not niche. It is a signed millisecond value that must **persist** at the same scope
as every other track preference ([D24](../../decisions/working-notes.md)) — cheap as a column
now, a migration later.

## 13. No continuous observability

Sorted by reactions, the **second-most-reacted open issue in the entire Jellyfin server
tracker** — ahead of every security issue, every metadata bug, every feature — is
***Improve Prometheus Exporter with JF Metrics*** (+63, open since 2020-04).

We have two observability surfaces and both are incident-shaped:
[D74](../../decisions/working-notes.md)'s bug report, generated when something has already gone
wrong, and [D73](../../decisions/working-notes.md)'s per-component status records, which the
core consumes. Neither answers "is it healthy right now", and neither lets
[performance-targets.md](../plans/performance-targets.md) be enforced anywhere except CI — a
benchmark that only runs in CI cannot tell you the library got slower as it grew, which is
exactly how Jellyfin 10.11's 30–50 second home page shipped.

This audience already runs Prometheus and Grafana. A `/metrics` endpoint is boring, expected,
and the natural home for the numbers D73 already collects. It must be **off by default and
bound locally when on** — it is a data-exposure surface and [D13](../../decisions/working-notes.md)
makes that a promise, not a preference.

## 14. The client's probe is the right authority, and it lies

[D2](../../decisions/working-notes.md) is right that the client is the only party that can ask
its own decoder. [playback-survey.md](../plans/playback-survey.md) is right that you must
*"measure, do not just ask"*. Neither covers the runtime case: the probe said yes, playback
started, the decoder failed at minute three.

This is the case the big operators answer with something we cannot have — Netflix runs a device
certification programme and ships a per-device platform stack precisely because probes are
unreliable. Our equivalent has to be cheaper and it exists already in pieces:

- **A ladder, not a single pick.** The client sends a *prioritised* list already
  ([D21](../../decisions/working-notes.md)); on failure it falls to the next entry rather than
  to an error screen.
- **A client-local memory.** The client remembers the (probe answer → actual failure) pairing
  for its own hardware. That is not a device database and does not become one: it never leaves
  the device except as a report.
- **A report that fans in.** [D73](../../decisions/working-notes.md) already makes the client's
  observations flow to the core, which is where a human can see that every Fire TV in the house
  fails the same way. That gives [device-lab.md](../plans/device-lab.md) a production data
  source it currently lacks.

None of this reintroduces a server-side device-capability database
([D21](../../decisions/working-notes.md) holds). The server still never guesses.

## 15. Nobody has designed signing in on a television

Absent from the tree. It is the first interaction every user has, on the device with the worst
text entry ever shipped, and the first one a *shared* user has on somebody else's TV.

**The standard is RFC 8628**, the OAuth 2.0 Device Authorization Grant: the TV shows a short
code and a URL, the user opens it on a phone, the TV polls. Every large streaming service uses
it. Jellyfin hand-rolled the same shape as Quick Connect —
`QuickConnectResult { Secret, Code, DateAdded, DeviceId, DeviceName, AppName, AppVersion }`,
read locally — which is a reasonable design that is nonetheless a bespoke protocol where a
standard one exists.

[D20](../../decisions/working-notes.md) already puts OIDC in the core in Phase 1. The device
grant is nearly free **if the auth design anticipates it** and awkward if it does not, because
it changes what a "session" is: the authorising act happens on a different device from the one
being authorised. It also interacts with sharing — a grantee's television must be pairable
without the owner typing a password into somebody else's living room — and with
[D85](../../decisions/working-notes.md), since the pairing endpoint is the one surface a very
old client will hit first.

**And there was no `auth.md`.** Identity, sessions, token scope and lifetime, revocation, device
pairing and the sharing hand-off were spread across a bullet in `library-model.md`, two open
questions in `threat-model.md` and a section in `remote-access.md` — none of which owned them,
for a subsystem [D20](../../decisions/working-notes.md) already put in Phase 1. There is one
now: [auth.md](../plans/auth.md).

## 16. Spin-down is an unpriced cost of the snapshot interval

Jellyfin issue #7689 is *Reduce hard disk access during playback*, and the comparison in it is
that Plex has nearly no disk activity where Jellyfin has a lot. **§31's forum sweep shows that
comparison is wrong** — *Plex is constantly spinning HDD up and down* (22 posts), *HDD never
turns off while PMS is running*, *Plex wakes up Synology NAS every hour* — which makes the
finding stronger, not weaker: both do it, so it is a property of the workload and not something
a better implementation avoids by accident.

For a NAS audience — and [test-hardware.md](test-hardware.md) names an 8 GB Celeron NAS as the
honest low end — spinning drives cost power, noise and wear, and "it keeps my array awake" is
the kind of complaint that ends in an uninstall.

[D60](../../decisions/working-notes.md) made snapshots **temporal**, for good reasons, and
`snapshot_interval` is a number [performance-targets.md](../plans/performance-targets.md)
currently justifies with two competing pressures: a silently-dead watcher wants it short, an
expensive SMB enumeration wants it long. **There is a third pressure and it was not written
down: the interval is how often the disks must wake.**

Two mitigations, both belonging in `scanner.md`:

- **Batch the wake.** All roots on one physical device enumerate together, so one scan spins the
  array up once instead of dribbling. Adaptive per-directory cadence — already specified — must
  not be allowed to produce a continuous trickle of small wake-ups, which is strictly worse
  than one long pass.
- **`archival` means untouched.** The scanner plan already has "a config field letting the user
  declare a library archival". Make its meaning concrete: no walk, no probe, no thumbnailing, no
  loudness pass — only the journal, if a watcher is available. And the node **reports** that it
  is honouring it, per [D73](../../decisions/working-notes.md), so "why is my new file missing"
  has an answer.

## 17. People are not modelled, and merging by name is the field's oldest bug

`library-model.md` has no `Person`. The tracker has *Actors with the same name appear as one
person* (27 comments, open since 2020-06) and its music twin *Music artists with the same name
are merged while MBIDs are ignored* (29 comments) — the second title states the cause exactly:
a stable external identifier was available and the code matched on the display string instead.

The rule is the same one [D7](../../decisions/working-notes.md) already applies to items: a
Person is an entity with `{provider, provider_id}` identity; credits are typed rows
(`cast` with a character name and an order, `crew` with a job); and **name is never the key**.
It is small, it is schema, and retrofitting it means re-matching every credit in the library.

## 18. Artwork has no pipeline, and the home page is fifty posters

Nothing in the tree says how an image gets from a provider to a television: no resizing, no
cache, no format choice, no ceiling. Grep finds no "resize", no "image cache", no "avif".

It is multiplied by two decisions already taken. Artwork is **per-language**
([D45](../../decisions/working-notes.md)) — posters have title text in the pixels — and there
are **four levels** ([D79](../../decisions/working-notes.md)), so a Title, an Edition and a
Collection can each carry their own with fallback between them.

And the field's evidence that it goes wrong is a data-loss bug, not a performance one:
Jellyfin's *Some custom primary images/art seem to have automatically reverted or replaced with
defaults* (39 comments) — user-chosen artwork destroyed by a metadata refresh, which is
[principles §2](../../principles/README.md) in image form.

[artwork.md](../plans/artwork.md) has the shape: derived sizes produced in the **node** (an
image decoder is attacker-supplied-data surface exactly like a media file, and the core never
parses one), content-addressed immutable URLs, a **closed set of named sizes** rather than an
open `?w=` grammar, and user-chosen artwork treated as user data that a refresh can never
overwrite.

## 19. An episode has one position where it needs one per ordering

The tree mentions episode ordering three times and all three are about **providers** — TheTVDB
is good at it, regional providers differ, ordering is a per-field provenance question. Nowhere
does the *library model* have a place for it.

**This is [D79](../../decisions/working-notes.md)'s disease in a different organ**, and
Jellyfin's source shows the same signature. An episode's position is `IndexNumber` +
`ParentIndexNumber` — **one position**. Specials, which do not fit, get three nullable
escape-hatch columns and a coalescing chain:

```csharp
public int? AirsBeforeSeasonNumber  { get; set; }
public int? AirsAfterSeasonNumber   { get; set; }
public int? AirsBeforeEpisodeNumber { get; set; }
public int? AiredSeasonNumber =>
    AirsAfterSeasonNumber ?? AirsBeforeSeasonNumber ?? ParentIndexNumber;
```

And which ordering a series uses is `Series.DisplayOrder`, **a bare string**, compared against
magic values in two places with **two different comparison modes** —
`string.Equals(displayOrder, "absolute", StringComparison.Ordinal)` in the TMDB client and
`string.Equals(series.DisplayOrder, "absolute", StringComparison.OrdinalIgnoreCase)` in the
library manager. Three nullable side-columns plus a magic string is what a missing relation
looks like.

The real shape is that **aired, DVD, absolute and a provider's alternate orders are all
orderings of the same set of episodes**, so a position is `(ordering, season, number)` and an
episode has several. Anime makes it unavoidable rather than academic — absolute numbering,
season splits, and providers that disagree — and
[tech-metadata.md](tech-metadata.md) already says generic providers are simply *wrong* there.

The cost of getting it wrong is not cosmetic: [play-state.md](../plans/play-state.md)'s
"Next Up" is defined as *the earliest unwatched episode after the latest completed one*, which
is a statement about an ordering. With one position, a household cannot have one person
watching in DVD order and another in aired order — and with the ordering explicit, that is
free.

## 20. Extras are not Editions, and there is nowhere for them

Trailers, deleted scenes, featurettes, behind-the-scenes, interviews, bloopers, shorts — and
**theme songs and backdrop videos**, which is `jellyfin-androidtv`'s *Video Backdrop and Theme
song playback* (+37). None of them appear anywhere in the tree.

They break the four-level model if forced into it. A trailer is not an **Edition** — it is not
a cut of the film. It is not a **Version** — it is not an encoding of the film. It is a
different, shorter work that belongs *to* the film. With no place for it, the two outcomes are
both bad and both observable in the field: extras become top-level items that pollute the
library, or they become a side-array.

Jellyfin took the second road and its enum is the right vocabulary even though its storage is
not: `Clip, Trailer, BehindTheScenes, DeletedScene, Interview, Scene, Sample, ThemeSong,
ThemeVideo, Featurette, Short`. Each extra is a full `BaseItem` with an `OwnerId`, excluded
from listings by convention.

The model that fits ours: **an extra is a typed relation to a Title or an Edition**, holding
its own Versions and Files like anything else, never surfacing in the main listing, and never
confusable with a cut. It costs one table now. Note also that `ThemeSong`/`ThemeVideo` being
extras is what makes the +37 request nearly free — and that
[audio-presentation.md](../plans/audio-presentation.md) has a stake, because jellyfin-web has
an open *theme song / theme videos volume adjustments* issue.

## 21. Sidecars: a three-way contradiction, and a promise that is conditional

Found by reading the decisions against each other rather than against the outside world.

- [D7](../../decisions/working-notes.md): *"Anything the user authored is mirrored to disk so
  it survives us."*
- [D24](../../decisions/working-notes.md): track-selection preferences *"are ours, not derived
  from the files, so they mirror to sidecars too."*
- [D77](../../decisions/working-notes.md) and [backup-restore.md](../plans/backup-restore.md),
  correctly: watch state *"must **not** go to sidecars: it is per-user, and writing it beside
  the media would expose one household member's viewing to anyone with filesystem access. The
  sidecar mechanism structurally cannot carry it."*

D77's argument is right and **it does not stop at watch state**. Track preferences are
per-user. So are favourites, ratings, presentation settings and the play log. D24 says the
opposite about the same class of data, and `backup-restore.md`'s own irreplaceable-set table
lists track preferences without noticing.

The rule that resolves it, and it is a good one to have out loud
([D98](../../decisions/working-notes.md)): **a sidecar carries what is true about the work; the
database carries what is true about a person.** The test is that *the media tree is shared* —
with the household, often with a grantee, sometimes with a seedbox. "This is actually the 1982
cut" belongs there. "Karl watched this at 2 a.m." does not.

**And the mechanism collides with two other decisions, which nobody had noticed.**
[principles §2](../../principles/README.md) mounts media **read-only by default**, and
[D33](../../decisions/working-notes.md) says the core **never touches a media filesystem**. So
a sidecar write needs an opt-in writable path — the same one
[D89](../../decisions/working-notes.md) needs for deletion — and must happen in the node.

Which makes the README's *"your metadata corrections are written back to disk so they survive
us"* **conditional, while reading as unconditional**. The honest version separates two
mechanisms doing two jobs: the automatic database backup ([D77](../../decisions/working-notes.md))
is the **durability** answer and is on by default; sidecars are the **portability** answer —
the part that actually means "survive us" — and they need the opt-in.

## 22. The core is not supposed to parse hostile bytes, and a poster is hostile bytes

[D26](../../decisions/working-notes.md) keeps FFmpeg out of the core because media is
attacker-supplied. That was written about media files. The tree already contains the premise
for the other case and never drew the conclusion —
[threat-model.md](threat-model.md) §5, verbatim:

> *"posters are the one binary we fetch **from a third party by default** — TMDB — rather than
> from the user's own disk."*

**TMDB is community-editable.** Anyone can upload a poster. So a provider image is
attacker-supplied in the ordinary sense, and unlike a film it arrives *unprompted*, during a
background refresh, from the internet, on a schedule — a better delivery vector than a film the
user chose to acquire.

The exploitability is already counted in our own research: **39 CISA KEV entries touch media,
image or font parsing**, with Apple's Image I/O and Samsung's `libimagecodec` (twice) in a
five-row sample. Add the one that hit everything — **CVE-2023-4863**, the libwebp
`BuildHuffmanTable` heap overflow, KEV-listed 2023-09-14, exploited in a 0-click chain, in a
library that ships inside Chrome, Electron, GIMP, LibreOffice, Telegram, 1Password *and
FFmpeg*.

So the rule generalises ([D99](../../decisions/working-notes.md)): **the core never parses a
media or image file.** Derivation happens in the node's jail — where
[artwork.md](../plans/artwork.md) already put it for performance reasons — a fetched provider
image is bytes in flight handed to the confined worker, and serving a derived image from
`cache/` is not parsing it. It is the shape Apple chose for BlastDoor, which
`threat-model.md` §5 already quotes approvingly for the other half of the problem.

## 23. A destructive command on a replay channel deletes the wrong film

Created by this audit's own [D89](../../decisions/working-notes.md), and caught by reading it
against [D38](../../decisions/working-notes.md) — which states the rule it breaks, in as many
words:

> *"A node that loses `observed_config` re-executes. Every command in the vocabulary must
> tolerate that, which they do — and any future command that cannot must not be added to this
> channel."*

`delete <path>` does not tolerate re-execution, and the failure is not the harmless one it
looks like. Replaying a delete after the file is gone is fine. Replaying it after **a different
file has appeared at the same path** — a re-rip, a rename, a torrent client reusing a name —
deletes the wrong film, silently, from a channel designed to be replayed.

[D100](../../decisions/working-notes.md): a destructive command carries the **identity** of
what it destroys, not only its location, and the node refuses and reports on a mismatch. The
identity set is the same data D89 already shows the user in the confirmation, so the thing
displayed and the thing checked cannot drift.

## 24. The intro detector needs library knowledge the node is forbidden to have

[D82](../../decisions/working-notes.md) puts segment detection in the node, correctly — it
decodes audio, and [D26](../../decisions/working-notes.md) keeps that out of the core. But the
detector that works finds **the segment repeated across the episodes of a season**, and that
fails [principles §9](../../principles/README.md)'s test outright: *could this component
determine it with no knowledge of the library?* No. "These files are episodes of one season" is
a conclusion the **core** reaches from parses [D59](../../decisions/working-notes.md) forbids
the node to make.

A node that groups files by itself has re-implemented the filename parser — the exact thing
D59 moved out.

[D101](../../decisions/working-notes.md) splits it along the line §9 already draws: the core
supplies **the set** ("compare these twelve files"), the node supplies **the measurement** ("a
91-second segment repeats in all twelve, at these offsets"). And the rule generalises to every
compare-these-files pass — perceptual-hash duplicate detection, cross-version alignment,
re-encode detection — which is why it is a decision and not a paragraph.

## 25. Nine passes over every file, and nobody added them up

[D33](../../decisions/working-notes.md) gave the node "everything requiring access to a media
file": discovery, probing, subtitle and font extraction, thumbnails and trickplay. Counting
what has been added since — including three from this audit:

enumerate · probe · content hash · subtitle extraction · font subsetting · thumbnails and
trickplay · **poster derivation** ([D99](../../decisions/working-notes.md)) · **loudness**
([D83](../../decisions/working-notes.md)) · **segment detection**
([D82](../../decisions/working-notes.md)) · overlay rendering
([D78](../../decisions/working-notes.md)) · *later* content-safety inspection
([D61](../../decisions/working-notes.md)).

Nine passes, several of them full decodes, on hardware whose honest low end is an 8 GB Celeron
NAS. **Each was added in isolation and each was individually cheap.** The two failure modes are
easy to predict and hard to retrofit: a first scan that takes a week, and an array that never
spins down ([D94](../../decisions/working-notes.md)).

[D102](../../decisions/working-notes.md) makes the pipeline a first-class object — passes
named, individually deferrable per library, separately reported, restartable, ordered by user
value. It also turns the user-facing question from *"is it scanning?"* into *"which passes have
finished?"*, which is what
[sentiment.md](sentiment.md)'s *"I can't tell what the scanner did"* is actually asking. And it
makes the total cost the most consequential unmeasured number in the project, because the first
scan is the first thing anyone sees.

## 26. There is nowhere to store a device preference, and the obvious fix is a trap

[D83](../../decisions/working-notes.md) makes dynamic-range compression per-device, because the
right value depends on the room. [D24](../../decisions/working-notes.md)'s preference table has
scopes of user, library and series. There is no device scope.

Adding one is how you get a device-profile database, which
[D21](../../decisions/working-notes.md) calls the incumbents' largest bug source — so the line
has to be drawn explicitly ([D103](../../decisions/working-notes.md)):

- a **capability** (what this device can decode) is declared per request and **never stored**,
  because it changes with an OS update and a stored copy is a stale one;
- a **preference** (what this device's owner wants in this room) is stored, keyed by device id,
  because it does not change by itself and losing it annoys people.

A preference is a fact about a person in a room. A capability is a fact about hardware, and
hardware lies (§14). Keeping them apart is what makes a device scope safe to add.

## 27. Nobody said who may join a Watch Together group

[watch-together.md](../plans/watch-together.md) says *"anyone in a group may play, pause and
seek"* and never says who may be in one. No invite, no join authorisation, no entitlement check
anywhere in the plan or the research, and its `Depends on` line does not name
[sharing-model.md](../plans/sharing-model.md).

**It fails open in the most natural implementation.** The point of the feature is watching with
someone outside your house, so the obvious build is a group link — an access path that routes
around [D76](../../decisions/working-notes.md)'s share predicate and
[D84](../../decisions/working-notes.md)'s maturity ceiling, both of which D76 requires to be
enforced *at every access path, not only at listing*, for exactly this reason.

[D104](../../decisions/working-notes-archive.md): **the group is not a grant** — every participant
resolves the item through their own entitlement, and a user who cannot see the film cannot see
the group ([principles §10](../../principles/README.md)). **The invite is a capability URL
scoped to one Edition**, which is mechanism (2) of the four already researched in
[remote-access.md](remote-access.md) §6, and the weakness named there —
*"unattributable for ongoing access"* — does not apply to a grant that is time-boxed to a
session.

The happy consequence: the feature that most needs an identity story needs the **cheapest** of
the four, so the motivating use case — a partner travelling, with no account — is answered
without the hosted-directory question being settled.

> **Superseded in part, 2026-09-20.** This document is a dated snapshot and is not rewritten,
> but a reader should not take the above as the current design. The *finding* stands — nobody
> had said who may join, and it failed open. The *answer* was overturned by the project owner
> in [D117](../../decisions/working-notes.md): **the session link is the grant**, with no
> per-participant entitlement resolution at all, because "a griefer who gets hold of a link is
> a revocation problem, not an authorisation problem" and requiring the other person to have
> an account first is exactly the friction the feature exists to avoid. What replaces the
> entitlement check is revocation, and it was then sharpened three more times: a link admits
> while a **membership** persists, so rotation is seamless and ejection is owner-only
> ([D119](../../decisions/working-notes.md)); the cap counts **people**
> ([D120](../../decisions/working-notes.md)); and "scoped to one Edition" was retired outright
> ([D122](../../decisions/working-notes.md)) — the session is the object, what plays is
> mutable state on it, and the bound on a leaked link is that a guest sees *the current
> playback* rather than anything enumerable. See
> [watch-together.md](../plans/watch-together.md).

**And one smaller thing in the same plan.** A user's playback rate and the reconciler's drift
nudge are the same knob. A participant at 1.25× is not drifting, so rate is group state and the
effective rate is group × nudge; and since `setRate` is optional in the six-method surface, a
group stays at 1.0 unless every participant can honour a change.

## 28. The Jellyfin adapter has no stated identity, and the convenient answer is a confused deputy

[D15](../../decisions/working-notes.md) gives an out-of-process adapter *"its own auth, its own
websockets and its own route namespace"*. [jellyfin-api-shim.md](../plans/jellyfin-api-shim.md)
inherits that and never says what the adapter authenticates **to the core** as. There is one
convenient answer — a single privileged token configured at install — and it defeats every
access control in the project: [D76](../../decisions/working-notes.md)'s share predicate,
[D84](../../decisions/working-notes.md)'s maturity ceiling,
[D104](../../decisions/working-notes-archive.md)'s group rule. Worse, the core sees a legitimate owner
request, so nothing fires.

[D105](../../decisions/working-notes.md): the adapter is a **login proxy, not a principal**.
It forwards credentials, the core authenticates, and it holds a token scoped to that user for
that session. Entitlement is resolved once, by the core, in the place it is already resolved —
so the adapter cannot get it wrong because it never computes it. The rule generalises to every
tier-2 surface, including the OpenSubsonic adapter in Phase 7 and DLNA, which has no user
concept at all and therefore must be configured to act as one explicitly chosen user rather
than as the owner by default.

## 29. Play state cannot survive a protocol that has no sequence number

[D81](../../decisions/working-notes.md)'s guard is a monotonic sequence. Jellyfin's progress
API has no such field and neither will OpenSubsonic's, so the obvious implementation — treat
"no sequence" as "newest" — reinstates last-writer-wins for precisely the clients most likely
to be somebody's second device.

[D106](../../decisions/working-notes.md): the adapter **mints** the sequence per
`(user, device)`. The guard's property survives within a device; between two adapter-driven
devices there is nothing to order by but arrival, which is the ceiling of the adapted protocol
and belongs in the adapter's documentation — because the symptom, a phone occasionally
rewinding a television, is otherwise indistinguishable from the bug D81 exists to prevent.

The same document should record how four levels flatten into Jellyfin's one, which is forced:
Edition → item, Version → "alternate version", multi-part File set → `AdditionalParts`.
Jellyfin's own vocabulary, used for what [D79](../../decisions/working-notes.md) says it was
reaching for.

## 30. The preferred node transport has no security model

[D35](../../decisions/working-notes.md) states the file transport's exactly and well —
*"the permissions split **is** the security model"*, with a table that doubles as the node's
Landlock ruleset. It then says *"where HTTP exists, prefer it"*, and **says nothing about what
authenticates either end of the preferred transport.**

The framing is what hid it. The node is consistently described as the *less* trusted half —
correctly; it handles hostile media — so all the attention went to what a bad node can inject.
But `config.json` flows the other way, it carries a command list, and since
[D89](../../decisions/working-notes.md) it carries **deletion**. **A spoofed core is worse
than a spoofed node**, and nobody had looked in that direction.

[D107](../../decisions/working-notes.md): mutual authentication with enrolment as a deliberate
human act, reusing [D93](../../decisions/working-notes.md)'s pairing rather than inventing a
second mechanism — and **a node's roots are local configuration the core cannot add to**. The
command vocabulary already names roots by identifier rather than path, so this makes a rule of
what was already the shape. The reasoning is the tree's own, applied one level out: the
directory table *is* the Landlock ruleset, and a Landlock ruleset is declared at startup and
cannot be widened at runtime. Without it, a compromised core turns every node into an arbitrary
filesystem enumerator reporting over the network, on the machine that by design can read
everything.

## 31. Plex's own forum was reachable all along, and it says something different

The original sentiment round recorded Reddit as unreachable and worked from Hacker News,
GitHub and Lemmy. It did not try **`forums.plex.tv`**, which runs Discourse and whose JSON API
answers this network — `/top.json`, `/search.json`, `/t/<id>.json`, all of it. That is the
first-hand Plex-user source the Reddit gap was standing in for, and it **partly contradicts our
own conclusion.**

[sentiment.md](sentiment.md) says Plex's problem is *"commercial, not technical"*. On Plex's
own forum, sorted by likes over the year:

| Likes | Posts | Topic |
| --- | --- | --- |
| **1,124** | 304 | *Vote to roll back to Plex Classic!* |
| 937 | 443 | *Elephant in the room. Lifetime Plex Pass* |
| 502 | 250 | *Playback Error on Samsung TV* |
| 325 | 106 | *How do I get the old experience back?* |

**The loudest complaint of the year is a UI redesign users cannot revert**, not the price —
and the theme recurs under at least eight further titles. Plex partially reverted in August
2026 after, in their own announcement's words, *"consistent feedback from the start"* over
about a year; the forum's verdict, in a thread titled *Why did you cave?*, is *"too little too
late."*

**The second theme is absent from our tree entirely: a client update that breaks a platform,
with no way back.** *"I just reverted to the old version and turned off updates."* *"Please
tell me how to revert to the previous Plex on Fire TV!"* Enough people needed it that a pinned
rollback-instructions thread exists, and a separate one organises users to petition **Vizio**,
because the television vendor is the only party who can un-ship an update.

[D108](../../decisions/working-notes.md) takes both: a layout change is opt-in with the
previous one reachable for a release, and **every client release is published as a directly
installable artefact with old versions kept up**. The second is nearly free on Android and
Android TV, where [tv-client.md](../plans/tv-client.md) already treats sideloading as a
*distribution* advantage — it is a **rollback** advantage too, and that is the more valuable
one. It composes with [D85](../../decisions/working-notes.md): a compatibility contract lets an
old client keep working; a published artefact lets a user get back to one.

**And the forum confirms, first-hand, seven things this audit had already decided from other
evidence** — *Add Watch Together to New Plex Experience* (350 posts), *Let's finally solve the
low audio issue please* (141), *Option for semi-persistent automatic skip intro* (125), two
parental-controls threads including one asking in effect for a predicate language, a subtitle
thread requesting *"a slider with size %"* which is 47 CFR §79.103's 50–200% written by someone
who has never heard of it, and *Plex NFO Agent Forum Preview* at **506 posts**, which is
[D98](../../decisions/working-notes.md)'s portability argument arriving from the other
direction.

## 32. Smaller notes, recorded rather than decided

- **Playback speed** (streamyfin +10; a webOS "no sound above 1×" bug) interacts with
  [D66](../../decisions/working-notes.md): a participant at 1.25× is not drifting, and the
  Watch Together reconciler must not fight them. Rate is part of the shared state or it is
  explicitly local; there is no third option.
- **Sleep timer** (streamyfin +6) is trivial in the client and changes the play-event stream:
  it produces `abandoned`, not `completed` (§3).
- **mTLS / client certificates** (findroid +28) is a reasonable option to name in
  `remote-access.md` for the technical user, alongside the VPN answer we already reject for
  families.
- **IPv6-only installs** break Jellyfin in two open issues (*Fresh install unreachable on IPv6
  single-stack*, *Metadata fetch timeout — IPv6 connectivity broken*). A test-matrix row.
- **A full library scan must never destroy user-authored data** — Jellyfin's *All Library Scan
  causes playlists to disappear* has 50 comments. We are structurally safe
  ([D7](../../decisions/working-notes.md), sidecars, the change journal), which means it costs
  one fixture assertion to stay safe, and nothing to find out the hard way.
- **Dual subtitles** (androidtv +33) — already covered: [D24](../../decisions/working-notes.md)
  models the subtitle selection as a **set**. Recorded as a hit.
- **"Force direct play" / "force transcode"** (+49 / +21) — already covered by
  [D4](../../decisions/working-notes.md) and principles §3. Recorded as a hit.

## 33. What holds up

Most of this document is correction, so the checks that passed are worth recording.

- **The four-level model** ([D79](../../decisions/working-notes.md)) survives everything above.
  Segments, play state and loudness all landed at a *specific* level without strain, which is
  the test of a level model — and the one place it was short (multi-part positions, §3) is a
  clarification, not a fifth level.
- **The predicate language** ([D75](../../decisions/working-notes.md)) absorbed a fifth binding
  (parental controls) with no change. Two of the biggest gaps in this audit cost almost nothing
  because it exists.
- **Sensors report, the core decides** ([D42](../../decisions/working-notes.md), §9) put the
  loudness measurement, the segment detection input and the play event in the right place
  without argument each time.
- **SQLite** ([D31](../../decisions/working-notes.md)) survives the added write load: the play
  log is the only new high-rate writer, at the same ~2 writes/second the reconsideration already
  budgeted, and it is append-only, which is the cheapest thing SQLite does.
- **The database is a rebuildable index** ([D7](../../decisions/working-notes.md)) held every
  time it was tested here. Every new table above is either derived (segments, loudness, sort
  keys) or user-authored and mirrored (preferences, overrides, play state).
- **No DRM, no household verification, no device counting** — re-checked against Netflix's
  apparatus in [sharing-model.md](sharing-model.md) and still correct for the same reason: they
  license per household and we license nothing.
