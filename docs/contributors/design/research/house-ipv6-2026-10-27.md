> **ABOUTME:** How a core with no IPv6 of its own (an IPv4-only container behind DS-Lite or carrier
> NAT) can let its discovery recognise the house's devices, which ask over the house's IPv6 /64:
> every way the core could learn that /64, what each trusts, what a wrong one grants, how others
> judge "local", and the recommendation behind D356's proposal. 2026-10-27.

# The house's IPv6 network, for a core that has none

- **Date:** 2026-10-27, after [local-path-2026-10-27.md](local-path-2026-10-27.md) (cause 3,
  option D). The owner approved the direction the same day: *"the core tells the discovery the
  house's IPv6 network so an IPv4-only core can recognise devices at home"*, noting that it amends
  D290 §2. **Feeds** [D356](../../decisions/working-notes.md) (proposed).
- **Method:** read-only. Orpheum's `cmd/orpheum` (config), `internal/core/api/home_network.go`,
  `internal/core/rtcapi/own_network.go`, `internal/core/discovery`, `discovery/`,
  `internal/deployment` (the install script and the compose file), and the sibling repository
  `orpheum-connect` (`internal/clients/athome.go`, `clients.go`, `offers.go`,
  `internal/store/heartbeat.go`, `docs/spec.md` §6). Web searches for how others judge "local".
- **Labels:** **[C]** read in the code or config; **[W]** from the web (a forum post is marked as
  one); **[I]** inference.

---

## 1. The gap, exactly

The discovery's `isAtHome` (`orpheum-connect/internal/clients/athome.go`) says a client is at home
when its address shares a public IPv6 /64 with the heartbeat's source or with one of the core's
public IPv6 candidates, or is a public IPv4 that the probe reached and that is the household's own
(interface, configured, or mapped by UPnP or NAT-PMP, never PCP) **[C]**. A core whose heartbeat
leaves over IPv4, behind DS-Lite or carrier NAT, offers it nothing to match: its source is the
carrier's shared address, and it has no IPv6 candidate. The house's devices ask over IPv6, from the
house's /64, and are never offered the LAN name.

Which cores are affected **[C, I]**:

| Install | Heartbeat over IPv6? | Why |
| --- | --- | --- |
| Orpheum's own compose, host with working IPv6 | yes | the `outside` network has `enable_ipv6` and a private /64 Docker translates on the way out, so the heartbeat comes from the host's global address, in the house's /64 (nas.example works so, 2026-10-20) |
| Orpheum's compose, host without IPv6, or with an address but no route (`accept_ra` not 2 while Docker forwards) | **no** | the install script reports both cases and how to fix them, but does not insist |
| A Docker install of someone else's making (Unraid, Synology, a hand-written compose on the default bridge) | **no**, usually | Docker's default bridge has no IPv6 |
| Bare metal with IPv6 | yes | its own address |
| Bare metal, IPv6 off (a NAS with IPv6 disabled, a Proxmox container without SLAAC) | **no** | |
| Staging (the yoloAI sandbox) | **no** | the sandbox has no IPv6 at all; `eth0` is IPv4 only |

A house with no IPv6 at all is not affected: its devices ask over the shared IPv4 too, and nothing
can tell households apart on it.

## 2. How others judge "local" **[W]**

- **Plex** judges local by the source address against its `LAN Networks` setting, or, with that
  empty, against the server's interface subnets. Plex staff: the setting "completely takes over for
  determination of Local vs Remote" and "currently only works for v4 addresses", so with it set
  every IPv6 client is remote; with it empty, IPv6 is local only by a link-local address
  ([Plex forum: Plex not honoring IPv6 traffic as local](https://forums.plex.tv/t/plex-not-honoring-ipv6-traffic-as-local/641837)).
  DS-Lite users have complained since 2012–2013 that Plex speaks IPv4 for remote access
  ([Plex forum: DS-Lite remote access](https://forums.plex.tv/t/solved-secure-remote-access-with-ipv6-dual-stack-lite-no-public-ipv4/633997)).
  plex.tv does not judge local for its clients; it hands out every address of the server under
  `plex.direct` and the client races them
  ([Plex: why can't the app find or connect](https://support.plex.tv/articles/204604227-why-can-t-the-plex-app-find-or-connect-to-my-plex-media-server/)).
  Plex has no answer to this gap: it never matches across families.
- **Jellyfin** judges local by `LocalNetworkSubnets`, defaulting to the RFC private ranges
  (RFC 1918, ULA, link-local); a house's public IPv6 /64 is remote unless the admin names it, and an
  admin who names it loses it when the provider moves the prefix. The reporter: *"because the prefix
  changes somewhat regularly by my ISP … I might lose access at some point again."* The issue was
  closed as not planned
  ([jellyfin#14189](https://github.com/jellyfin/jellyfin/issues/14189)). This is option (a)'s
  failure, measured by users.
- **Tailscale** does not judge local at all: peers exchange every endpoint they know (interfaces,
  port maps, STUN's, static ones) through the coordination server and let their own pings choose,
  so a LAN pair wins on a LAN by working. The LAN addresses' disclosure to peers elsewhere is
  discussed as a privacy cost, with mDNS names proposed in its place
  ([tailscale#1252](https://github.com/tailscale/tailscale/issues/1252);
  [endpoint discovery](https://deepwiki.com/tailscale/tailscale/4.3-endpoint-discovery-and-nat-traversal),
  a third-party summary). Tailscale can afford to try everything because its clients are native:
  no browser asks permission before a LAN address. A page at a public origin cannot (Chrome's Local
  Network Access prompt, whose "Block" holds for the whole origin, every household's; discovery
  protocol §3.2).
- **What the three share:** the evidence a device is local is the path it actually reached the
  server by. Orpheum's core already judges home so (D297 §6, D300 §3). Only the discovery has to
  guess before a path exists, and a guess is the one thing the others do not make across families.
- **Prefixes move.** Deutsche Telekom has moved its customers' /64 and delegated /56 every night
  since 2023-10-10, where before it was two or three times a month
  ([Telekom hilft: IPv6 und das sich ändernde Präfix](https://telekomhilft.telekom.de/t5/Telefonie-Internet/IPV6-und-das-sich-aendernde-Praefix/td-p/5432647),
  a customer forum; [v64.tech forum](https://v64.tech/t/fragen-zur-umstellung-auf-ipv6-u-a-statisch-vs-dynamisch/3947)).
  German DSL in general gives a new prefix with each forced reconnection
  ([kuerbis.org](https://www.kuerbis.org/2023/03/ipv6-im-heimnetz-mit-pfsense-und-dynamischer-prefix-delegation-teil-1/)).
  Any mechanism must notice a new prefix within a day without an admin.

## 3. The mechanisms

What a wrong network grants, whichever mechanism made it: a device in it that holds the core's
locator (a household member, a Watch Together guest) is offered the LAN name, and Chrome may ask it
for the local-network permission; nothing else. The discovery's judgement orders paths (D290 §2); the
core alone grants admin, from the path a request actually took (D297 §6, D300 §3, D302). A stranger
without a locator gets no paths at all. The LAN name itself is in the public zone already.

### (a) The admin configures it

A `[discovery]` key naming the house's public /64s, sent to the discovery as configured.

- **Staging:** works (the admin types the house's /64). **Docker on a NAS:** works. **Bare
  metal:** works.
- **Trusts:** the admin. **Stranger:** cannot set it; only the core's authenticated heartbeat
  carries it.
- **Prefix change:** not noticed. Stale every night at Telekom, as Jellyfin's users found. A stale
  network names someone else's household after the provider reuses it; harmless here, since none of
  them holds the locator, but the house's own devices lose the LAN name.
- **Verdict:** a fallback for a house whose devices cannot prove themselves (below), not the answer.

### (b) The deployment reads it from the host

The install script (`internal/deployment/templates/install.sh`) already reads the host's LAN address
and reports its IPv6; it could write the host's global /64 into the config.

- **Staging:** fails (no IPv6 anywhere). **Docker on a NAS:** works only where the host has IPv6,
  which is where Orpheum's own compose already sends the heartbeat over IPv6. **Bare metal:** same.
- **Prefix change:** the script runs at install and update, not nightly; stale as (a).
- **Verdict:** helps only third-party Docker installs on IPv6 hosts, and goes stale. Rejected.

### (c) A STUN binding over IPv6 from the host's network

A helper in the host's network namespace (a `network_mode: host` sidecar) asks a STUN server over
IPv6 and reports the address seen.

- **Staging:** fails. **Docker on a NAS:** works where the host has IPv6; Orpheum's own compose
  already covers that case. **Bare metal:** the core is on the host; its own candidates cover it.
- **Prefix change:** noticed at each binding.
- **Cost:** a second container with the host's network, for a case the compose file already solves.
- **Verdict:** rejected.

### (d) Learnt from a device the core has proven at home

When a WebRTC connection made through the discovery is from home by D300 §3 (its selected pair is
direct, and the client's end of it is in the home networks, as the core's own end says), the device
is in the house by the strongest evidence the core trusts. The device's offer reached the discovery
over HTTPS from some source address, which the discovery saw. If that source was a public IPv6, its
/64 is the house's.

The binding needs one fact to cross: the discovery knows the source, the core knows the pair. Three
ways to join them **[I]**:

1. **The discovery passes the offer's source network to the core with the offer** (a field on the
   signalling message), the core keeps it beside the connection, and when the connection proves
   home the core adds the network to its heartbeat. Nothing a page says counts; the core sees
   nothing new (the offer's own candidates already carry the device's public addresses); the
   network rides the heartbeat, where the configured fallback rides too; the core can show it on
   its System page. **Recommended.**
2. The core tells the discovery "offer X was at home", and the discovery, having kept each offer's
   source for a minute or two, stores the network. Same trust; the knowledge stays at the discovery
   only, so the core cannot show it, and the configured fallback needs a second route.
3. The core gives the page a signed, short-lived witness, which the page posts to the discovery
   from its own address. Same trust, but a bearer token can be carried to another network within
   its life, and it adds a client endpoint.

- **Staging:** works once the core's UDP port is published into the sandbox (local-path option
  A1); today no direct pair forms there, so nothing is learnt. **Docker on a NAS:** works wherever
  the house's WebRTC LAN pair works (D300 §1; D354 warns when it does not). **Bare metal:** works.
- **Trusts:** the core's own judgement of the pair (D300 §3), and the discovery's own observation of
  the offer's source; never the page.
- **Stranger:** cannot make a direct pair into the house's networks: an offer through a discovery
  never makes the core send a check into its own networks, and it answers only a check that arrives
  from them (D300 §2). A household member can teach a wrong network: a device on a VPN that keeps
  LAN access (the offer leaves through the VPN, the pair stays on the LAN) teaches the VPN's exit
  /64. The harm is the bounded one above, to that household's own locator holders in that /64.
  iCloud Private Relay, if it covers Safari's HTTP but not its WebRTC, is this case **[I, unverified]**; Safari
  races the LAN name always anyway (discovery protocol §3.2).
- **Prefix change:** the first device that connects from home after the move teaches the new one.
  Every first reach is WebRTC through the discovery (D274), so this happens on the first use after
  the move, with no admin. Until then, devices get no LAN name, which is today's behaviour.
- **Corroboration, not required [I]:** the device's own IPv6 server-reflexive candidate in its
  offer, where a browser sends one, should be in the same /64; a mismatch says a VPN or relay.
  Browsers hide host candidates behind mDNS names and may drop a reflexive candidate equal to the
  host's, so its absence proves nothing. Worth logging, not gating on, until a device shows how
  often it is present.

### (e) Router advertisements on the LAN

Listening for the router's RAs gives the on-link prefix.

- Needs the host's network namespace and a raw socket (CAP_NET_RAW), and IPv6 enabled on the
  interface, where the host's own address (and Orpheum's compose's heartbeat) already covers it.
  Fails on staging, and in a container on a bridge, which sees no RA. Rejected.

### Also rejected

- **The page's word** (a page reporting its `clientPrefix` and "my pair was host to host"): D300 §3,
  nothing a page sends counts. A stranger holding a locator could plant their own network.
- **A hairpinned pair as evidence** (D354): its address is the carrier's, many households'
  (D354 §4).
- **Accepting a shared IPv4 match:** local-path §5.4's "not recommended" stands.

## 4. What the discovery holds, and the privacy cost

The discovery already holds, per core, the last heartbeat (`core.heartbeat`, with its source,
`store.Heartbeat.Source`) as the current value only, and its spec's §6 lists "Current addresses
(personal data: home IP addresses)" as kept current only, past values only in backups **[C]**. Its
request logs, kept 7 days, already carry each client's /64 (`a core's paths were asked for …
client=<prefix>`).

For a dual-stack core the heartbeat's source already names the house's /64, so the house networks
add nothing new. For a DS-Lite or carrier-NAT household with an IPv4-only core they are new: today
the discovery holds only a shared IPv4 for it, which identifies a carrier's pool, not a household.
The cost is that the discovery's database ties one account's core to a household's current
connection, as it already does for every dual-stack core. Kept as the heartbeat is: current value
only, replaced by each heartbeat, deleted when the core is released; never written to the zone,
never returned to a client (a client is told only its own `clientPrefix`), and logged as the
existing `/64`-level line already logs.

## 5. Recommendation

(d)1 as the mechanism, (a) as the fallback for a house whose devices cannot make a direct pair, the
match in `discovery/discoveryproto` so both discoveries and Orpheum's tests share it, and nothing on
the core's side that counts a house network as home. D356 states it, with the owner's questions.
