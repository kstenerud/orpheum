# The core–node link: the owner's model against practice (2026-09-30)

The readiness audit before Phase 4 ([audit-2026-09-30](audit-2026-09-30.md)) found the link
between core and node open exactly where it is hard, and the round trip written five times. Asked
how the two talk today, the owner proposed a different shape: *"It should be the core that drives
the node. The node drives only the hello … From then on, the core drives everything."* This note
checks that model against the systems it resembles and records what the discussion added.

## 1. How it works today

The node dials the core over a Unix socket and drives most of the exchange: a hello, an endless
JSONL report stream (scan records and a status record every few seconds, which is also the
heartbeat), a long-poll that returns commands, and a POST per job kind for answers, retried for
five minutes and then dropped. The core reads file bytes from the node's own socket. In the core, a
job sent to a node is a goroutine blocked on its answer with a real-clock silence timer, written
five times (prepare, loudness, subtitle extraction, fetched-subtitle conversion, artwork).
Everything in flight is in memory on both sides: a core restart loses the waiting goroutines and
the queued commands, a dropped session cancels the node's work, and a late answer from an earlier
attempt cannot be told from the current one.

## 2. The model

1. The node says hello: who it is and a summary of its state. The core acknowledges.
2. From then on the core drives. It asks the node for detail, squares it with what it believes the
   node holds, and brings both into agreement.
3. The core issues jobs with an id and limits. The node keeps a durable record of its jobs,
   schedules them itself within the core's priorities, and accepts updates and cancels.
4. The node runs its own jobs to the end, keeps them from getting stuck, handles what failures it
   can, and reports what it cannot.
5. A finished job's result is posted to the core: the data itself, or a reference the core can
   reach. Finished results are kept long enough that an extended absence loses nothing, bounded by
   the cache cleanup.
6. The core can ask at any time for the node's pending and finished jobs, to repair any drift.
7. The core never blocks on a node. A job is pending; whatever depends on it waits, with a
   timeout, for its resolution: finished, failed, timed out, cancelled, or blocked by the
   infrastructure.

## 3. Against practice

The model is the shape of the coordinator–agent systems that have been run at scale:

- **Kubernetes (control plane and kubelet).** The control plane holds the desired state; the agent
  on each machine reconciles it and reports what it observes. Correctness comes from comparing
  whole state periodically ("level-triggered"), so a lost or duplicated message only delays. A
  generation number on the desired state, echoed by the agent as the one it last applied, shows at
  once what the agent has not yet taken.
- **HashiCorp Nomad (servers and clients).** Each client keeps its allocations in a local database
  and restores them after its own restart; the servers track which client holds what.
- **Build agents (Buildkite, GitHub's self-hosted runners).** The agent dials out and holds the
  connection, so it works behind NAT; the server decides the work.
- **Temporal (durable workflows).** A task's time limits are distinct: schedule-to-close (the whole
  deadline), start-to-close, and a heartbeat timeout that detects a silent worker. Progress rides
  on the heartbeat.
- **The transactional outbox and the idempotent consumer.** A result is kept until acknowledged and
  may arrive twice; the receiver deduplicates by identity. A fencing token (the attempt number)
  lets the receiver refuse a stale writer.

Where the model matches: one side decides and the other reports; the agent's state is durable and
survives its restart; the agent schedules within the coordinator's priorities; periodic whole-state
comparison is the correctness path; the coordinator never blocks on an agent.

## 4. What the discussion settled (the owner, 2026-09-30)

1. **Who dials is not who decides.** The node keeps dialling the core (D127): a remote node on the
   owner's network (DS-Lite, no public IPv4) is often unreachable from the core. Over the
   connection the node holds, the core sends requests and the node answers them, each matched by
   id. The long-poll today is a crude form of this return channel.
2. **Pushes for speed, checks for correctness.** The node tells the core as things happen; the
   core's watchdog asks when it has not heard what it expected. Neither alone is enough, and the
   push can be lost without losing anything.
3. **Progress is a stream of best-effort updates; a finish is acknowledged.** The owner's shape:
   *"U, U, U, F, U, U, U, F"*. An update carries where the job is, from the same watchdog position
   stall detection reads; it needs no acknowledgement, the newest supersedes the rest, and it is
   throttled. A finish carries the result inline when small and a reference when large, and is
   kept and resent until the core acknowledges it. If a node with an assigned job is silent for a
   few update intervals, the core asks it what is happening; no answer means the node is
   unreachable and its work parks. An idle node sends nothing, and the core's periodic check,
   on its own schedule, is the liveness signal.
4. **No lease: the node finishes its work whether or not the core is there.** Finished work costs
   nothing but disk, which the cache cleanup bounds: unacknowledged results are evicted oldest
   first under pressure, and since all of it is regenerable (D231), the core re-issues what it
   still wants. A core that returns changed (a new core, a discarded cache.db, a deleted library)
   tells the node, at its first check, to drop jobs it does not know.
5. **A reference is an optimisation on a node-served address.** The core can always fetch a result
   from the node's byte socket and check it by hash; when the node also names a path the core's
   own mount shows with the same content, the core may read it there.
6. **What else it needs**, all agreed:
   - a job id and attempt number on every job, result and cancel (fencing; S27);
   - a generation number on each node's desired jobs, echoed back;
   - a window: the core gives a node a little work beyond its free slots and keeps global
     priority, the node orders what it holds, and "update a job" includes its priority;
   - a node whose disk is full refuses new work, a balk with its reason;
   - a job running when the node restarted is run again or reported interrupted, never lost;
   - the node's own hang is the service manager's to restart (a systemd watchdog); the core only
     reports a node that does not answer;
   - the three failure sources (the item, the tool, the infrastructure) in the protocol, so each
     is charged where D233 §6 says;
   - a protocol number and capabilities in the hello;
   - node authentication (a node key or mutual TLS bound to its name) before any node is remote;
   - a scan as an ordinary job whose result is a record stream the core reads from an offset,
     which retires the report stream as a mechanism of its own;
   - a `node.db` for the journal, with its own schema versions;
   - a deterministic simulation on a fake clock that drops, duplicates, reorders and delays
     messages and restarts either side at chosen points.

## 5. Against D233, clause by clause

| D233 | The model |
| --- | --- |
| §2 the node's lifetime is its own | Kept; the service manager also restarts a hung node |
| §3 an outbox numbered as the report stream; results by identity; attempt tokens; a core run id | The outbox becomes the node's job journal; finishes are acknowledged; identity and attempts kept; the report stream retires into scan jobs |
| §4 reconciliation at hello; "awaiting hello" | Kept, and generalised: the core may reconcile at any time, not only at hello |
| §5 watchdogs; a core lease renewed by movement | The node's watchdog kept; the core's lease becomes its expectation of updates, with a question when they stop |
| §6 three failure sources | Kept, carried in the protocol |
| §7 claiming respects each node's slots; wanted until | Slots are the node's to schedule; the core keeps a window per node and global priority; wanted until kept |
| §8 what is shown | Kept |
| §9 protocol number | Kept, with capabilities |

What the model removes from the plan: the five waiting loops, `runnerPool` and slot counting in the
core. The core's queue gains a state for work assigned to a node, which the checks keep true.
