# FFmpeg reading through the node's byte path, 2026-10-22

**What prompted it.** [D329](../../decisions/working-notes.md#d329--work-is-scheduled-from-wants-each-resource-is-decided-next-to-it-playback-is-admitted-and-long-work-is-cut-into-pieces)
§7 and [work-scheduling.md](../plans/work-scheduling.md) §8.1. The owner: *"Yes, test this and then
we decide based on the results."*

**How it was done.**
- A Go harness, kept outside the tree under `.git/spikes/ffhttp/`, served files from a loopback HTTP
  server with Range support. The server counted requests and bytes. It could also withhold its next
  bytes (a gate) and pace its reads.
- The harness ran each of the node's command shapes, with their arguments copied from the node's
  code, twice: once with today's `-protocol_whitelist file -i file:` and once with
  `-protocol_whitelist http,tcp -multiple_requests 1 -rw_timeout … -i http://127.0.0.1:…/`.
- It compared the outputs byte for byte, and loudness by value.
- The tools were the pinned jellyfin-ffmpeg 8.1.2 (`make ffmpeg`) in the dev container.
- **The media was synthetic**, generated by FFmpeg: no real library was touched.
  - **`film.mkv`:** 5 min, 1080p H.264 at 8 Mb/s, a 5.1 AAC track, a stereo AAC track and an SRT
    track, 315 MB.
  - **`film-moov-at-end.mp4`:** the same remuxed to MP4 without faststart, so its index is at the
    end.
  - **`heavy.mkv`:** 2 min at 80 Mb/s, a 4K remux's rate, 1.2 GB.
- Files were read from the page cache, so the times compare the two paths, not the disk.

## Results

| Command shape (the node's) | Output over HTTP | File / HTTP time | Read over HTTP |
| --- | --- | --- | --- |
| Probe (examine): `ffprobe -show_format -show_streams -show_chapters` | Identical JSON (filename aside) | 0.04 / 0.06 s | MKV 3.5 MB in 1 request; MP4 with its index at the end 0.8 MB in 3 requests (start, end, start) |
| Read-through: 5.1 loudness as is and as the stereo mix, plus the framecrc timeline | Identical: the framecrc is byte-equal, and loudness −22.4 and −16.3 LUFS on both | 9.1 / 11.9 s MKV; 11.4 / 12.0 s MP4 | The whole file, once |
| Embedded subtitle extraction as ASS | Identical | 0.15 / 0.90 s | The whole file |
| Chunk: seek to 2:30, copy 6 s of picture | Identical framemd5 | 0.06 / 0.08 s | 7.6–11.1 MB in 4 requests: the seek fetches only what it needs |
| Chunk: seek to 2:30, encode 6 s | Same | 2.9 / 2.7 s | 14–15 MB |
| Remux of the 80 Mb/s file to null | Same | 0.80 / 3.61 s: 1,502 MB/s against **333 MB/s** | Whole file; CPU 0.85 s against 2.70 s |

**Pausing between pieces works.** The server withheld its next bytes for 15 s at 40% of the film.
FFmpeg waited, used **10 ms of CPU** in those 15 s, then finished with the same loudness. Holding
back an answer is all that pausing needs. SIGSTOP isn't needed.

**A dead source can be killed at once.** SIGKILL ended an FFmpeg waiting on a silent source in
**3 ms**. It waits on a socket, never in the kernel on a share. That is the virtiofs and NFS problem
(D233 §10) gone for FFmpeg.

**A dead source that FFmpeg gives up on is reported as a success unless `-xerror` is given.** With
the source silent after 20%, FFmpeg logged `Read error` and `Error during demuxing: Input/output
error`, printed the loudness of the 20% it had read (−34.8 LUFS), and **exited 0**. With `-xerror`
it exits 251. `-reconnect 0` and `-err_detect explode` change nothing. With `-rw_timeout` at 5 s it
gave up about 38 s after the source fell silent, after its own retries.

## What it means

1. **FFmpeg reads correctly through the byte path for everything the node does.** Every output was
   identical, and seeks fetch only the ranges they need, including an MP4 whose index sits at its
   end.
2. **Throughput is ample.** The loopback path ran at 333–395 MB/s: about 3 times a NAS on 1 Gb/s,
   and about 30 times a 4K remux's real-time rate.
   - It costs about **1.6 CPU-seconds per GB** more than reading the file: about 30 s of CPU for a
     20 GB film's read-through.
   - That is small beside the decode, and Background work pays it.
   - The Go side of the harness was a plain `http.ServeContent`. The node's server can do better
     with larger writes.
3. **The node, not FFmpeg's exit status, decides whether a read finished.**
   - The byte path knows whether it served the file to its end. A run whose source didn't is failed
     by the node, whatever FFmpeg says.
   - A run whose log has FFmpeg's `Error during demuxing: Input/output error` is failed too.
   - **`-xerror` is not the fix** (a second test, below). It makes every error fatal, and a damaged
     frame that FFmpeg conceals today would fail the whole run.
   - The node doesn't rely on `-rw_timeout`. It closes the connection itself when its diskwatch gate
     declares the place stalled, and FFmpeg then errors at once.
4. **The defect in today's file reads, very likely.** The same "error during demuxing, exit 0"
   behaviour belongs to FFmpeg's demuxer, not to the HTTP protocol. So a read error mid-film on a
   soft NFS mount (EIO) very likely ends today's read-through or extraction with **a measurement of
   part of the film, reported as complete**. It wasn't reproduced on a real share here: simulating
   EIO on a file needs a device-mapper or FUSE fault. The fix is to treat the demuxer's I/O error in
   the log as a failure of the run. It is recorded as phase 1's first step.
5. **Confinement.** Today FFmpeg is confined to the `file` protocol and Landlock read access to the
   one file (cut-a §7).
   - With HTTP input it needs `http,tcp` only. The URL is the node's own, and a filename never
     reaches it.
   - Landlock's network rules (ABI 4, Linux 6.7 and later) can restrict FFmpeg to connecting to the
     node's one loopback port. On an older kernel, the URL's per-run token is the guard: the byte
     path serves only the file that run was given.
   - FFmpeg then needs no read access to media at all.

## A second test: `-xerror` on a damaged film

Damage was written into `film.mkv`: 4 KB of random bytes at every 5% of the file. The same runs
followed, without and with `-xerror`:

| Run | Without `-xerror` | With `-xerror` |
| --- | --- | --- |
| Loudness of the 5.1 track | exit 0, −16.3 LUFS; the demuxer resynchronised past the damage | exit 0, the same |
| Decoding the picture (as an encode does) | exit 0; 61 lines of errors, the damaged frames concealed | **exit 183** at the first damaged frame |

A real film with a few damaged frames plays and encodes today, with a glitch. Under `-xerror` its
prepare and its chunks would fail. So the fix fails a run on the I/O error alone, not on every
error.

## Recommendation

**Take §8.1:** FFmpeg reads media only through the node's byte path. The test found no blocker,
and it confirmed the gains the design relies on:
- pieces by withholding answers;
- a kill that always works;
- reads the scheduler sees and paces;
- one read that can be shared.

Two conditions come with it:
- **Success judged by the byte path, and by the demuxer's I/O error in the log**, not by FFmpeg's
  exit status and not with `-xerror`. The fix for the log line lands first, for today's file reads
  too.
- **Landlock's network rule where the kernel has it, and a per-run token always.**
