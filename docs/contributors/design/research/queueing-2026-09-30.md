> library fits Orpheum: the research behind D231 (2026-09-30).

# Queueing research (2026-09-30)

Two reports, asked for by the owner while deciding D231: how mature systems (mail transfer
agents, circuit breakers, job queues, brokers) handle work bound for an unreliable destination,
and whether a Go queue library could replace our own. History, not specification: D231 is the
decision.

## 1. Unreliable destinations

I read the queue, outbound, artwork and node code, and gathered primary sources on how mail servers, circuit breakers, job queues and messaging systems handle a destination that is down. All fetched pages are cached in `/yoloai/cache/queueing-research/` (raw HTML plus `.txt` extracts). The repo was not changed.

### Current behaviour

- **Queue** (`internal/core/jobs/runner.go`): an ordinary error spends an attempt. The waits start at `job_first_retry_delay_s` (30s) and double, capped at 24h. With `job_attempt_limit` at its default of 5, a job fails after about 7.5 minutes (30s + 60s + 120s + 240s). `RetryAtError` and `blocked` spend no attempt and pause that one runner (`pausedUntil`, held in memory). `blocked` always waits exactly 30s, and there is no jitter anywhere.
- **TMDB API** (`identify/match.go`): a 429 becomes `RetryAtError`, and a missing or refused key becomes `blocked`. But when TMDB is down (DNS failure, refused connection, timeout, 5xx), the error is a plain one. So every queued fetch job, one after another, sends its own request, waits up to `provider_timeout_s` (20s) and spends an attempt. A TMDB outage longer than about 7.5 minutes fails every fetch job in the queue. This is exactly the "hammer 1000 times" case you described.
- **TMDB image host** (`artwork/retry.go`, D213 §5): each source has a circuit breaker held in memory. Five failures in a row open it for the next step of the schedule (1m, 5m, 30m, 2h, 12h, then daily). While it is open, jobs get `RetryAtError` and spend nothing. The first job after it reopens is the probe; if that fails, it spends an attempt and the breaker opens again. The five jobs that tripped it each spent an attempt, and a restart forgets the breaker.
- **OpenSubtitles**: search and download run inside the user's HTTP request, not as jobs. Only converting a fetched subtitle is a job, and that one goes to a node.
- **Nodes** (`nodes/service.go`):
  - An entry in `connectedNodes` is created by the node's hello and is never removed. So `IsConnected` really means "has said hello since the core started"; it never turns false when a node disconnects.
  - `Enqueue` silently drops a command only for a node that has not said hello since the core started. For a node that connected and then dropped, commands pile up in memory.
  - A restarted node polls from sequence 0 and receives every command it never acknowledged, including ones whose jobs already gave up. The answers are then logged as "for no waiting job".
  - Prepare, subtitle and loudness jobs never check connection first: they send the command, wait `prepareMaxSilence` (5 min), then spend an attempt. Only artwork checks `IsConnected` first (a 1-minute `RetryAtError`).
  - The supervisor flags a node as silent after 30s and restarts it after 120s.

### 1. Common patterns

**A. Retry state belongs to the destination, not only the job.**
- Postfix's queue manager keeps a "destination status cache": an in-memory list of unreachable destinations. When the delivery agent blames the receiving party, the destination goes on a "dead" list and is skipped for at least `minimal_backoff_time` (300s). A destination is declared dead after `destination_concurrency_failed_cohort_limit` "pseudo-cohorts" fail (default 1, meaning one round of concurrent deliveries failing at connection or handshake). One successful delivery resets that count. Sources: [qmgr(8)](https://www.postfix.org/qmgr.8.html), [SCHEDULER_README](https://www.postfix.org/SCHEDULER_README.html), [TUNING_README](https://www.postfix.org/TUNING_README.html).
- Exim applies retries "on a per-host (strictly, per IP address) basis, not on a per-message basis… delivery of a new message to the same host is not immediately tried, but waits for the host's retry time". It keeps this in a "hints" database that is safe to delete ([Exim ch. 33](https://www.exim.org/exim-html-current/doc/html/spec_html/ch-retry_configuration.html)).
- Sendmail caches host status such as "host down" (`Timeout.hoststatus`, 30m) ([op guide](https://www.sendmail.org/~ca/email/doc8.12/op-sh-4.html)).

**B. Give up by elapsed time, not by attempt count.**
- Postfix's `maximal_queue_lifetime` is 5 days.
- Exim's cutoff "is measured from the time that the first failure for the domain… was detected… it is the length of continuous failure for the recipient address that counts."
- Temporal's default is unlimited attempts, and it recommends "the Schedule-To-Close Timeout… to limit the total duration of retries, rather than using [Maximum Attempts]" ([retry policies](https://docs.temporal.io/encyclopedia/retry-policies)).

**C. The item's failure and the destination's state are separate.**
- Postfix separates "blames the message" (the message backs off) from "blames the receiving party" (the destination is marked dead).
- Oban has three outcomes: `{:error}` (spends an attempt), `{:snooze}` ("a snooze never consumes an attempt") and `{:cancel}`/discard ([worker.ex](https://github.com/oban-bg/oban/blob/main/lib/oban/worker.ex)). It also has `pause_queue`/`resume_queue` ([oban.ex](https://github.com/oban-bg/oban/blob/main/lib/oban.ex)).
- Temporal has non-retryable errors and a per-error `NextRetryDelay` ([failures](https://docs.temporal.io/references/failures)).
- Kafka's `pause(partitions)` suspends fetching without losing a message's place ([KafkaConsumer](https://kafka.apache.org/36/javadoc/org/apache/kafka/clients/consumer/KafkaConsumer.html)).

**D. A circuit breaker with one trial call.**
- Nygard's *Release It!* introduced it. [Fowler](https://martinfowler.com/bliki/CircuitBreaker.html) describes the half-open state, in which "the circuit is ready to make a real call as trial", and says "operations staff should be able to trip or reset breakers".
- [resilience4j](https://resilience4j.readme.io/docs/circuitbreaker) allows a configurable number of calls while half-open (default 10) and has an `ignoreExceptions` list so business errors don't count as failures. [Polly](https://www.pollydocs.org/strategies/circuit-breaker.html) can lengthen the break each time it reopens, and offers manual isolation.
- [Envoy](https://www.envoyproxy.io/docs/envoy/latest/intro/arch_overview/upstream/outlier) ejects a failing host for base time × consecutive ejections, and pairs this passive detection with optional active health checks.

**E. Backoff needs jitter; retries amplify outages.**
- [AWS: Exponential Backoff and Jitter](https://aws.amazon.com/blogs/architecture/exponential-backoff-and-jitter/): "no-jitter exponential backoff… is the clear loser"; full jitter does the least work.
- [AWS Builders' Library](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/): three layers of retries turn load into 243×; "retry at a single point in the stack"; "retries are selfish"; cap retries with a token bucket.
- [Google SRE, Handling Overload](https://sre.google/sre-book/handling-overload/): at most 3 attempts per request, and retries limited to 10% of a client's requests.

**F. Resume by reconnecting, and ramp up slowly.**
- MQTT 5 §4.4: resend unacknowledged messages on reconnect, and "MUST NOT resend messages at any other time" ([spec](https://docs.oasis-open.org/mqtt/mqtt/v5.0/os/mqtt-v5.0-os.html)).
- Postfix's "slow start… eliminates 'thundering herd' problems" by raising concurrency gradually. Its "fairness" rule takes one message from the incoming queue and one from the deferred queue in turn, so a backlog cannot starve new mail.

**G. Dead-letter queues are for poison items, not outages.**
- SQS moves a message after `maxReceiveCount` receives, and warns to set it "high enough" ([DLQ](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-dead-letter-queues.html)).
- RabbitMQ dead-letters a message when it is rejected, expires or passes its delivery limit ([dlx](https://github.com/rabbitmq/rabbitmq-website/blob/main/docs/dlx.md)).
- Sidekiq retries 25 times over about 21 days, then moves the job to the Dead set for a person to retry by hand ([Error Handling](https://github.com/sidekiq/sidekiq/wiki/Error-Handling)).
- None of them detects a down destination. A long outage simply fills the dead-letter queue, which is why people redrive it by hand.

### 2. Where they disagree, and why

- **Circuit breakers or not.** AWS says breakers "introduce modal behavior… difficult to test, and can introduce significant additional time to recovery", and prefers token buckets. That is advice for high-volume request/response between services, where a success rate carries information. Mail servers and your case are the opposite: queued work, few destinations, where a synchronous caller cannot wait. There, a "dead" state per destination is standard.
- **Adaptive throttling needs traffic.** SRE notes that client-side throttling "may not work well with clients that only very sporadically send requests". A household server is sporadic, so an explicit up/down state fits better than ratio statistics.
- **Declaring a destination dead: fast or slow.** Postfix declares it after one failed cohort. Postfix before 2.5 waited for concurrency to reach zero, and resilience4j needs `minimumNumberOfCalls` (100). Postfix counts only connection and handshake failures, so declaring early is cheap and safe; a breaker that counts every error needs volume to avoid false trips.
- **Who probes.** Postfix, Exim and resilience4j (by default) let the next real item be the probe. Envoy and Fowler's monitored breaker also use a separate health check. A real item needs no probe endpoint, but if it fails it pays an attempt unless that is excused.
- **Attempts or time.** Sidekiq and SQS count attempts; mail and Temporal count time. Counting attempts is simple, but an outage uses them up.

### 3. Recommended design

**Concept: a destination has a state, and a job waiting on a down destination is parked, not failed.**

1. **Destinations.** A small fixed set:
   - `tmdb-api`
   - `tmdb-images`
   - `opensubtitles`, reserved in case its work ever becomes jobs
   - one per node
   
   Each job kind declares which destination it needs. An artwork job needs `tmdb-images` and then a node, so a handler can name the destination at run time.
2. **What counts as "down".** Only failures that say nothing about the item:
   - for outside hosts, `outbound.ErrUnavailable` (connection, DNS, timeout, 5xx);
   - for a node, "not connected" or silence.
   
   A 404, a refused key or a failure parsing the item are the item's own. A 429 is not "down" but "asked to wait". It keeps today's `RetryAtError` hold, which is really the same mechanism with the time chosen by the server.
   
   Declare a destination down on the first such failure, as Postfix does with a cohort limit of 1. At a household's volume there is nothing to average, and the failure classes are already narrow.
3. **A down destination parks work and spends nothing.** The failing job, and every job queued for that destination, is not claimed while it is down. Their attempt counts and back-off stay untouched, as with Oban's snooze or Kafka's pause. This extends the existing `blocked`/`pausedUntil` mechanism from one runner to a destination shared by every kind that uses it. It does not add a second queue: a separate "parked" queue would be a second way to do one job (rule 11), whereas a filter in `NextQueuedJob` does it.
4. **One probe.** For outside hosts, the next due job is the probe, and a probe failure costs no attempt. That removes the one wart of today's artwork breaker.
   - Probe interval: jittered back-off per destination, e.g. 30s doubling to about 1h. The Retry-After cap is already an hour; D213 §5's image schedule could become this.
   - Nodes get no probe: their hello or first long-poll *is* the recovery signal (the MQTT model), and the supervisor already restarts them.
   - `Enqueue` to a node that is not connected should mark the job waiting for that node rather than drop the command silently.
   - The node table should track the connection truthfully (connected / last heard / gone), not "said hello once".
5. **Resuming.** When the probe succeeds or the node says hello, wake that destination's runners. Runners are already one job at a time per provider, which is a natural slow start, so no concurrency ramp is needed. Two things are needed:
   - drop commands whose jobs have ended, so a reconnecting node does not do orphaned work;
   - keep the queue's priority order, so play-now work goes first.
6. **Giving up.** Keep `job_attempt_limit` for failures of the item itself. Time spent parked on a down destination counts against nothing, or against a long ceiling measured in time like Exim's cutoff. A job never fails merely because TMDB was down overnight.
7. **Where the state lives.** In memory, like Postfix's cache and Exim's "hints". After a restart the first job probes again. Nothing is lost, because the jobs themselves are in SQLite.
8. **What a person sees.** The job view shows parked jobs as "waiting for TMDB (unreachable since 14:02; next check 14:10)" instead of a list of failures. The System page lists each destination's state. A "check now" action, like Fowler's operator reset, would be cheap to add.

### 4. Owner decisions needed

1. Whether you want this at all: a concept of "destination" in the job queue, shared across job kinds. This is new design under the freeze (rule 1) and needs a D-number.
2. Whether time parked while a destination is down should count toward giving up, and if so, what time-based ceiling (e.g. mail's 5 days).
3. Whether to replace D213 §5's artwork breaker (and its separate retry schedule) with the general mechanism, or keep it as a special case.
4. Whether node jobs should wait indefinitely for their node, or fail after a ceiling, since a node can be retired.
5. Whether 5xx counts as "down", or only connection, DNS and timeout failures. Postfix counts only connection and handshake failures; a 5xx on one TMDB endpoint may not mean the whole API is down.
6. Whether to add jitter to all back-off. It is cheap and standard, but changes existing tested timings.
7. Whether parked state should be visible in the API/UI in Cut A, or only in logs.
## 2. Go queue libraries

I recommend keeping our own queue. None of these libraries does the part we actually need, which is per-destination up/down state, and the one serious candidate would add more code to audit than it removes. If the owner wants a library for the rest, River with its SQLite driver is the only real fit. Two small resilience libraries could replace a few dozen lines, but they don't do the parking either.

Sources are cached under `/yoloai/cache/go-queue-survey/`: the repos in `repos/`, GitHub metadata in `api/`, the latest versions from proxy.golang.org in `latest.txt`, and dependency trees measured by building a small test module per library in `depprobe/`. Nothing in the repo was changed.

### The real candidates

**1. River with riversqlite.** It is the only maintained library that works as an in-process job system on SQLite, and its model is close to ours: kinds, JSON args, a job table, snooze, cancel, list, pause, a retry policy per worker, and an injectable test clock (`Config.Test.Time`). It builds cleanly with modernc.org/sqlite, needs no cgo, and pgx does not end up in our dependencies. It has a lot of company support and releases often: ten releases between 2026-07-02 and 09-01.

What it would replace: `queue.go`, `runner.go` and most of `view.go` (about 630 lines), crash requeue, the per-kind wake-ups, doubling back-off, and `RetryAtError`, which becomes `JobSnooze`.

What we would still have to build or bend:
- **All of the destination design.** River's `QueuePause` is manual, applies to a whole queue, and has no timed resume or probe. A kind that needs two destinations in turn (artwork needs TMDB images, then a node) doesn't map onto "a queue per destination". Parking, the single probe, resuming in priority order and showing destination state stay ours.
- `MarkBlocked`'s timed hold on a kind has no River equivalent.
- **Priority.** Ours is an integer with play-now at 1000; River allows only 1–4.
- **Raising priority on a repeat request.** Neither our queue nor River does this. A "play now" request for a target that already has a job keeps that job's old priority either way.
- **Progress.** River has no `progress_fraction`; it would need metadata or a side table.
- **`EverQueued`.** It depends on job history (D170). River deletes completed jobs after 24 hours unless `CompletedJobRetentionPeriod` is set to -1.
- **The job view contract.** River's states (available, scheduled, retryable, discarded…) change `api/openapi.json`, the SDK and the web jobs page.
- **We would lose our target columns.** Today each target is its own typed column; under River it becomes a field inside JSON args, marked `river:"unique"`.

Migration cost: rewrite all eight kinds' registrations in `cmd/orpheum/metadata.go`, about 30 `Enqueue` call sites, the job API and web view, and `jobs_test.go`/`view_test.go` (about 500 lines), which would be written again against River. There are also structural costs:
- **Where River lives.** Only `internal/store` may import `database/sql`, so River's client has to be built there.
- **A second writer on cache.db.** River wants its own pool with `MaxOpenConns(1)`, running alongside our writer, which risks `SQLITE_BUSY`. River also keeps writing in the background even when idle: leader election, a notification table, maintenance.
- **Migrations.** River has its own versioned migrations. Each one (up to step 8 so far; step 7 required stopping the app) has to become one of our cache.db steps. Because cache.db is never backed up and can be rebuilt, this is easier.

Dependency cost: 11 new modules (MPL-2.0, MIT, BSD), all pure Go, so arm64 and riscv64 are fine. MPL-2.0 can be combined with our GPL-3.0; I checked and River's files do not carry the "Incompatible With Secondary Licenses" notice. Under D220, though, auditing about **25,000 lines** of non-test River code, plus reviewing a pre-1.0 project's frequent release diffs, is far more than maintaining our 627 lines.

**2. failsafe-go, or gobreaker plus backoff, for the resilience parts only.** Either could replace `doubledDelay`, add jitter, and replace D213 §5's hand-written artwork breaker. But they are built around synchronous calls and keep their state in memory. A breaker can tell us "TMDB is open" but can't park the rows in our queue; the part that ties that state to not claiming jobs is still ours. The first failsafe release was 2023 and it is still pre-1.0. It uses 8,600 lines to cover the whole library, when we would use perhaps 100 lines' worth. Neither library's clock can be swapped for `clocktest`, which conflicts with rule 16. Jitter plus a small table of destination states is about 50 lines against our existing clock.

### Recommendation

Keep the queue and build the destination state on it, as the design in `queueing-research.md` proposes.

The trade-off: River would save us owning about 400 lines of well-trodden mechanics (claiming, retry, snooze, cancel, crash recovery). In return we'd take on a pre-1.0 SQLite driver its own authors call barely field-tested, 25,000 lines to audit under D220, a second writer and a foreign migration history on cache.db, a 1–4 priority scale, and changes to the job API. It still wouldn't give us parking, the probe or visible destination state, which is the work actually ahead of us.

If the owner values "not our code" above audit size, River is the one to pick, and a spike should first check whether it can share `store`'s single writer on cache.db. Otherwise nothing surveyed justifies a dependency. Borrow River's ideas instead: its ±10% jitter, a snooze that never costs an attempt, and a separate "discarded" state for jobs that have used up their attempts.

### Needs the owner's decision

1. Adopt River (the heavier dependency) or keep and extend our queue. My recommendation is to keep it.
2. If River: approve 11 modules for `deps/go.allow`, accept MPL-2.0 alongside GPL-3.0, accept a pre-1.0 driver marked "early testing", and accept a second SQLite writer plus River's own migrations in cache.db.
3. If River: accept the 1–4 priority scale and the change to the job API's states. Either needs a D-number, since Cut A's design is frozen.
4. Whether any resilience library is worth adding for jitter and the breaker. I recommend no, because none takes a testable clock (rule 16), unless the owner accepts `testing/synctest` as a stand-in for `clocktest`.
5. Separately from which library, and not something any of them provides: should a repeat request for an open job raise its priority (for example, a queued prepare that someone now wants to play)? Today it doesn't.
