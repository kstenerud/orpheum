# B0: a household can join the beta

- **Status:** PLANNED — phased 2026-10-18 from [closed-beta.md](closed-beta.md) B0, D310–D314. Phase
  A's questions are answered (D314); phase B starts with the password sign-in's design, written
  first.
- **Depends on:** [closed-beta.md](closed-beta.md), [discovery-core.md](discovery-core.md),
  [release.md](release.md), the paid service's service.md and spec.md (orpheum-connect)

What B0 ends with (closed-beta.md, proposed): a household that has only an invitation link, on a
machine it has not set up before, gets from nothing to playing a film at app.orpheum-app.com with no
help from the operator. The phases run in this order because each stands on the one before; bug
reports and run-time log levels go in whichever phase has room, since they help test the rest.

Every phase: behaviour changes carry tests that fail when reverted; `make check-pr` passes at its
end; work in orpheum-connect passes its own gate.

## Phase A — a core anyone can install

Today a core is built from the private repository on the machine that runs it (release.md), and
waits on a WireGuard tunnel to a VPS (`internal/deployment/templates/compose.yaml`: every service
depends on `orpheum-tunnel`), which D310 §1 says no beta household sets up. D272 §3 decided the
tunnel would be optional; it was never built.

1. **The tunnel-less deployment** (D272 §3, D314 §3): `write-deployment` writes a core with no
   tunnel service, reached through its discovery over WebRTC and its LAN names (D300), publishing
   only the LAN ports. *Built 2026-10-18.* Staging drops its tunnel once the install is
   ready, so it runs what a beta household runs; nas.example keeps its tunnel until the owner says
   (the owner, 2026-10-18).
2. **A prebuilt image** a household pulls, so no source and no build on the target. *Built
   2026-10-18: a version tag publishes ghcr.io/kstenerud/orpheum:<tag> and :latest; the
   owner makes the package public once.*
3. **An install a household follows alone**: one command or a short script that writes the
   deployment and starts it, the first admin made from the setup code shown where the household
   looks (not only the log), and the host's checks (Landlock, BBR, a GPU) reported, never required.
   *Built 2026-10-18:* `docker run --rm IMAGE install-script | sh -s -- --media /path/to/films`;
   deploy/release/build.sh installs through the same script.
4. **The core's page for the key** (D310 §5): signed in at home, the admin enters the account's key;
   the core enrols with the paid service and shows which account holds it.

## Phase C — enrolment, and what keeps it safe

1. **Generate key** (built) on the account's panel: 16 safe32 characters, an hour, one use, hashed at rest,
   compared in constant time, failures limited (D310 §8, D312 §5).
2. **Enrolling with it** (built) from the core's System → Discovery; a new key removes the old core at once:
   sessions revoked, names withdrawn, connections closed, its System page saying so (D310 §9, D312
   §15).
3. **The account's realm** (D298 §2, §3; added 2026-10-19, the owner: a household must finish
   alone; *built 2026-10-19, orpheum-connect*): the master realm chosen on the join page, or on the account's page by an account made
   before, once, first come first served, never changed; a key made only once it is chosen, and a
   core claimed by it given it. A realm the operator gave a core by hand is taken like any other.
   Subrealms wait for a second core per account.
4. **The record and the re-confirmation** for what moves a household (D312 §1, §14, §16). *Built
   2026-10-19 (orpheum-connect, and before):* a key, a password change and a passkey's change
   ask for the password or a passkey again, and keys are limited to five a day; the record holds
   each key made, each server enrolled, replaced or removed by its id and fingerprint and where it
   came from, and the realm chosen. Re-issuing an invitation is the operator's alone in the beta,
   on the passkey-only panel.
5. **The household told when its core changed**, and a device that knows the old fingerprint
   stopping with a warning (D312 §2). *Built 2026-10-19:* the account's address is mailed at each
   enrolment, naming the server and the one it replaced by fingerprint; the old core's System page
   says it was removed; a browser that reached the realm's server before keeps it, gone or not, and a
   realm sign-in that finds another server for the realm stops with a warning, dated by when the new
   one was claimed, until its person goes on.
6. **The operator's claim by code from the console, for customers, retired** (D310). *Built
   2026-10-19 (orpheum-connect):* a service with accounts gives a pending core no claim
   code, so its System page shows the key form alone; production's `up.sh` has no `claim`.
   `connectd claim` stays for a service without accounts, and the own-discovery's claim by code
   (discovery/single) is unchanged.

## Phase D — every code to one pattern (D311)

On the core: its registration invitations, Watch Together's links and device codes take D318's one
shape (several outstanding for one entitlement, any one redeemed ending them all, revoking ending
every one), each show what they made, and each can be issued again for the same entitlement, the new code's redemption ending
the old sessions and credentials (D311 §5, D312 §3); links redeemed by an action on their page, the
secret in the fragment (D312 §10, §11).

*Built 2026-10-19:* a person's registration links all work until one is used, which ends the
others, sets the password and signs them out elsewhere; an invitation may have several
links, sent again from the admin's list, any one used ending the others, and the used one names
the account it made (migration 0053). Links already carry their secret in the fragment
and are redeemed by a button. Device codes need nothing: a device asking again keeps its code, and
one signing in again by its proof is the same device, not the entitlement moving. *Waiting on the
owner:* whether a Watch Together guest given a new link is cut off at once, as now (D267 §4, D311
§5), or only once the new link is used (D312 §3).

## Phase A's questions, answered (D314)

1. **A public container registry**, from the start (*"it will be public eventually anyway"*).
2. **Any machine that runs Docker with the hardware passthrough the node needs**; amd64 and arm64
   where every piece builds. Windows is being researched separately (WSL and Docker Desktop).
3. **No public relay without the tunnel is accepted, and each failure that needed one is recorded**
   (D274 §3's count). The tunnel stays as an option.
