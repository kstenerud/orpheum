# B0: a household can join the beta

- **Status:** PLANNED — phased 2026-10-18 from [closed-beta.md](closed-beta.md) B0, D310–D313. Phase
  A waits on the owner's answers to its questions; phase B on the password sign-in's design, written
  first.
- **Depends on:** [closed-beta.md](closed-beta.md), [discovery-core.md](discovery-core.md),
  [release.md](release.md), the paid service's service.md and spec.md (orpheum-connect)

What B0 ends with (closed-beta.md, proposed): a household that has only an invitation link, on a
machine it has not set up before, gets from nothing to playing a film at app.orpheum-app.com with no
help from the operator. The phases run in this order because each stands on the one before; bug
reports and run-time log levels go in whichever phase has room, since they help test the rest.

Every phase: behaviour changes carry tests that fail when reverted; `make check-pr` passes at its
end; work in orpheum-connect passes its own gate.

## Phase A — a core anyone can install

Today a core is built from the private repository on the machine that runs it (release.md), and
waits on a WireGuard tunnel to a VPS (`internal/deployment/templates/compose.yaml`: every service
depends on `orpheum-tunnel`), which D310 §1 says no beta household sets up. D272 §3 decided the
tunnel would be optional; it was never built.

1. **The tunnel-less deployment** (D272 §3): `write-deployment` writes a core with no tunnel
   service, reached through its discovery over WebRTC and its LAN names (D300), publishing only the
   LAN ports. The tunnel stays for the owner's own setup.
2. **A prebuilt image** a household pulls, so no source and no build on the target.
3. **An install a household follows alone**: one command or a short script that writes the
   deployment and starts it, the first admin made from the setup code shown where the household
   looks (not only the log), and the host's checks (Landlock, BBR, a GPU) reported, never required.
4. **The core's page for the key** (D310 §5): signed in at home, the admin enters the account's key;
   the core enrols with the paid service and shows which account holds it.

**Questions for the owner** (below, "Phase A's questions").

## Phase B — the paid service's accounts (orpheum-connect)

1. **The design of the password sign-in, written first**, to D312 §6–§9 and §17: argon2id, at least
   15 characters while the password stands alone, the breached-password check by k-anonymity, slowed
   guessing without lockout, every failure answered after one time, sessions with an idle and an
   absolute limit, listed and revocable.
2. **Accounts and sessions**, the account's panel showing its server.
3. **Passkeys** (D312 §7).
4. **The operator's panel** over the WireGuard network only, with its own passkey (D312 §4), and
   **invitations** with notes, their redemption making an account (D310 §10, §13).
5. **The free-for-life mark and test accounts** (D312 §13).

## Phase C — enrolment, and what keeps it safe

1. **Generate key** on the account's panel: 16 safe32 characters, an hour, one use, hashed at rest,
   compared in constant time, failures limited (D310 §8, D312 §5).
2. **Enrolling with it** from the core (phase A's page); a new key removes the old core at once:
   sessions revoked, names withdrawn, connections closed, its System page saying so (D310 §9, D312
   §15).
3. **The record and the re-confirmation** for what moves a household (D312 §1, §14, §16).
4. **The household told when its core changed**, and a device that knows the old fingerprint
   stopping with a warning (D312 §2).
5. The operator's claim by code from the console, for customers, retired (D310).

## Phase D — every code to one pattern (D311)

On the core: its registration invitations, Watch Together's links and device codes each show what
they made, and each can be issued again for the same entitlement, the new code's redemption ending
the old sessions and credentials (D311 §5, D312 §3); links redeemed by an action on their page, the
secret in the fragment (D312 §10, §11).

## Phase E — recovery, healing connections, the System page

1. **The identity key's recovery code** (K8a, D292 §4).
2. **ICE restart and network change events** (K3b, K4).
3. **The System page in plain words**, the first-run form and the home address (K12), and counting
   where people get stuck (K16).

## Phase F — the service made whole, and B0's acceptance

1. **The service's thickening** (service.md M-S1–M-S4, M-S6): the probe whole, names and certificates
   whole, caps, client integrity with its kill switch, operations and lapse.
2. **Terms, privacy policy, Impressum** (P13), from the drafts.
3. **B0's acceptance**, run as a household would: a fresh machine, an invitation, nothing else.

## Phase A's questions

1. **Where does a household get the core?** The choices: a prebuilt image on a container registry
   (private, needing each tester given pull access; or public, the image published while the source
   stays private); or a file the operator hands out (as the paid service's package is). A registry
   is what makes "one command" possible.
2. **Which machines does the closed beta support?** Plain Docker on any Linux machine, and which
   NAS families (Synology, Unraid, TrueNAS, a Proxmox LXC as nas.example is); amd64 only, or ARM too.
3. **With no tunnel, a household has no public relay for WebRTC.** WebRTC connects most devices
   directly, but two devices both behind restrictive NATs need a relay to meet, and the paid service
   relays nothing (D273 §2). Is that acceptable for the closed beta, with the failure counted (K16)
   so the beta shows how often it happens, or should the tunnel stay as an option for a household
   that has a VPS?
